# Bugbot review rules: Cypress Documentation

This is a **Docusaurus 3** documentation site. Almost every PR changes
`docs/**/*.mdx` content, not application code, so the bugs that matter here are
_docs bugs_: content that renders fine and passes CI but is wrong, unreachable,
or silently drifts from the rest of the site.

The repo's conventions are written down in
[`AGENTS.md`](../AGENTS.md) (the short rules) and
[`AGENTS_REFERENCE.md`](../AGENTS_REFERENCE.md) (the detail). Treat those as the
spec. This file says what to **review for** and what to **stay quiet about**.

## Do not comment on these

Every one of these is already enforced, or is a human's call. Comments here are
pure noise:

- **Formatting.** Prettier runs on `**/*.{md,mdx}` in a pre-commit hook and in
  CI. Never comment on wrapping, spacing, quotes, or line length.
- **Frontmatter presence or key order.** `npm run lint:frontmatter` enforces
  that `title`, `description`, and `sidebar_label` exist and that keys follow
  the canonical order. Only comment on frontmatter _content_ (see below).
- **Broken internal links and heading anchors.** `onBrokenLinks`,
  `onBrokenAnchors`, and `onBrokenMarkdownLinks` are all `throw`, so the build
  already fails on these. The exceptions in "URLs the build never checks" below
  are the only link comments worth making.
- **Anchor casing looking wrong.** Anchors intentionally preserve heading case
  (`#Disabling-Web-Security`) via a `patch-package` patch. This is correct.
- **Line-editing prose.** Wording, tone, and structure are what human reviewers
  spend their time on. Do not suggest rewrites for readability, and do not
  restate a paragraph "more clearly". The hard writing rules below are the only
  prose rules to enforce.
- **Missing tests for `docs/**` changes.\*\* Content changes are covered by the
  e2e specs that visit every page.

## Flag these

### 1. Content that silently breaks after merge

The build catches broken links _inside the site_. It catches none of this:

- **A page was renamed, moved, or deleted without a `301` in
  `static/_redirects`.** This is the single highest-cost miss in the repo:
  inbound links and bookmarks die and nothing fails. Check the PR's
  renames/deletions under `docs/` against new lines in `static/_redirects`, the
  live redirect list (~200 entries). Exact paths belong above the wildcard (`*`)
  rules at the end of the file.
- **URLs the build never checks.** Docusaurus only validates links it can see as
  internal markdown links. Verify by hand that these resolve to a real page:
  - absolute `https://docs.cypress.io/...` URLs (treated as external, unchecked)
  - any URL inside a `<CopyPrompt prompt={...}>` string
  - any URL inside a fenced code block
  - `<page-url>.md` markdown URLs used in prompts, which must correspond to a
    real page (and `#section` variants to a real `##` heading)
- **Images that 404.** `<DocsImage src="/img/..." />` is a JSX prop, not a
  markdown link, so a missing file under `static/img/` is never caught. Check
  that every added or changed `src` points at a file the PR adds or that already
  exists.
- **UTM params.** Links to `www.cypress.io`, `on.cypress.io`, or
  `learn.cypress.io` need `utm_source=docs.cypress.io` plus a placement
  `utm_medium`. Internal links, `cloud.cypress.io`, and third-party links must
  **not** have them.
- **A hand-edited `sidebars.js` entry for a new page.** Sidebars are
  autogenerated from the folder structure; ordering belongs in
  `sidebar_position` / `_category_.json`.

### 2. Hand-written markup where a component or directive exists

Each of these renders acceptably, which is why it slips through, but it breaks
site-wide consistency and TS/JS parity. Flag and name the replacement:

- A `defineConfig(...)` block or config tabs written by hand → must be
  `:::cypress-config-example` (or `:::cypress-config-plugin-example`).
- Hand-written npm/Yarn/pnpm/Bun tab sets → `<PackageManagerTabs>` (or
  `<CypressCommandTabs>`), or one of the existing shared partials
  (`<CypressInstallCommands />`, `<CypressOpenCommands />`, …).
- A hand-maintained JavaScript copy of a TypeScript snippet → one `ts` block
  tagged `copyTsToJs`.
- Near-duplicate e2e/component snippets differing only in `cy.visit` vs
  `cy.mount` → `:::visit-mount-example`.
- Raw HTML `<img>`/`<video>` → `<DocsImage>` / `<DocsVideo>`.
- A code block holding a **reusable** AI prompt → `<CopyPrompt>` (and the
  reverse: example-specific prompts, commands, and config belong in code
  blocks, not `<CopyPrompt>`).
- A new `docs/partials/_*.mdx` rendered in only **one** place, or a PR that
  removes the second-to-last usage of an existing partial. Partials must have
  more than one render site; otherwise inline the content.
- A new `<Icon name="..." />` whose icon is not imported under the
  `fontawesome` key in `src/theme/MDXComponents.js` (this one renders blank).
- A fenced code block with no language tag (` ``` ` on its own), or a file
  snippet with no `title="file.ext"` → tag the language and title the file.
- A tab group nested inside another `<Tabs>`, or a `copyTsToJs` block inside
  framework tabs (it renders its own tabs) → one level of tabs, with a plain
  `js` block inside.

### 3. Accuracy of what is documented

This is where Bugbot's code reading is most valuable. Verify claims against the
repo rather than accepting them:

- **Sample code that would not run.** Invalid Cypress usage in `.mdx` snippets:
  a `cy.*` command that does not exist, `await` on a Cypress chain, assertions
  chained off a command that yields nothing, a `cy.origin()` callback closing
  over outer-scope variables, syntax errors.
- **A fixed `cy.wait(ms)` in added test code** (`cy.wait(2000)`). Wait on a
  retrying assertion or `cy.wait('@alias')` instead. Exempt a short pause
  between polls of an endpoint with nothing else to wait on, and pages that
  exist to show the pattern.
- **Hosts outside `cypress.io` in examples.** `example.com`, a third-party site,
  or an invented domain in a code block or a sample URL in prose
  (`https://example.com/products/123`) → a real Cypress site or a stand-in such
  as `app.cypress.io`. `localhost` is fine. Exempt alt text that describes a
  diagram of a literal URL.
- **Config options, CLI flags, and env vars that do not match the reference.**
  Cross-check names, defaults, and types against
  `docs/app/references/configuration.mdx` and
  `docs/app/references/command-line.mdx`. A new option documented in a guide but
  missing from the reference table (or vice versa) is a real defect.
- **Version claims.** "Added in", "deprecated in", and minimum-version
  statements should match the changelog entry in the same PR or an existing one.
- **Contradictions with the rest of the site.** If a PR changes how a behavior
  is described, look for other pages still describing the old behavior and name
  them.
- **Missing `<ProductHeading product="…" />`** on a new product page, or a wrong
  `product` / `plan` value.
- **Frontmatter content** (not shape): a `description` copy-pasted from another
  page, a `title` that ignores the section's house style (API reference pages
  are terse, `'cy.blur()'`; guides are descriptive), a `title` ending in
  `| Cypress Documentation` (the build appends the section suffix, and
  `page_titles.cy.ts` asserts it), a `keywords` field (banned), or a
  `sidebar_position` introduced into a folder whose siblings don't use one.
- **Weak `alt` text** on `<DocsImage>`: "screenshot", "image of…", or text that
  just repeats the adjacent caption. Alt text should name what the reader is
  meant to notice.

### 4. Hard writing rules (only these)

- **Em dashes.** Flag added em dashes (`—`) in prose; use commas, periods, or
  parentheses.
- **Minimizing words.** "simply", "just", "easy", "obviously" in instructions.
- **Bold vs quotes for UI labels.** Bold is only for real controls the reader
  acts on (the **App Quality** tab). Hypothetical labels in illustrative
  examples go in `"quotes"`.
- **Product names.** Cypress App, Cypress Cloud, Cypress Accessibility, UI
  Coverage (no "Cypress" prefix on UI Coverage).
- **House terminology.** `.textlintrc` holds the term list (Cypress Cloud not
  "Cypress cloud", `localStorage`, "end-to-end", "retry-ability", American
  spellings, no "blacklist"/"whitelist"). Nothing runs textlint today, so these
  are unenforced: flag clear violations in added prose only.
- **Product names in frontmatter.** The product-name and terminology rules
  above apply to frontmatter `title` and `description` values too. Flag a
  lowercase "cypress" or "Cypress app" there (`title: 'Run cypress in…'`).
- **Heading case and form.** An added H2 or H3 in Title Case
  (`## Running Cypress Tests Interactively`), or one that opens with a gerund
  (`## Running…`, `## Configuring…`). Headings are sentence case and name a task
  with an imperative verb. Exempt the fixed API page skeleton, function-name
  headings on namespace API pages, and `## See also`. Don't judge whether a
  heading stands on its own; that's a human call.
- **Release numbers in body text.** An added Cypress version in prose or an
  admonition ("in Cypress 16.3.0 and later", a `:::info` naming the release that
  added a feature). Exempt `## History` tables, changelogs, and migration,
  deprecation, or removal notes.
- **Agent instructions in a code block.** A reusable agent instruction (an
  `AGENTS.md` recipe, a rule, or a skill body meant to be copied) added as a
  fenced block (` ```md title="AGENTS.md" `) → `<CopyPrompt>`. This is the
  agent-instruction case of the `<CopyPrompt>` rule in section 2, so raise it
  once. Example-specific prompts and commands stay in code blocks.
- **Custom admonition titles.** `:::tip Do this` or `:::note Requirements`. Site
  CSS hides every admonition heading; use a bold lead line in the body instead.
- **`:::warning`.** Use `:::caution`.
- **Single-`l` cancel forms.** "canceled", "canceling", "cancelation" in prose →
  "cancelled", "cancelling", "cancellation". Exempt quoted API values and UI
  strings.
- **Formal words and filler.** "leverage", "utilize", "in order to", "please",
  "note that".
- **"a11y" in prose** ("partial a11y coverage") → "accessibility". Exempt names
  such as `checkA11y()`, `data-a11y-ignore`, and identifiers.
- **Generic link text.** `[here]`, `[this link]`, `[learn more]`, `[click here]`.
  Link text names its destination.

### 5. Code changes: `plugins/`, `scripts/`, `src/`, `cypress/`

Review these with normal code-review rigor. The `CI` GitHub Actions workflow
runs the build, Prettier, the frontmatter linter, `npm run typecheck`, the unit
tests (Algolia/search and the plugins), and the e2e specs, so type errors and
plugin regressions fail the PR rather than reaching `main`. Don't re-report what
those catch; look for what they can't.

- `npm run typecheck` covers `src/`, `cypress/`, and `cypress.config.ts`;
  `plugins/*` are type checked by their own `tsc` builds. Casts (`as any`,
  `as SomeType`) that silence an error rather than fix it are worth flagging,
  since they pass the gate.
- A behavior change in `plugins/cypressRemarkPlugins` or `plugins/llm` with no
  corresponding Vitest change: the suites run in CI, so an untested change is
  green but unguarded. Flag missing test coverage here.
- Remark/unist visitors: mutating `children` while iterating, assuming a node
  type without checking, and dropping `position` data are the recurring bugs.
- **Dependencies for `plugins/*` belong in the root `package.json`.** The
  sub-packages are never installed on their own; a dependency added to a
  plugin's own `package.json` is never installed and just drifts stale.
- Changes to the LLM export or `.md` routes should keep every page reachable at
  `<page-url>.md` and its `##` sections at `<page-url>/<h2-slug>.md`.

### 6. `.github/workflows/`

- Jobs that push commits, open PRs, or use repo secrets must carry a job-level
  guard, or they fail noisily in the many forks of this repo:
  `if: (github.ref == 'refs/heads/main') && (github.repository == 'cypress-io/cypress-documentation')`.
- Actions must be pinned to a major tag (`@v4`), and the tag should be one that
  actually exists.

## How to comment

- One comment per distinct defect, on the exact line, with the fix stated.
- Only raise something you can point at in the diff or verify in the repo. If a
  claim needs product knowledge you don't have, say what you'd check rather than
  asserting it is wrong.
- Prefer silence over a marginal comment. A PR touching only prose in a single
  page will usually have nothing worth flagging, and that is a fine outcome.
