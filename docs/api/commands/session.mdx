# session

Cache and restore [cookies](/api/cypress-api/cookies),
[`localStorage`](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage),
and
[`sessionStorage`](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage)
(together, the session data) to recreate a consistent browser context between
tests. Your login code runs the first time, and later calls to `cy.session()`
with the same `id` restore the saved session instead of logging in again. For a
walkthrough of adding it to an existing login, see
[Caching login sessions](/app/guides/authentication-testing/caching-login-sessions).

`cy.session()` inherits the
[`testIsolation`](/app/core-concepts/writing-and-organizing-tests#Test-Isolation)
value to determine whether the page is cleared when it caches and restores the
browser context.

## Syntax

```javascript
cy.session(id, setup)
cy.session(id, setup, options)
```

### Usage

<Icon name="check-circle" color="green" /> **Correct Usage**

```javascript
// Caching session when logging in via page visit
cy.session(name, () => {
  cy.visit('/login')
  cy.get('[data-test=name]').type(name)
  cy.get('[data-test=password]').type('s3cr3t')
  cy.get('form').contains('Log In').click()
  cy.url().should('contain', '/login-successful')
})

// Caching session when logging in via API
cy.session(username, () => {
  cy.request({
    method: 'POST',
    url: '/login',
    body: { username, password },
  }).then(({ body }) => {
    window.localStorage.setItem('authToken', body.token)
  })
})
```

<Icon name="exclamation-triangle" color="red" /> **Incorrect Usage**

```javascript
// visiting before calling cy.session() is redundant, it needs to
// be done inside the setup function
cy.visit('/login')
cy.session(name, () => {
  // need to call cy.visit() here because the page is blank when
  // the setup function runs
  cy.get('[data-test=name]').type(name)
  cy.get('[data-test=password]').type('s3cr3t')
  cy.get('form').contains('Log In').click()
  // should assert that login was successful here to guarantee the
  // login process completes before it is cached
})
// should have asserted this inside the cy.session() setup
// function because the page is blank here
cy.url().should('contain', '/login-successful')
```

### Arguments

<Icon name="angle-right" /> **id _(String, Array, Object)_**

A unique identifier that Cypress uses to cache and restore a given session. In
simple cases, a `String` value is sufficient. If you pass an `Array` or
`Object`, Cypress generates the id for you by deterministically stringifying the
value. For example, `['Jane', '123', 'admin']` becomes the id
`["Jane","123","admin"]`.

:::info

See
[Choose a unique id for each `cy.session()` session](#Choose-a-unique-id-for-each-cysession-session)
for how to build an `id` that caches each session separately.

:::

:::caution

Large or cyclical data structures may be slow or difficult to
serialize into an identifier, so exercise care with the data you specify.

:::

<Icon name="angle-right" /> **setup _(Function)_**

Cypress calls this function whenever a session for the given `id` hasn't been
cached yet, or when the cached session is no longer valid (see the `validate`
option). After `setup` and `validate` run for the first time, Cypress saves all
cookies, `localStorage`, and `sessionStorage`, so later calls to `cy.session()`
with the same `id` skip `setup` and restore and validate the cached session data
instead.

The page is cleared before `setup` when `testIsolation` is enabled and is not
cleared when `testIsolation` is disabled.

Cookies, local storage, and session storage in all domains are always cleared
before `setup` runs, regardless of the `testIsolation` configuration.

<Icon name="angle-right" /> **options _(Object)_**

| Option             | Default     | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------ | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `validate`         | `undefined` | Validates the newly created or restored session. Cypress runs this function right after `setup` creates a session, and right after a cached session is restored. The session is invalid if the function throws an exception, contains a failing Cypress command, returns a Promise that rejects or resolves to `false`, or returns nothing (or a Cypress chain) and its last Cypress command yields `false`.<br/><br/>- If validation fails immediately after `setup`, the test fails.<br/>- If validation fails after restoring a session, `setup` runs again. |
| `cacheAcrossSpecs` | `false`     | When `true`, the session is "global": any spec in the same Cypress run on the same machine can restore it. Use this option for a session that many specs share.                                                                                                                                                                                                                                                                                                                                                                                                 |

<HeaderYields />

- `cy.session()` yields the status of the session:
  - `'created'` when `setup` ran for a new session.
  - `'restored'` when a saved session was restored.
  - `'recreated'` when a restored session failed validation and `setup` ran
    again.
- In Cypress 16.2.0 and earlier, the TypeScript types declare the yielded value
  as `null`, even though the command yields the status at runtime.

## Examples

### Cache a login custom command with `cy.session()`

Wrap the body of your login
[custom command](/api/cypress-api/custom-commands) in `cy.session()`. The first
call logs in and saves the session; later calls with the same `username`
restore it, and `validate` confirms the restored session still works. For a
step-by-step migration of an existing login command, see
[Caching login sessions](/app/guides/authentication-testing/caching-login-sessions).

```typescript copyTsToJs
declare global {
  namespace Cypress {
    interface Chainable {
      login(username: string, password: string): Chainable<void>
    }
  }
}

Cypress.Commands.add('login', (username, password) => {
  cy.session(
    username,
    () => {
      cy.visit('/login')
      cy.get('[data-test=name]').type(username)
      cy.get('[data-test=password]').type(password)
      cy.get('form').contains('Log In').click()
      cy.url().should('contain', '/login-successful')
    },
    {
      validate() {
        cy.request('/whoami').its('status').should('eq', 200)
      },
    }
  )
})

export {}
```

### Switch users within a test using `cy.session()`

Because `cy.session()` clears the page and all session data before running
`setup`, you can use it to switch between sessions without first logging the
previous user out. Tests represent real-world scenarios more accurately, and
run times stay short.

```javascript
const login = (name) => {
  cy.session(name, () => {
    cy.request({
      method: 'POST',
      url: '/login',
      body: { name, password: 's3cr3t' },
    }).then(({ body }) => {
      window.localStorage.setItem('authToken', body.token)
    })
  })
}

it('should transfer money between users', () => {
  login('user')
  cy.visit('/transfer')
  cy.get('#amount').type('100.00')
  cy.get('#send-money').click()

  login('other-user')
  cy.visit('/account_balance')
  cy.get('#balance').should('have.text', '100.00')
})
```

### Validate a restored session with `cy.session()`

The `validate` function confirms the session was established correctly. It
matters most when a cached session is restored: if the restored session isn't
valid, `cy.session()` recreates it by running `setup` again.

These scenarios mark the session as invalid:

- The `validate` function throws an exception.
- The `validate` function returns a Promise that resolves to `false` or rejects.
- The `validate` function contains a failing Cypress command.
- The `validate` function returns nothing (or a Cypress chain), and its last
  Cypress command yields `false`.

A `validate` function that returns `false` directly, without a Promise, leaves
the session valid. Cypress checks the last command's yielded value only when
`validate` returns nothing or a Cypress chain, so a function that returns a
Promise is judged by the Promise alone. To fail validation on a condition,
assert it with a Cypress command or yield `false` from the last command.

Here are a few `validate` examples:

```javascript
// Visit a page that only a logged-in user can see
function validate() {
  cy.visit('/private')
}

// Make an API request that returns a 200 only when logged in
function validate() {
  cy.request('/api/user').its('status').should('eq', 200)
}

// Visit a page that redirects to /login when the user isn't logged in
function validate() {
  cy.visit('/account', { failOnStatusCode: false })
  cy.location('pathname').should('eq', '/account')
}
```

### Change which session data `cy.session()` caches

To change which session data is cached, modify cookies, `localStorage`, and
`sessionStorage` as needed at the end of `setup`. Cypress saves the session
data as it stands when `setup` and `validate` finish.

```javascript
cy.session('user', () => {
  cy.visit('/login')
  cy.get('[data-test=name]').type('user')
  cy.get('[data-test=password]').type('p4ssw0rd123')
  cy.get('#submit').click()
  cy.url().should('contain', '/home')
  // Remove session data we don't want to cache
  cy.clearCookie('authId')
  cy.window().then((win) => {
    win.localStorage.removeItem('authToken')
  })
  // Add session data we do want to cache
  cy.setCookie('session_id', '189jd09sufh33aaiidhf99d09')
})
```

### Share a `cy.session()` session across specs

To reuse the same session across multiple specs in the same Cypress run on the
same machine, set `cacheAcrossSpecs: true` in the session options. Define the
login function once, for example in a support file, and call it from each spec.

```javascript
const login = (name = 'user1') => {
  cy.session(
    name,
    () => {
      cy.request({
        method: 'POST',
        url: '/login',
        body: { name, password: 's3cr3t' },
      }).then(({ body }) => {
        window.localStorage.setItem('authToken', body.token)
      })
    },
    {
      validate() {
        cy.visit('/user_profile')
        cy.contains(`Hello ${name}`)
      },
      cacheAcrossSpecs: true,
    }
  )
}

// profile.cy.js
it('can view profile', () => {
  login()
})

// add_blog.cy.js
it('can create a blog post', () => {
  login()
})
```

:::caution

When a session is cached across specs, every spec that uses it must call
`cy.session()` with the **same** `id`, `setup`, `validate`, and
`cacheAcrossSpecs` value. Cypress compares `setup` and `validate` by their source
code. If any of these differ between specs, Cypress throws an error rather than
reusing the session. For this reason, define the session once in a shared custom
command or helper function and call that everywhere, rather than copying the
`cy.session()` call into each spec.

:::

The cross-spec cache lives in memory for a single `cypress run` on a single
machine. It is not written to disk and is not shared between machines, so:

- A new `cypress run` starts with an empty cache and runs `setup` again.
- When specs are split across machines in parallel CI, `setup` runs at least
  once per machine.

### Cache a cross-origin login with `cy.session()`

`cy.session()` caches cookies, `localStorage`, and `sessionStorage` for every
domain the browser visited during `setup`, not only the domain the test ends
on, and restores all of them. A login that passes through an identity provider
on another origin is cached in full. Inside `setup`, use
[`cy.origin()`](/api/commands/origin) to run commands on the other origin.

```javascript
const login = (name) => {
  cy.session(
    name,
    () => {
      cy.visit('/login')
      cy.get('[data-test=sso-login]').click()
      cy.origin('https://auth.example.com', { args: { name } }, ({ name }) => {
        cy.get('[data-test=name]').type(name)
        cy.get('[data-test=password]').type('s3cr3t')
        cy.get('form').contains('Log In').click()
      })
      cy.url().should('contain', '/home')
    },
    {
      validate() {
        cy.request('/whoami').its('status').should('eq', 200)
      },
    }
  )
}

it('views the dashboard', () => {
  login('bob')
  cy.visit('/home')
  // assertions
})
```

## Notes

### When `cy.session()` clears the page and session data

#### Session clearing with test isolation enabled

When test isolation is enabled with `testIsolation: true`, `cy.session()`
clears the page and the cookies, local storage, and session storage (session
data) in all domains. Behavior stays consistent whether a session is being
created or restored, and you can switch sessions without logging out first.

| When cleared?                    |            Page cleared (test)             |            Session data cleared            |
| -------------------------------- | :----------------------------------------: | :----------------------------------------: |
| Before `setup`                   | <Icon name="check-circle" color="green" /> | <Icon name="check-circle" color="green" /> |
| Before restoring a saved session | <Icon name="check-circle" color="green" /> | <Icon name="check-circle" color="green" /> |
| Before `cy.session()` ends       | <Icon name="check-circle" color="green" /> |                                            |

Because the page is blank when `cy.session()` ends, call
[`cy.visit()`](/api/commands/visit) afterwards to load the page you want to
test. To avoid visiting twice, see
[Where to call cy.visit() after cy.session()](/app/guides/authentication-testing/caching-login-sessions#Where-to-call-cyvisit-after-cysession).

#### Session clearing with test isolation disabled

When test isolation is disabled with `testIsolation: false`, `cy.session()`
doesn't clear the page, but it still clears the session data.

| When cleared?                    | Page cleared (test) |            Session data cleared            |
| -------------------------------- | :-----------------: | :----------------------------------------: |
| Before `setup`                   |                     | <Icon name="check-circle" color="green" /> |
| Before restoring a saved session |                     | <Icon name="check-circle" color="green" /> |
| Before `cy.session()` ends       |                     |                                            |

The page you were on stays loaded after `cy.session()`, so you don't need to
call [`cy.visit()`](/api/commands/visit) afterwards.

Disabling test isolation can make end-to-end tests faster, but a previous test
can change the browser state the next test starts with, which makes results
inconsistent when you run a single test with `.only()`. Write isolated tests
when test isolation is disabled, and set up your session in a `before` hook or
in the first test so it starts from a clean state.

### How long `cy.session()` keeps a session cached

Once created, a session for a given `id` is cached for the duration of the spec
file. You can't modify a stored session after it has been cached, but you can
always create a new session with a different `id`.

To reduce development time, when running Cypress in "open" mode, sessions stay
cached _for spec file reruns_.

To persist a session across multiple specs, set the `cacheAcrossSpecs: true`
option.

### Clear saved `cy.session()` sessions while debugging

When running Cypress in "open" mode, you can explicitly clear all spec and
global sessions and re-run the spec file by clicking the **Clear All Sessions**
button in the [Instrument Panel](#The-Instrument-Panel).

For debugging purposes, all spec and global sessions can be cleared with the
[`Cypress.session.clearAllSavedSessions()`](/api/cypress-api/session) method.

### Choose a unique id for each `cy.session()` session

For sessions to be cached uniquely, the [`id` argument](#Arguments) must be
unique for each new session created. Build it from every value that changes the
resulting session, such as the user and their role. The `id` you pass to
`cy.session()` displays in the Command Log, so leave out sensitive data like
passwords and tokens. For examples, including how a too-narrow `id` restores
the wrong session, see
[Choose a unique id for each cached session](/app/guides/authentication-testing/caching-login-sessions#Choose-a-unique-id-for-each-cached-session).

### Common questions about `cy.session()`

#### Why are all my Cypress commands failing after calling `cy.session()`?

When
[`testIsolation`](/app/core-concepts/writing-and-organizing-tests#Test-Isolation)
is enabled, call [`cy.visit()`](/api/commands/visit) after `cy.session()`.
Otherwise your tests run on a blank page.

#### Why am I seeing `401` errors after calling `cy.session()`?

It's possible that your session is not valid or was not fully established before
the session was saved and the command ended. Be sure to specify a `validate`
function so that `cy.session()` can validate and recreate the session if
necessary.

## Rules

<HeaderRequirements />

- `cy.session()` requires being chained off of `cy`.
- `cy.session()` requires an `id` that is a non-empty string or a serializable
  object or array.
- `cy.session()` requires a `setup` function as its second argument.
- `cy.session()` requires `options`, when passed, to be an object that contains
  only `validate` (a function) and `cacheAcrossSpecs` (a boolean).
- `cy.session()` requires an `id` that was already used to be called with the
  same `setup`, `validate`, and `cacheAcrossSpecs` values as before.
- `cy.session()` can't be called inside a [`cy.origin()`](/api/commands/origin)
  callback. Call it outside the callback, and call `cy.origin()` inside `setup`
  instead.
- `cy.session()` requires end-to-end testing. In a component spec, the official
  mount adapters (`cypress/react`, `cypress/vue`, `cypress/angular`, and
  `cypress/svelte`) make it throw `cy.session from a component spec is not
allowed`.
