# session

Cache and restore [cookies](/api/cypress-api/cookies),
[`localStorage`](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage),
and
[`sessionStorage`](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage)
(together, session data) to recreate a consistent browser context between
tests. Your tests sign in once, and every later call to `cy.session()` with the
same `id` restores that sign-in instead of repeating it.

`cy.session()` follows the
[`testIsolation`](/app/core-concepts/test-isolation) setting to decide whether
it clears the page when it creates or restores a session.

## Syntax

```javascript
cy.session(id, setup)
cy.session(id, setup, options)
```

### Usage

<Icon name="check-circle" color="green" /> **Correct Usage**

```javascript
// Caching session when logging in via page visit
cy.session(name, () => {
  cy.visit('/login')
  cy.get('[data-test=name]').type(name)
  cy.get('[data-test=password]').type('s3cr3t')
  cy.get('form').contains('Log In').click()
  cy.url().should('contain', '/login-successful')
})

// Caching session when logging in via API
cy.session(username, () => {
  cy.request({
    method: 'POST',
    url: '/login',
    body: { username, password },
  }).then(({ body }) => {
    window.localStorage.setItem('authToken', body.token)
  })
})
```

<Icon name="exclamation-triangle" color="red" /> **Incorrect Usage**

```javascript
// visiting before calling cy.session() is redundant, it needs to
// be done inside the setup function
cy.visit('/login')
cy.session(name, () => {
  // need to call cy.visit() here because the page is blank when
  // the setup function runs
  cy.get('[data-test=name]').type(name)
  cy.get('[data-test=password]').type('s3cr3t')
  cy.get('form').contains('Log In').click()
  // should assert that login was successful here to guarantee the
  // login process completes before it is cached
})
// should have asserted this inside the cy.session() setup
// function because the page is blank here
cy.url().should('contain', '/login-successful')
```

### Arguments

<Icon name="angle-right" /> **id _(String, Array, Object)_**

A unique identifier that Cypress uses to cache and restore a given session. A
`String` is enough in most cases. When you pass an `Array` or `Object`, Cypress
generates the id by stringifying the value deterministically. For example,
`['Jane', '123', 'admin']` becomes the id `["Jane","123","admin"]`. See
[Choosing the correct id to cache a session](#Choosing-the-correct-id-to-cache-a-session)
for examples.

:::caution

Large data structures are slow to serialize into an identifier, and cyclical
ones can fail to serialize at all. Pass only the values that identify the
session.

:::

<Icon name="angle-right" /> **setup _(Function)_**

Cypress calls this function whenever a session for the given `id` isn't cached
yet, or when the cached session is no longer valid (see the `validate` option).
After `setup` and `validate` run for the first time, Cypress saves all cookies,
`localStorage`, and `sessionStorage`. Later calls to `cy.session()` with the
same `id` skip `setup` and only restore and validate the cached session data.

`setup` starts with cookies, `localStorage`, and `sessionStorage` cleared in all
domains, and with a blank page when test isolation is enabled, so visit the page
it needs inside `setup`. See
[When the page and session data are cleared](#When-the-page-and-session-data-are-cleared).

<Icon name="angle-right" /> **options _(Object)_**

| Option             | Default     | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------ | ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cacheAcrossSpecs` | `false`     | When enabled, Cypress treats the newly created session as global, and any spec in the same Cypress run on the same machine can restore it. Use this option for a session that many specs share.                                                                                                                                                                                                                                                                         |
| `validate`         | `undefined` | Validates the newly created or restored session. Cypress runs it immediately after `setup` creates the session, or after it clears the page and restores a saved session. See [Validating a restored session with `validate`](#Validating-a-restored-session-with-validate) for what makes a session invalid.<br/><br/>- If validation fails immediately after `setup`, the test fails.<br/>- If validation fails after Cypress restores a session, `setup` runs again. |

<HeaderYields />

- `cy.session()` yields the session's status as a string:
  - `'created'` when `setup` ran for a new session.
  - `'restored'` when a saved session was restored.
  - `'recreated'` when a restored session failed validation and `setup` ran
    again.

## Examples

### Caching a session in a login custom command

Wrap the body of your login
[custom command](/api/cypress-api/custom-commands) in `cy.session()`. The first
call signs in and caches the session. Later calls with the same username restore
it and check it with `validate`.

<Tabs groupId="cypress-lang">
<TabItem value="js" label="JavaScript">

```js title="cypress/support/commands.js"
Cypress.Commands.add('login', (username, password) => {
  cy.session(
    username,
    () => {
      cy.visit('/login')
      cy.get('[data-test=name]').type(username)
      cy.get('[data-test=password]').type(password)
      cy.get('form').contains('Log In').click()
      cy.url().should('contain', '/login-successful')
    },
    {
      validate() {
        cy.request('/whoami').its('status').should('eq', 200)
      },
    }
  )
})
```

</TabItem>
<TabItem value="ts" label="TypeScript">

```ts title="cypress/support/commands.ts"
declare global {
  namespace Cypress {
    interface Chainable {
      login(username: string, password: string): Chainable<void>
    }
  }
}

Cypress.Commands.add('login', (username, password) => {
  cy.session(
    username,
    () => {
      cy.visit('/login')
      cy.get('[data-test=name]').type(username)
      cy.get('[data-test=password]').type(password)
      cy.get('form').contains('Log In').click()
      cy.url().should('contain', '/login-successful')
    },
    {
      validate() {
        cy.request('/whoami').its('status').should('eq', 200)
      },
    }
  )
})
```

</TabItem>
</Tabs>

The `id` is the username alone. Cypress shows the `id` in the Command Log, so
keep passwords out of it.

### Caching a session in a login helper function

The same pattern works in a login helper function:

```javascript
const login = (name, password) => {
  cy.session(
    name,
    () => {
      cy.visit('/login')
      cy.get('[data-test=name]').type(name)
      cy.get('[data-test=password]').type(password)
      cy.get('#submit').click()
      cy.url().should('contain', '/home')
    },
    {
      validate() {
        // A protected page returns a 4xx status code when the user isn't
        // signed in, which makes cy.visit() fail by default
        cy.visit('/account-details')
      },
    }
  )
}
```

### Asserting on the sign-in response inside `setup`

`cy.session()` yields the session's status, not the value your login code
returns, so a test can't assert on the sign-in response after `cy.session()`.
Assert on it inside `setup` instead:

<Tabs groupId="cypress-lang">
<TabItem value="js" label="JavaScript">

```js title="cypress/support/commands.js"
Cypress.Commands.add('loginByApi', (username, password) => {
  cy.session(username, () => {
    cy.request('POST', `/api/login`, {
      username,
      password,
    }).then((response) => {
      expect(response.status).to.eq(200)
    })
  })
})
```

</TabItem>
<TabItem value="ts" label="TypeScript">

```ts title="cypress/support/commands.ts"
declare global {
  namespace Cypress {
    interface Chainable {
      loginByApi(username: string, password: string): Chainable<void>
    }
  }
}

Cypress.Commands.add('loginByApi', (username, password) => {
  cy.session(username, () => {
    cy.request('POST', `/api/login`, {
      username,
      password,
    }).then((response) => {
      expect(response.status).to.eq(200)
    })
  })
})
```

</TabItem>
</Tabs>

The assertion runs every time `setup` signs in, so a failed sign-in still fails
the test. On a restore, `setup` doesn't run, and `cy.session()` checks the
session with `validate` instead, if you pass one.

### Modifying session data before caching

To change which session data Cypress caches, modify cookies, `localStorage`, or
`sessionStorage` in `setup`.

```javascript
cy.session('user', () => {
  cy.visit('/login')
  cy.get('[data-test=name]').type('user')
  cy.get('[data-test=password]').type('p4ssw0rd123')
  cy.get('#submit').click()
  cy.url().should('contain', '/home')
  // Remove session data you don't want to cache
  cy.clearCookie('authId')
  cy.window().then((win) => {
    win.localStorage.removeItem('authToken')
  })
  // Add session data you want to cache
  cy.setCookie('session_id', '189jd09sufh33aaiidhf99d09')
})
```

### Using the session status `cy.session()` yields

`cy.session()` yields `'created'`, `'restored'`, or `'recreated'`.
Use it to run work that belongs with `setup`, such as seeding data for a new
user, only when `setup` actually ran.

```javascript
cy.session('admin', loginAsAdmin).then((status) => {
  if (status !== 'restored') {
    cy.task('db:seed:admin')
  }
})
```

### Validating a restored session with `validate`

The `validate` function checks that the session is established correctly. This
matters most when Cypress restores a cached session: if the session is no longer
valid, `cy.session()` recreates it by running `setup` again.

These scenarios mark the session as invalid:

- the `validate` function throws an exception
- the `validate` function returns a Promise that resolves to `false` or rejects
- the `validate` function contains a failing Cypress command
- the `validate` function returns nothing, or returns a Cypress chain, and its
  last Cypress command yields `false`

Returning `false` directly from `validate`, without a Promise, does not mark the
session as invalid.

Here are a few `validate` examples:

```javascript
// Attempt to visit a page that only a logged-in user can see
function validateByVisit() {
  cy.visit('/private')
}

// Make an API request that returns a 200 only when logged in
function validateByRequest() {
  cy.request('/api/user').its('status').should('eq', 200)
}

// Run any Cypress command that fails if the user is not logged in
function validateByUrl() {
  cy.visit('/account', { failOnStatusCode: false })
  cy.url().should('match', /\/account$/)
}
```

### Validating a cached session without a network request

A `validate` function that visits a page or makes a request confirms the server
still accepts the session, at the cost of a round trip on every restore. When
your app keeps its session in a cookie or in storage, checking for that data
directly is quicker.

```javascript
const login = (name) => {
  cy.session(
    name,
    () => {
      cy.visit('/login')
      cy.get('[data-test=name]').type(name)
      cy.get('[data-test=password]').type('s3cr3t')
      cy.get('form').contains('Log In').click()
      cy.url().should('contain', '/login-successful')
    },
    {
      validate() {
        cy.getCookie('session_id').should('exist')
      },
    }
  )
}
```

When test isolation is enabled, the application's page is blank while `validate`
runs after a restore, so `cy.window()` can't reach its storage. Read storage with
[`cy.getAllLocalStorage()`](/api/commands/getalllocalstorage), which returns it
for every origin. This `validate` recreates the session once the cached token
expires:

```javascript
function validate() {
  cy.getAllLocalStorage().then((storage) => {
    const { tokenExpiresAt } = storage['https://app.cypress.io'] ?? {}

    expect(Number(tokenExpiresAt)).to.be.greaterThan(Date.now())
  })
}
```

These checks confirm that the session data is present. If your server can end a
session on its own, such as when a user logs out in another test, validate with
a request instead so `cy.session()` catches it.

### Switching between cached sessions in one test

`cy.session()` clears all session data before it creates or restores a session,
so it switches from one user to another without logging the first one out. One
test can then act as two users without a logout step between them.

```javascript
const login = (name) => {
  cy.session(name, () => {
    cy.request({
      method: 'POST',
      url: '/login',
      body: { name, password: 's3cr3t' },
    }).then(({ body }) => {
      window.localStorage.setItem('authToken', body.token)
    })
  })
}

it('should transfer money between users', () => {
  login('user')
  cy.visit('/transfer')
  cy.get('#amount').type('100.00')
  cy.get('#send-money').click()

  login('other-user')
  cy.visit('/account_balance')
  cy.get('#balance').should('have.text', '100.00')
})
```

### Where to call `cy.visit()` after `cy.session()`

Call [`cy.visit()`](/api/commands/visit) after logging in, inside each suite's
[`beforeEach`](/app/core-concepts/writing-and-organizing-tests#Hooks) hook.
[Organize your tests into suites](/app/core-concepts/writing-and-organizing-tests#Test-Structure)
by the page they test, so each test loads only the page it needs.

```javascript
const login = (name) => {
  cy.session(name, () => {
    cy.visit('/login')
    cy.get('[data-test=name]').type(name)
    cy.get('[data-test=password]').type('s3cr3t')
    cy.get('#submit').click()
    cy.url().should('contain', '/home')
  })
}

describe('home page tests', () => {
  beforeEach(() => {
    login('user')
    cy.visit('/home')
  })

  it('should test something on the /home page', () => {
    // assertions
  })

  it('should test something else on the /home page', () => {
    // assertions
  })
})

describe('other page tests', () => {
  beforeEach(() => {
    login('user')
    cy.visit('/other')
  })

  it('should test something on the /other page', () => {
    // assertions
  })
})
```

### Caching a session with test isolation disabled

With [`testIsolation`](/app/core-concepts/test-isolation) disabled, Cypress
keeps the page and its session data between tests. Log in once in a `before`
hook, then visit the page your tests share. The tests that follow pick up where
the previous one left off, so they don't call `cy.visit()` again.

```javascript
describe('dashboard', { testIsolation: false }, () => {
  before(() => {
    login('user')
    cy.visit('/dashboard')
  })

  it('shows the signed-in user', () => {
    cy.contains('h1', 'user')
  })

  it('lists recent orders', () => {
    cy.get('[data-test=orders]').should('be.visible')
  })
})
```

With test isolation disabled, `cy.session()` doesn't clear the page. After it
creates a session, the browser stays on whatever page `setup` ends on. Call
`login()` before `cy.visit()`, not after, so your tests start on the page you
visited.

### Caching a session across specs with `cacheAcrossSpecs`

To reuse a session across specs in the same Cypress run on the same machine, set
`cacheAcrossSpecs: true` in the session options. Define the session once, in a
file every spec imports:

```javascript title="cypress/support/login.js"
export const login = (name = 'user1') => {
  cy.session(
    name,
    () => {
      cy.request({
        method: 'POST',
        url: '/login',
        body: { name, password: 's3cr3t' },
      }).then(({ body }) => {
        window.localStorage.setItem('authToken', body.token)
      })
    },
    {
      validate() {
        cy.visit('/user_profile')
        cy.contains(`Hello ${name}`)
      },
      cacheAcrossSpecs: true,
    }
  )
}
```

```javascript title="cypress/e2e/profile.cy.js"
import { login } from '../support/login'

it('can view profile', () => {
  login()
})
```

```javascript title="cypress/e2e/add_blog.cy.js"
import { login } from '../support/login'

it('can create a blog post', () => {
  login()
})
```

Because every spec imports the same `login()`, each call with the `id` `user1`
passes the same `setup` and `validate`. Reusing an `id` with a different `setup`
function fails the test, as the second call here does:

```javascript
cy.session('user1', () => {
  cy.visit('/login')
})

// The same id with a different setup function
cy.session('user1', () => {
  cy.visit('/sso-login')
})
```

The error names the `id` to change:

<DocsImage
  src="/img/api/session/session-duplicate-id-error.png"
  alt="Command Log showing the second cy.session('user1') call failing with 'This session already exists. You may not create a new session with a previously used identifier.'"
/>

The cross-spec cache lives in memory for a single `cypress run` on a single
machine. Cypress doesn't write it to disk or share it between machines, so:

- A new `cypress run` starts with an empty cache and runs `setup` again.
- When specs are split across machines in parallel CI, `setup` runs at least
  once per machine.

In the [Instrument Panel](#The-Instrument-Panel), a globe icon marks each
session cached across specs.

### Caching sessions from multiple login commands

A more complex app can need several login commands, each with its own
`cy.session()` call. Cypress saves and restores sessions by `id`, so each
session needs an `id` of its own.

In this example, `loginByForm` and `loginByApi` can create different session
data for the same user. If both used `name` as the `id`, `cy.session()` couldn't
tell the session `loginByForm` creates for `'user'` apart from the one
`loginByApi` creates. Adding the login method to the `id` caches each one
separately.

```javascript
const loginByForm = (name, password) => {
  cy.session(['loginByForm', name], () => {
    cy.visit('/login')
    cy.get('[data-test=name]').type(name)
    cy.get('[data-test=password]').type(password)
    cy.get('#submit').click()
    cy.url().should('contain', '/home')
  })
}

const loginByApi = (name, password) => {
  cy.session(['loginByApi', name], () => {
    cy.request({
      method: 'POST',
      url: '/api/login',
      body: { name, password },
    }).then(({ body }) => {
      window.localStorage.setItem('authToken', body.token)
    })
  })
}
```

### Testing logout without ending a cached session

A test that logs out ends the session on the server, but the copy that
`cy.session()` cached still holds the old cookies. The next test that restores
it fails `validate` and runs `setup` again. Give the logout test a session `id`
of its own, so the session your other tests share stays valid.

```javascript
const login = (name, id = name) => {
  cy.session(
    id,
    () => {
      cy.visit('/login')
      cy.get('[data-test=name]').type(name)
      cy.get('[data-test=password]').type('s3cr3t')
      cy.get('form').contains('Log In').click()
      cy.url().should('contain', '/login-successful')
    },
    {
      validate() {
        cy.request('/whoami').its('status').should('eq', 200)
      },
    }
  )
}

it('views the dashboard', () => {
  login('user')
  cy.visit('/dashboard')
  cy.contains('h1', 'Dashboard')
})

it('logs out', () => {
  // a separate session, so logging out doesn't end the shared one
  login('user', 'user-logout')
  cy.visit('/dashboard')
  cy.contains('button', 'Log out').click()
  cy.request({ url: '/whoami', failOnStatusCode: false })
    .its('status')
    .should('eq', 401)
})
```

To test what a signed-out user sees without logging out on the server, clear
the browser's session data instead. This leaves the cached session as it is.

```javascript
it('redirects a signed-out user to the login page', () => {
  login('user')
  cy.then(Cypress.session.clearCurrentSessionData)
  cy.visit('/dashboard')
  cy.url().should('contain', '/login')
})
```

### Restoring a session across domains

`cy.session()` caches cookies, `localStorage`, and `sessionStorage` for every
domain, so your tests can move between domains and still restore the same
session. Visit the login page by its full URL inside `setup`, rather than
visiting the domain before you call `cy.session()`. `cy.session()` clears the
page before `setup` runs, and a relative URL in `cy.visit()` resolves against
your [`baseUrl`](/app/references/configuration#Global), not the page you visited
earlier.

```javascript
const login = (name) => {
  cy.session(
    name,
    () => {
      cy.visit('https://app.cypress.io/login')
      cy.get('[data-test=name]').type(name)
      cy.get('[data-test=password]').type('s3cr3t')
      cy.get('form').contains('Log In').click()
      cy.url().should('contain', '/login-successful')
    },
    {
      validate() {
        cy.request('https://app.cypress.io/whoami')
          .its('status')
          .should('eq', 200)
      },
    }
  )
}

it('signs in on app.cypress.io', () => {
  login('bob')
  cy.visit('https://app.cypress.io/dashboard')
  // do things on app.cypress.io
})

it('visits www.cypress.io without the session', () => {
  cy.visit('https://www.cypress.io')
  // do things on www.cypress.io
})

it('restores the session on app.cypress.io', () => {
  // restores bob's app.cypress.io cookies without logging in again
  login('bob')
  cy.visit('https://app.cypress.io/dashboard')
  // do things on app.cypress.io
})
```

### Logging in through an identity provider with `cy.origin()`

When your app signs users in through an identity provider on another domain,
call [`cy.origin()`](/api/commands/origin) inside `setup`. `cy.session()` caches
the cookies and storage for both domains, so a restored session skips the
identity provider entirely.

```javascript
const login = (name) => {
  cy.session(
    name,
    () => {
      cy.visit('https://app.cypress.io/login')
      cy.contains('button', 'Sign in with SSO').click()

      cy.origin('https://auth.cypress.io', { args: { name } }, ({ name }) => {
        cy.get('[data-test=name]').type(name)
        cy.get('[data-test=password]').type('s3cr3t')
        cy.get('form').contains('Log In').click()
      })

      cy.url().should('eq', 'https://app.cypress.io/dashboard')
    },
    {
      validate() {
        cy.request('https://app.cypress.io/whoami')
          .its('status')
          .should('eq', 200)
      },
    }
  )
}
```

`cy.session()` can't be called inside the `cy.origin()` callback, so keep the
`cy.origin()` call inside `setup`. For provider-specific walkthroughs, see the
guides for [Auth0](/app/guides/authentication-testing/auth0-authentication),
[Okta](/app/guides/authentication-testing/okta-authentication), and
[Azure Active Directory](/app/guides/authentication-testing/azure-active-directory-authentication).

## Notes

### When the page and session data are cleared

Every call to `cy.session()` creates, restores, or recreates the session, and
yields the status that names the path it took:

<DocsImage
  src="/img/api/session/session-lifecycle-diagram.svg"
  alt="Diagram: cy.session() creates a session when none is saved, or restores the saved one and recreates it if validate fails. Each path clears session data first and yields 'created', 'restored', or 'recreated'."
  noBorder
/>

The `testIsolation` setting decides whether Cypress also clears the page:

| What Cypress clears                                                      |           Test isolation enabled           |          Test isolation disabled           |
| ------------------------------------------------------------------------ | :----------------------------------------: | :----------------------------------------: |
| The page, before `setup` or a restore and again when `cy.session()` ends | <Icon name="check-circle" color="green" /> |                                            |
| Session data, before `setup` or a restore                                | <Icon name="check-circle" color="green" /> | <Icon name="check-circle" color="green" /> |

#### Clearing with test isolation enabled in `cy.session()`

Clearing the page as well as the session data makes `cy.session()` behave the
same whether it creates or restores a session, and it switches sessions without
logging out first. Call [`cy.visit()`](/api/commands/visit) after
`cy.session()` to load the page you want to test.

#### Clearing with test isolation disabled in `cy.session()`

Cypress clears the session data but doesn't clear the page. After `cy.session()`,
the browser shows the page `setup` ended on, or, after a restore, the page that
was open before the call. Call `cy.visit()` afterward when a test needs a
specific page. Disabling test isolation can make end-to-end
tests faster, but each test inherits the browser state the previous one left
behind, and a test can behave differently when you run it alone with `.only()`.
Write each test so it doesn't depend on the one before it, and set up your
session in a `before` hook or in the first test.

### How long Cypress keeps a cached session

Cypress keeps a session for a given `id` for the rest of the spec file. You
can't change a session once it's cached, but you can create a new session with a
different `id`.

In `cypress open`, Cypress also keeps sessions when you rerun the spec file, so
you don't wait for `setup` on every rerun.

To keep a session across specs, set `cacheAcrossSpecs` to `true`.

### Where to call `cy.session()`

You can call `cy.session()` directly in a test or `beforeEach`, but we recommend
calling it inside a login [custom command](/api/cypress-api/custom-commands) or
reusable helper function. See the
[Caching a session in a login custom command](#Caching-a-session-in-a-login-custom-command)
and
[Caching a session in a login helper function](#Caching-a-session-in-a-login-helper-function)
examples for more details.

### Choosing the correct id to cache a session

For Cypress to cache sessions separately, each session needs its own
[`id`](#Arguments). Cypress shows the `id` in the Command Log, so we recommend
keeping sensitive data such as passwords and tokens out of it.

```javascript
// If your session setup code uses a string variable, pass in the
// string as the id
const loginByName = (name) => {
  cy.session(name, () => {
    loginWith(name)
  })
}

// If your session setup code uses a single object, pass in the
// object as the id, and Cypress serializes it into an identifier
const loginWithParams = (params = {}) => {
  cy.session(params, () => {
    loginWith(params)
  })
}

// If your session setup code uses multiple variables, pass in an
// array of those variables, and Cypress serializes it into an
// identifier
const loginWithVariables = (name, email, params = {}) => {
  cy.session([name, email, params], () => {
    loginWith(name, email, params)
  })
}

// If your session setup code uses external constants, leave them
// out of the id, since they never change
const API_KEY = 'I_AM_AN_API_KEY'
const loginWithConstants = (name, email) => {
  cy.session([name, email], () => {
    loginWith(name, email, API_KEY)
  })
}
```

<Icon name="exclamation-triangle" color="red" /> **Incorrect Usage**

This `login()` signs in with a name, a role, and a password, but its `id` uses
only the name:

```javascript
const login = (name, role, password) => {
  cy.session(name, () => {
    cy.visit('/login')
    cy.get('[data-test=name]').type(name)
    cy.get('[data-test=role]').select(role)
    cy.get('[data-test=password]').type(password)
    cy.get('#submit').click()
  })
}
```

This call signs `user1` in as an admin and caches the session under the `id`
`"user1"`:

```javascript
login('user1', 'admin', 'p4ssw0rd')
```

A later call for the same user with a different role expects a new session.
Because the `id` is still `"user1"`, `cy.session()` restores the admin session
instead of signing in as a viewer:

```javascript
login('user1', 'viewer', 'p4ssw0rd')
```

Build the `id` from every value in `setup` that can change between sessions, or
different sessions share an `id` and restore each other's data.

<Icon name="check-circle" color="green" /> **Correct Usage**

Setting the `id` to `[name, role]` caches a separate session for each name and
role, and leaves the password out.

```javascript
const login = (name, role, password) => {
  cy.session([name, role], () => {
    cy.visit('/login')
    cy.get('[data-test=name]').type(name)
    cy.get('[data-test=role]').select(role)
    cy.get('[data-test=password]').type(password)
    cy.get('#submit').click()
  })
}
```

Keep the `id` the same for every call that should get the same session. A value
that changes on every call, such as a random id from a package like `uuid`,
never matches a saved session, so `setup` runs every time.

### Common questions about `cy.session()`

#### Why are all my Cypress commands failing after calling `cy.session()`?

When [`testIsolation`](/app/core-concepts/test-isolation) is enabled, call
[`cy.visit()`](/api/commands/visit) after `cy.session()`. Otherwise your tests
run on a blank page.

#### Why am I seeing `401` errors after calling `cy.session()`?

Your session might not be valid, or it might not have been fully established
before Cypress saved it. Add a `validate` function so `cy.session()` can check
the session and recreate it when needed.

## Rules

<HeaderRequirements />

- `cy.session()` requires being chained off of `cy`.
- `cy.session()` runs only in end-to-end tests. In a component test, the
  Cypress mount adapters make it throw
  `cy.session from a component spec is not allowed`.
- `cy.session()` can't be called inside a [`cy.origin()`](/api/commands/origin)
  callback. Call it outside of the callback instead.

<HeaderTimeouts />

- `cy.session()` has no `timeout` option. It runs for as long as the commands in
  `setup` and `validate` run, and each of those commands uses its own timeout.
- If `setup` or `validate` returns a Promise, `cy.session()` waits up to 20
  seconds for it to settle, then fails the test.

### Session status in the Command Log

The images in this section come from running this `login()` function, with
`baseUrl` set to `https://app.cypress.io`, in three tests. The first test
creates the session and the second restores it. The third logs out, which ends
the session on the server, so the next restore fails `validate` and Cypress
recreates the session. `validate` passes `failOnStatusCode: false` so a failed
check reports the status code, `401`, rather than the full request.

```javascript
const login = (name) => {
  cy.session(
    name,
    () => {
      cy.visit('/login')
      cy.get('[data-test=name]').type(name)
      cy.get('[data-test=password]').type('s3cr3t')
      cy.get('form').contains('Log In').click()
      cy.url().should('contain', '/login-successful')
    },
    {
      validate() {
        cy.request({ url: '/whoami', failOnStatusCode: false })
          .its('status')
          .should('eq', 200)
      },
    }
  )
}

it('creates a session', () => {
  login('user')
})

it('restores the session', () => {
  login('user')
})

it('recreates the session after logging out', () => {
  login('user')
  cy.visit('/dashboard')
  cy.contains('button', 'Log out').click()
  cy.url().should('contain', '/login')
  login('user')
})
```
