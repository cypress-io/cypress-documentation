# origin

`cy.origin()` runs Cypress commands on a page at a different
[origin](https://developer.mozilla.org/en-US/docs/Web/Security/Same-origin_policy#definition_of_an_origin)
than the one your test is running in, such as a sign-in page on another domain
or subdomain. You put the commands in a callback, Cypress runs them against the
page in that origin, and your test carries on in its own origin afterward.

[How cy.origin() runs commands in another origin](#How-cyorigin-runs-commands-in-another-origin)
shows what happens when the callback runs, which explains most of the rules on
this page.

## Syntax

```js
cy.origin(url, callbackFn)
cy.origin(url, options, callbackFn)
```

### Usage

<Icon name="check-circle" color="green" /> **Correct Usage**

```js
const email = 'fake@email.com'

cy.visit('https://app.cypress.io')

// Pass values in with args, and receive them as the callback's argument
cy.origin('https://example.cypress.io', { args: { email } }, ({ email }) => {
  // Relative URLs resolve against the cy.origin() URL
  cy.visit('/commands/actions')
  cy.get('.action-email').type(email)
})
```

<Icon name="exclamation-triangle" color="red" /> **Incorrect Usage**

```js
const email = 'fake@email.com'

cy.visit('https://app.cypress.io')
cy.visit('https://example.cypress.io/commands/actions')

// Fails: this page is at another origin, so the command goes inside cy.origin()
cy.get('.action-email').type(email)
```

```js
const email = 'fake@email.com'

cy.origin('https://example.cypress.io', () => {
  cy.visit('/commands/actions')
  // Fails: the callback can't see email, because it's declared outside it
  cy.get('.action-email').type(email)
})
```

### Arguments

<Icon name="angle-right" /> **url _(String)_**

The URL (`https://example.cypress.io/commands/actions`) or domain name
(`example.cypress.io`) of the secondary origin, where the callback runs. It needs
at least a hostname, and can include a scheme and port. The scheme defaults to
`https`. A path or hash is fine, but query parameters aren't.

The URL must match the secondary origin's scheme, hostname, and port exactly, and
be a different origin than the one the test is running in. See
[What counts as a different origin for cy.origin()](#What-counts-as-a-different-origin-for-cyorigin).

Inside the callback, the URL replaces your configured
[`baseUrl`](/app/references/configuration#Global), so `cy.visit()` and
`cy.request()` resolve relative URLs against it.

<Icon name="angle-right" /> **options _(Object)_**

Pass in an options object to control the behavior of `cy.origin()`.

| option | description                                                                                                                                                                |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `args` | A plain object that Cypress serializes, sends to the secondary origin, and passes to the callback as its only argument. Its values must be [serializable](#Serialization). |

`args` is the only supported option. Passing any other key throws an error.

<Icon name="angle-right" /> **callbackFn _(Function)_**

The function whose commands run in the secondary origin. Cypress sends it there
as text, so it can't use variables declared outside it: pass them in with `args`
instead. When you pass `args`, the callback receives them as its only argument.

Some commands throw an error inside the callback. See
[Commands that can't run inside cy.origin()](#Commands-that-cant-run-inside-cyorigin).

<HeaderYields />

- `cy.origin()` yields the value yielded by the last Cypress command in the
  callback. If the callback also returns a Promise, the command's value takes
  precedence.
- If the callback runs no Cypress commands, `cy.origin()` yields the callback's
  return value, or the value a returned Promise resolves to.
- If the callback runs Cypress commands and also returns a truthy value that
  isn't a Promise, `cy.origin()` fails, because it mixes synchronous and
  asynchronous code.
- The yielded value crosses back to your test serialized. If it can't be
  serialized, such as a DOM element, accessing it throws an error. See
  [Yielding a value from cy.origin() back to your test](#Yielding-a-value-from-cyorigin-back-to-your-test).

## Examples

### Passing data into cy.origin() with the args option

The callback can't see variables from your test, so pass the values it needs
through `args`. Cypress serializes them and hands them to the callback:

```js
const couponCode = 'HALFOFF'

cy.origin(
  'https://example.cypress.io',
  // Send values in through args...
  { args: { couponCode } },
  // ...and receive them as the callback's argument
  ({ couponCode }) => {
    cy.visit('/commands/actions')
    cy.get('#couponCode1').type(couponCode)
    cy.get('.action-form').submit()
    cy.get('.action-form')
      .next()
      .should('contain', 'Your form has been submitted!')
  }
)
```

### Yielding a value from cy.origin() back to your test

Yield a value from the last command in the callback, and pick it up after the
block. The value crosses back serialized, so yield something that serializes,
such as a string, rather than an element:

<Icon name="check-circle" color="green" /> **Correct Usage**

```js
cy.origin('https://example.cypress.io', () => {
  cy.visit('/')
  // Yields a string, which serializes back to your test
  cy.get('h1').invoke('text')
}).should('equal', 'Kitchen Sink')
```

<Icon name="exclamation-triangle" color="red" /> **Incorrect Usage**

```js
cy.origin('https://example.cypress.io', () => {
  cy.visit('/')
  // Yields an element, which can't be serialized
  cy.get('h1')
}).should('contain', 'Kitchen Sink') // Fails
```

To use the value in later commands, pick it up with
[`.then()`](/api/commands/then). Here, a help site lists the latest release, and
the test checks that the app shows the same version:

<Icon name="check-circle" color="green" /> **Correct Usage**

```js
cy.visit('https://app.cypress.io')

cy.origin('https://help.cypress.io', () => {
  cy.visit('/releases')
  // Yields a string, which serializes back to the primary origin
  cy.get('#latest-version').invoke('text')
}).then((version) => {
  cy.visit('https://app.cypress.io/about')
  cy.get('#app-version').should('have.text', version)
})
```

Reading the value with plain JavaScript and returning it doesn't work. Code in
the callback runs before any of the Cypress commands it queues, so the page
hasn't loaded yet, and returning a value alongside queued commands fails the
test:

<Icon name="exclamation-triangle" color="red" /> **Incorrect Usage**

```js
cy.visit('https://app.cypress.io')

cy.origin('https://help.cypress.io', () => {
  cy.visit('/releases')
  // Fails: this runs before cy.visit(), and the callback also returns a value
  return { version: document.title }
})
```

### Visiting a secondary origin with cy.visit()

You can visit the secondary origin inside the `cy.origin()` callback, or before
it. Cypress doesn't fail on the navigation itself. It fails when a command
outside the callback interacts with the page at the other origin, as in
[Usage](#Usage).

Visit inside the callback, with a URL relative to the `cy.origin()` URL:

```js
cy.visit('https://app.cypress.io')

cy.origin('https://example.cypress.io', () => {
  // Visits https://example.cypress.io/commands/actions
  cy.visit('/commands/actions')
  cy.get('h1').should('have.text', 'Actions')
})
```

Or visit first, then run the commands for that page inside the callback:

```js
cy.visit('https://app.cypress.io')
cy.visit('https://example.cypress.io/commands/actions')

// Commands on the page at the other origin go inside cy.origin()
cy.origin('https://example.cypress.io', () => {
  cy.get('h1').should('have.text', 'Actions')
})
```

Clicking a link or button that goes to another origin works the same way, as in
[Navigating between subdomains with cy.origin()](#Navigating-between-subdomains-with-cyorigin).

### Navigating between subdomains with cy.origin()

Two subdomains of the same domain, such as `app.cypress.io` and
`auth.cypress.io`, are different origins. Commands that run on a page at the
other subdomain go inside `cy.origin()`, the same as for any other domain:

<Icon name="check-circle" color="green" /> **Correct Usage**

```js
cy.visit('https://app.cypress.io')
// The "Log in" link goes to https://auth.cypress.io/login
cy.contains('a', 'Log in').click()

cy.origin('https://auth.cypress.io', () => {
  cy.get('#username').type('jane')
  cy.contains('button', 'Sign in').click()
})

// The login page redirects back to the app
cy.url().should('eq', 'https://app.cypress.io/dashboard')
```

<Icon name="exclamation-triangle" color="red" /> **Incorrect Usage**

```js
cy.visit('https://app.cypress.io')
cy.contains('a', 'Log in').click()
// Fails: auth.cypress.io is a different origin than app.cypress.io
cy.get('#username').type('jane')
```

The command fails with an error that names both origins: it was expected to run
against `https://app.cypress.io`, but the application is at
`https://auth.cypress.io`.

### Navigating to multiple secondary origins in succession

A callback can't call `cy.origin()` itself, so to work in several origins, call
`cy.origin()` once for each, one after another at the top level of the test:

```js
cy.origin('auth.cypress.io', () => {
  cy.visit('/')
  cy.url().should('contain', 'auth.cypress.io')
})

cy.origin('help.cypress.io', () => {
  cy.visit('/')
  cy.url().should('contain', 'help.cypress.io')
})
```

### Using cy.origin() with a local http server

The scheme defaults to `https` when you leave it out, and local development
servers usually run on `http`. Include the scheme and port so the origin matches
the server exactly:

<Icon name="check-circle" color="green" /> **Correct Usage**

```js
// The app runs at http://localhost:3000 and the auth server at http://localhost:3001
cy.visit('http://localhost:3000')
cy.contains('a', 'Log in').click()

cy.origin('http://localhost:3001', () => {
  cy.get('#username').type('jane')
  cy.contains('button', 'Sign in').click()
})

cy.url().should('eq', 'http://localhost:3000/dashboard')
```

<Icon name="exclamation-triangle" color="red" /> **Incorrect Usage**

```js
cy.visit('http://localhost:3000')
cy.contains('a', 'Log in').click()

// Fails: without a scheme, this becomes https://localhost:3001
cy.origin('localhost:3001', () => {
  cy.get('#username').type('jane')
})
```

The first command in the callback fails because it was expected to run against
`https://localhost:3001`, but the application is at `http://localhost:3001`.

### Handling uncaught exceptions in a secondary origin

Third-party pages, such as an identity provider's login page, sometimes throw
errors you can't fix. Cypress fails the test on an uncaught exception from the
secondary origin, the same as from your own app. To ignore an error you expect,
register an [`uncaught:exception`](/api/cypress-api/catalog-of-events#Uncaught-Exceptions)
handler inside the `cy.origin()` callback, before the page loads:

```js
cy.visit('https://app.cypress.io')

cy.origin('https://auth.cypress.io', () => {
  cy.on('uncaught:exception', (err) => {
    // Ignore only the error you expect, so anything else still fails the test
    if (err.message.includes('Third-party widget failed to load')) {
      return false
    }
  })

  cy.visit('/legacy-login')
  cy.get('h1').should('have.text', 'Sign in')
})
```

If you navigate to the page outside the callback, register the handler in a
`cy.origin()` block that runs before the navigation:

```js
cy.visit('https://app.cypress.io')

// Register the handler in the secondary origin before its page loads
cy.origin('https://auth.cypress.io', () => {
  cy.on('uncaught:exception', (err) => {
    if (err.message.includes('Third-party widget failed to load')) {
      return false
    }
  })
})

cy.visit('https://auth.cypress.io/legacy-login')

cy.origin('https://auth.cypress.io', () => {
  cy.get('h1').should('have.text', 'Sign in')
})
```

### Stubbing secondary origin requests with cy.intercept()

[`cy.intercept()`](/api/commands/intercept) throws an error inside the
`cy.origin()` callback, but you don't need it there. Register it before the
`cy.origin()` block, and it matches requests the secondary origin's page makes.
Wait on its alias after the block:

```js
cy.visit('https://app.cypress.io')

cy.intercept('GET', 'https://auth.cypress.io/api/config', {
  body: { mfaRequired: false },
}).as('authConfig')

cy.origin('https://auth.cypress.io', () => {
  cy.visit('/login')
  cy.get('#mfa').should('have.text', 'MFA off')
})

cy.wait('@authConfig')
```

### Building an SSO login custom command with cy.origin()

When signing in isn't what a test is about, wrap the sign-in flow in a `login`
[custom command](/api/cypress-api/custom-commands), so each test signs in with
one line. This command signs in on a separate auth origin. It reads the password
with [`cy.env()`](/api/commands/env) inside the callback, so the secret never
passes through `args`:

```typescript copyTsToJs title="cypress/support/commands.ts"
declare global {
  namespace Cypress {
    interface Chainable {
      login(username: string): Chainable<void>
    }
  }
}

Cypress.Commands.add('login', (username: string) => {
  cy.visit('https://app.cypress.io')
  cy.contains('a', 'Log in').click()

  cy.origin(
    'https://auth.cypress.io',
    { args: { username } },
    ({ username }) => {
      cy.get('#username').type(username)
      // Read the secret inside the callback instead of passing it through args
      cy.env(['ssoPassword']).then(({ ssoPassword }) => {
        cy.get('#password').type(ssoPassword, { log: false })
      })
      cy.contains('button', 'Sign in').click()
    }
  )

  // The auth origin redirects back to the app
  cy.location('pathname').should('eq', '/dashboard')
})

export {}
```

Signing in through the UI before every test takes time. With
[test isolation](/app/core-concepts/writing-and-organizing-tests#Test-Isolation)
on, the default, Cypress clears cookies and storage between tests, so the next
test can't reuse the session. Wrap the sign-in in
[`cy.session()`](/api/commands/session), which caches the session after the
first sign-in and restores it in later tests:

```typescript copyTsToJs title="cypress/support/commands.ts"
declare global {
  namespace Cypress {
    interface Chainable {
      login(username: string): Chainable<void>
    }
  }
}

Cypress.Commands.add('login', (username: string) => {
  cy.session(
    // The username is the cache key, so each user gets their own session
    username,
    () => {
      cy.visit('https://app.cypress.io')
      cy.contains('a', 'Log in').click()

      cy.origin(
        'https://auth.cypress.io',
        { args: { username } },
        ({ username }) => {
          cy.get('#username').type(username)
          cy.env(['ssoPassword']).then(({ ssoPassword }) => {
            cy.get('#password').type(ssoPassword, { log: false })
          })
          cy.contains('button', 'Sign in').click()
        }
      )

      cy.location('pathname').should('eq', '/dashboard')
    },
    {
      // Checks that a restored session still works
      validate() {
        cy.request('https://app.cypress.io/api/me')
          .its('status')
          .should('eq', 200)
      },
    }
  )
})

export {}
```

## Notes

### How cy.origin() runs commands in another origin

Your test and the page in the secondary origin can't reach each other directly,
so Cypress runs a separate copy of itself inside the secondary origin. When your
test reaches `cy.origin()`, it sends that copy the callback as text and the
`args` option serialized. The copy runs the callback's commands against the
page, then sends the yielded value back, serialized:

<DocsImage
  src="/img/api/origin/how-cy-origin-runs-commands.svg"
  alt="Diagram of cy.origin(). Your test runs in the primary origin, https://app.cypress.io, and sends the callback as text, plus args serialized, to a copy of Cypress in the secondary origin, https://auth.cypress.io. That copy runs the callback's commands against the page under test at https://auth.cypress.io/login and sends the yielded value back to your test, serialized. Variables declared outside the callback, cy.intercept(), and cy.session() stay in your test. The copy of Cypress in the secondary origin stays loaded until the spec file ends."
  noBorder
/>

This explains the rules on the rest of this page:

- The callback runs from its text, so it can't see variables declared outside it.
  Pass them in with `args` ([Serialization](#Serialization)).
- Everything that crosses between origins is serialized, so `args` and yielded
  values must survive the structured clone algorithm ([Yields](#Yields)).
- `cy.intercept()` and `cy.session()` stay in your test
  ([Commands that can't run inside cy.origin()](#Commands-that-cant-run-inside-cyorigin)).
- The copy of Cypress stays loaded until the spec file ends, so code loaded in
  one callback is still there in later ones for the same origin
  ([Shared execution context across cy.origin() calls](#Shared-execution-context-across-cyorigin-calls)).

### What counts as a different origin for cy.origin()

An origin is a URL's scheme, hostname, and port. Two URLs that differ in any of
the three are different origins, and commands that run on a page at the other
one go inside `cy.origin()`. The path doesn't count.

For a test that starts on `https://app.cypress.io`:

| URL                               | Needs `cy.origin()`? | Why                               |
| --------------------------------- | -------------------- | --------------------------------- |
| `https://app.cypress.io/settings` | No                   | Only the path differs             |
| `https://app.cypress.io:443`      | No                   | `443` is the default `https` port |
| `https://app.cypress.io:8443`     | Yes                  | The port differs                  |
| `https://auth.cypress.io`         | Yes                  | The subdomain differs             |
| `http://app.cypress.io`           | Can't be reached     | The scheme differs                |

An `https` page can't reach an `http` origin at all, because the browser blocks
an `http` page inside an `https` one, so keep both origins on the same scheme.

When you pass a URL that is the same origin as the test, `cy.origin()` fails
with an error, since the commands don't need it.

Before Cypress 14.0.0, Cypress injected `document.domain` by default, so
subdomains of the same domain didn't need `cy.origin()`. To keep that behavior
while you migrate, set
[`injectDocumentDomain`](/app/references/configuration#injectDocumentDomain) to
`true`, and Cypress compares superdomains instead of origins. The option is
deprecated and will be removed in a future version of Cypress.

### Serialization

Cypress transfers `args` to the secondary origin, and the yielded value back,
with
[the structured clone algorithm](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Structured_clone_algorithm).
It has
[limits on what it can copy](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Structured_clone_algorithm#things_that_dont_work_with_structured_clone),
such as functions and DOM elements.

Variables declared outside the callback aren't available inside it. Using one
throws a `ReferenceError` that tells you to define the variable in the callback
or pass it in with `args`, as in [Usage](#Usage).

### Using dependencies and shared code in cy.origin()

Inside the callback, [`Cypress.require()`](/api/cypress-api/require) includes npm
packages and your own files, the same way
[CommonJS `require()`](https://nodejs.org/api/modules.html#requireid) works in
browser code. CommonJS `require()` and
[ES module `import()`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/import)
don't work in the callback. `Cypress.require()` requires turning on the
[`experimentalOriginDependencies`](/app/references/experiments) option.

```js
cy.origin('https://auth.cypress.io', () => {
  const _ = Cypress.require('lodash')

  cy.visit('/login')
  cy.get('#username').type(_.capitalize('jane'))
})
```

#### Sharing custom commands with cy.origin() callbacks

Load your custom commands into the secondary origin with `Cypress.require()`,
and the same commands work in both origins. Define them in their own file:

```typescript copyTsToJs title="cypress/support/commands.ts"
declare global {
  namespace Cypress {
    interface Chainable {
      clickLink(label: string): Chainable<JQuery<HTMLElement>>
    }
  }
}

Cypress.Commands.add('clickLink', (label: string) => {
  cy.get('a').contains(label).click()
})

export {}
```

Import that file in your support file, so tests get the commands outside
`cy.origin()` callbacks:

```js title="cypress/support/e2e.js"
import './commands'
```

Then load the commands into the secondary origin once, in a `before()` hook:

```js title="cypress/e2e/spec.cy.js"
before(() => {
  // Makes the custom commands available to every later cy.origin() callback
  // for this origin in this spec
  cy.origin('https://auth.cypress.io', () => {
    Cypress.require('../support/commands')
  })
})

it('clicks a link in the secondary origin', () => {
  cy.origin('https://auth.cypress.io', () => {
    cy.visit('/page')
    cy.clickLink('Click Me')
  })
})
```

#### Shared execution context across cy.origin() calls

The secondary origin keeps its JavaScript context until the spec file ends, so
code loaded in one callback is still there in later callbacks for the same
origin, including in later tests. A different origin has its own context, and
each spec file starts fresh. To share code with `cy.origin()` callbacks in every
spec, put the `before()` hook in your support file.

Continuing the spec above:

```js title="cypress/e2e/spec.cy.js"
it('clicks a link in a later test', () => {
  // cy.clickLink() is still loaded from the before() hook
  cy.origin('https://auth.cypress.io', () => {
    cy.visit('/page')
    cy.clickLink('Click Me')
  })

  cy.origin('https://help.cypress.io', () => {
    // cy.clickLink() isn't defined here, because this is a different origin
  })
})
```

#### Using page objects inside cy.origin()

A page object instance can't go into the callback. The callback has no access to
variables from outside it, and a class passed through `args` arrives without its
methods. Instead, import the page object inside the callback with
`Cypress.require()` and create the instance there:

```typescript copyTsToJs title="cypress/support/SignInPage.ts"
export class SignInPage {
  enterUsername(username: string) {
    cy.get('#username').type(username)
  }

  submit() {
    cy.contains('button', 'Sign in').click()
  }
}
```

```typescript copyTsToJs title="cypress/e2e/spec.cy.ts"
it('signs in on a secondary origin', () => {
  const username = 'jane'

  cy.origin(
    'https://auth.cypress.io',
    { args: { username } },
    ({ username }) => {
      const { SignInPage } = Cypress.require('../support/SignInPage')
      const signInPage = new SignInPage()

      cy.visit('/login')
      signInPage.enterUsername(username)
      signInPage.submit()
    }
  )
})
```

Data the methods need, such as the username above, still goes in through
`args`.

To skip the class, pass only the serializable data the page object holds, such
as a map of selectors, through `args`, and call the Cypress commands directly in
the callback:

```json title="cypress/support/selectors.json"
{
  "username": "#username"
}
```

```js title="cypress/e2e/spec.cy.js"
import selectors from '../support/selectors.json'

it('signs in with selectors passed through args', () => {
  cy.origin(
    'https://auth.cypress.io',
    { args: { selectors } },
    ({ selectors }) => {
      cy.visit('/login')
      cy.get(selectors.username).type('jane')
    }
  )
})
```

### Commands that can't run inside cy.origin()

These commands throw an error inside the callback:

- `cy.origin()`: call it again at the top level of the test instead, as in
  [Navigating to multiple secondary origins in succession](#Navigating-to-multiple-secondary-origins-in-succession)
- [`cy.intercept()`](/api/commands/intercept): register it before the block, as
  in [Stubbing secondary origin requests with cy.intercept()](#Stubbing-secondary-origin-requests-with-cyintercept)
- [`cy.session()`](/api/commands/session): wrap the whole flow in it instead, as
  in [Building an SSO login custom command with cy.origin()](#Building-an-SSO-login-custom-command-with-cyorigin)

`Cypress.session.*` methods throw an error inside the callback too, so call them
outside it.

### Framebusting code in third-party origins

Some pages run framebusting code that stops them from loading inside a frame,
where Cypress runs your app. By default, Cypress rewrites code that matches
common framebusting patterns in your own `.html` and `.js` responses. For
third-party pages you test with `cy.origin()`, such as an identity provider's,
set
[`experimentalModifyObstructiveThirdPartyCode`](/app/references/experiments) to
`true` so Cypress rewrites theirs too. See
[Modifying Obstructive Third Party Code](/app/guides/cross-origin-testing#Modifying-Obstructive-Third-Party-Code).

### Where cy.origin() runs commands

`cy.origin()` runs commands against the page your test visits. It doesn't run
them:

- [in a different browser window](/app/references/trade-offs#Multiple-browsers-open-at-the-same-time)
- in a different browser tab
- [inside an `<iframe>` element](/app/faq#How-do-I-test-elements-inside-an-iframe)

`cy.origin()` isn't supported in the experimental WebKit browser.

## Rules

<HeaderRequirements />

- `cy.origin()` requires being chained off of `cy`.
- `cy.origin()` must be invoked from the spec file or support file.
- `cy.origin()` requires the first argument to be a URL or domain name string
  without query parameters.
- `cy.origin()` requires the first argument to be a different origin than the
  one the test is running in. When
  [`injectDocumentDomain`](/app/references/configuration#injectDocumentDomain)
  is `true`, it must be a different superdomain.
- `cy.origin()` requires the `options` argument, when passed, to be a plain
  object whose only key is `args`.
- `cy.origin()` requires the last argument to be a function.
- `cy.origin()` isn't supported in experimental WebKit.

<HeaderTimeouts />

- `cy.origin()` has no timeout of its own. It runs for as long as the commands
  in the callback run, and each of those commands uses its own timeout.
- `cy.origin()` fails if Cypress can't set up communication with the secondary
  origin within the
  [`defaultCommandTimeout`](/app/references/configuration#Timeouts). This can
  happen when an `https` page tries to reach an insecure `http` origin.

## Command Log

This example visits a page in a secondary origin, passing the path in through
`args`, and asserts on the text the callback yields:

```javascript
cy.origin(
  'https://example.cypress.io',
  { args: { path: '/commands/actions' } },
  ({ path }) => {
    cy.visit(path)
    cy.get('h1').invoke('text')
  }
).should('equal', 'Actions')
```

with the commands run in the secondary origin nested inside it:
