# request

Send an HTTP request from your test. `cy.request()` seeds data before a test,
logs in without going through the login page, and tests API endpoints directly.
The Cypress server sends the request from Node.js rather than the browser, so
CORS doesn't apply, and it shares cookies with the browser. See
[How `cy.request()` sends a request](#How-cyrequest-sends-a-request).

## Syntax

```javascript
cy.request(url)
cy.request(url, body)
cy.request(method, url)
cy.request(method, url, body)
cy.request(options)
```

### Usage

<Icon name="check-circle" color="green" /> **Correct Usage**

```javascript
cy.request('http://dev.local/seed')
```

### Arguments

<Icon name="angle-right" /> **url _(String)_**

The URL to make the request to.

If you do not provide a fully qualified domain name (FQDN) URL, Cypress resolves
the host for `cy.request()` in this order:

1. Inside a [`cy.origin()`](/api/commands/origin) callback, Cypress uses the
   origin you passed to `cy.origin()`.
2. If the `baseUrl` property is set in your
   [configuration file](/app/references/configuration), Cypress prefixes the URL
   with it. This applies whether or not you have visited a page, so `baseUrl`
   wins over the origin of a page you visited.

:::cypress-config-example

```ts
{
  e2e: {
    baseUrl: 'http://localhost:1234'
  }
}
```

:::

```javascript
cy.request('seed/admin') // URL is http://localhost:1234/seed/admin
```

3. If no `baseUrl` is set and you have visited a page, Cypress uses the origin of
   the URL used for the `cy.visit()`.

```javascript
cy.visit('http://localhost:8080/app')
cy.request('users/1.json') //  URL is  http://localhost:8080/users/1.json
```

4. If Cypress cannot determine the host, it throws an error.

<Icon name="angle-right" /> **body _(String, Object, FormData, Blob)_**

A request `body` to be sent in the request. When `body` is a JavaScript object
or boolean, Cypress automatically JSON-serializes it and sets the
`Content-Type: application/json` request header, unless you set a `Content-Type`
in `headers`. When `body` is a string, it is sent as-is with no automatic
content-type. When `body` is a `FormData` instance, Cypress sends it as
`multipart/form-data`, which is how you
[upload a file](#Upload-a-file-with-multipartform-data).

<Icon name="angle-right" /> **method _(String)_**

Make a request using a specific method. If no method is defined, Cypress uses
the `GET` method by default.

Cypress accepts the common methods `GET`, `POST`, `PUT`, `PATCH`, `DELETE`,
`HEAD`, and `OPTIONS`, plus `QUERY`, `TRACE`, `CONNECT`, and these extension
methods: `CHECKOUT`, `COPY`, `LOCK`, `M-SEARCH`, `MERGE`, `MKACTIVITY`, `MKCOL`,
`MOVE`, `NOTIFY`, `PROPFIND`, `PROPPATCH`, `PURGE`, `REPORT`, `SEARCH`,
`SUBSCRIBE`, `UNLOCK`, and `UNSUBSCRIBE`.

<Icon name="angle-right" /> **options _(Object)_**

Pass in an options object to change the default behavior of `cy.request()`.

| Option                     | Default                                                     | Description                                                                                                                                                                                                                                                         |
| -------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `log`                      | `true`                                                      | Displays the command in the [Command log](/app/core-concepts/open-mode#Command-Log)                                                                                                                                                                                 |
| `url`                      | `null`                                                      | The URL to make the request to                                                                                                                                                                                                                                      |
| `method`                   | `GET`                                                       | The HTTP method to use in the request                                                                                                                                                                                                                               |
| `auth`                     | `null`                                                      | Adds an `Authorization` header for [HTTP Basic Authentication](#Authenticate-with-HTTP-Basic-or-a-bearer-token), or a bearer token with `bearer`                                                                                                                    |
| `body`                     | `null`                                                      | Body to send along with the request                                                                                                                                                                                                                                 |
| `failOnStatusCode`         | `true`                                                      | Whether to fail on response codes other than `2xx` and `3xx`                                                                                                                                                                                                        |
| `followRedirect`           | `true`                                                      | Whether to automatically follow redirects                                                                                                                                                                                                                           |
| `form`                     | `false`                                                     | Whether to convert the `body` values to URL encoded content and set the `x-www-form-urlencoded` header                                                                                                                                                              |
| `encoding`                 | `utf8`                                                      | The encoding to be used when serializing the response body. The following encodings are supported: `ascii`, `base64`, `binary`, `hex`, `latin1`, `utf8`, `utf-8`, `ucs2`, `ucs-2`, `utf16le`, `utf-16le`                                                            |
| `gzip`                     | `true`                                                      | Whether to accept the `gzip` encoding                                                                                                                                                                                                                               |
| `headers`                  | `null`                                                      | Additional headers to send; accepts an object literal. Cypress also sends them on each redirect it follows, with the exceptions in [How `cy.request()` follows redirects](#How-cyrequest-follows-redirects).                                                        |
| `qs`                       | `null`                                                      | Query parameters to append to the `url` of the request                                                                                                                                                                                                              |
| `retryOnStatusCodeFailure` | `false`                                                     | Whether to [retry a request](#Retry-a-request-that-fails-with-a-server-error) that fails with a status code error. Cypress retries up to 4 times when this is `true`. Requires `failOnStatusCode: true`; setting it with `failOnStatusCode: false` throws an error. |
| `retryOnNetworkFailure`    | `true`                                                      | Whether to retry a request that fails with a transient network error, such as `ECONNREFUSED`, `ECONNRESET`, or `ENOTFOUND`. Cypress retries up to 4 times when this is `true`.                                                                                      |
| `timeout`                  | [`responseTimeout`](/app/references/configuration#Timeouts) | Time to wait for `cy.request()` to resolve before [timing out](#Timeouts). See [Give a slow endpoint more time](#Give-a-slow-endpoint-more-time-with-timeout).                                                                                                      |

You can also set options for `cy.request()`'s `baseUrl` and `responseTimeout`
globally in the [Cypress configuration](/app/references/configuration).

<HeaderYields />

`cy.request()` yields the `response` as an object literal containing these
properties:

- `status`: the response status code
- `body`: the response body, parsed as described in
  [Response body parsing](#Response-body-parsing)
- `headers`: the response headers
- `duration`: how long the request took, in milliseconds
- `redirects`: each redirect Cypress followed, as `status: url` strings (only
  present when a redirect was followed)
- `redirectedToUrl`: the URL the response redirects to (only present with
  `followRedirect: false`)

It also includes `statusText`, `isOkStatusCode`, `requestHeaders`, and
`allRequestResponses`.

## Examples

### URL

#### Make a `GET` request

Call an endpoint before your tests run, such as one that seeds a database.

```javascript
beforeEach(() => {
  cy.request('http://localhost:8080/db/seed')
})
```

#### Check a page's HTML without visiting it

Requesting a page returns its HTML without loading the page and all of its
resources, the way [`cy.visit()`](/api/commands/visit) does. That makes it a
quick way to check what the server renders.

```javascript
cy.request('/admin').its('body').should('include', '<h1>Admin</h1>')
```

### Method and URL

#### Send a `DELETE` request

```javascript
cy.request('DELETE', 'http://localhost:8080/users/827')
```

#### Alias the request using [.as()](/api/commands/as)

```javascript
cy.request('https://jsonplaceholder.cypress.io/comments').as('comments')

cy.get('@comments').should((response) => {
  expect(response.body).to.have.length(500)
  expect(response).to.have.property('headers')
  expect(response).to.have.property('duration')
})
```

### Method, URL, and Body

#### Send a `POST` request with a JSON body

```javascript
cy.request('POST', 'http://localhost:8080/users/admin', { name: 'Jane' }).then(
  (response) => {
    // response.body is automatically parsed from JSON when the server responds
    // with a Content-Type ending in "json" (e.g. application/json)
    expect(response.body).to.have.property('name', 'Jane') // true
  }
)
```

### Authentication

#### Authenticate with HTTP Basic or a bearer token

To send a request to an endpoint protected by
[HTTP Basic Authentication](https://developer.mozilla.org/en-US/docs/Web/HTTP/Authentication),
provide the credentials with the `auth` option. Cypress base64-encodes them and
attaches an `Authorization` header to the request.

Read credentials with [`cy.env()`](/api/commands/env) rather than writing them
into the test, so they stay out of your spec files. The examples on this page
read `username`, `password`, and `apiToken`, which you set as described in
[Environment Variables & Secrets](/app/guides/environment-variables). A request
still shows its headers and body when you click it in the Command Log, so add
`log: false` to a request that carries a secret, as the login examples do.

```javascript
cy.env(['username', 'password']).then(({ username, password }) => {
  cy.request({
    method: 'POST',
    url: '/api/query',
    auth: {
      username,
      password,
    },
    body: {
      cpId: 709916,
    },
  })
})
```

The `auth` option also accepts `user`/`pass` as aliases for
`username`/`password`. To send a bearer token instead, pass it as `bearer`, and
Cypress sends `Authorization: Bearer <token>`.

```javascript
cy.env(['apiToken']).then(({ apiToken }) => {
  cy.request({
    url: '/api/profile',
    auth: {
      bearer: apiToken,
    },
  })
})
```

:::caution

When a request fails on its status code, the error message prints the headers
and body Cypress sent, credentials included, even with `log: false`. To keep a
secret out of a failure, pass `failOnStatusCode: false` and assert on the status
code yourself, as the
[API login example](#Log-in-through-the-API-and-cache-it-with-cysession) does.

:::

Here the bearer token example fails with a `401`. The token came from
`cy.env()`, and the error still prints it under `The request we sent was`:

  alt="The request we sent was section of a cy.request() failure, listing the method, URL, and request headers, including authorization: Bearer expired-token-123"

#### Log in with an HTML form using `form: true`

Once a test covers your login page, other tests don't need to go through it.
Submitting the login form with `cy.request()` skips loading the page and its
resources, and the session cookie your server sets lands in the browser, the
same as a real form submission. For more approaches, see the
[logging in recipes](/app/references/recipes#Logging-In).

```javascript
cy.env(['username', 'password']).then(({ username, password }) => {
  cy.request({
    method: 'POST',
    url: '/login_with_form', // baseUrl is prepended to the URL
    form: true, // sends the body URL-encoded with Content-Type: application/x-www-form-urlencoded
    body: {
      username,
      password,
    },
    log: false, // keeps the credentials out of the Command Log
  })
})

// to prove we have a session
cy.getCookie('cypress-session-cookie').should('exist')
```

#### Log in through the API and cache it with `cy.session()`

Logging in with `cy.request()` skips the login page, and wrapping it in
[`cy.session()`](/api/commands/session) runs the login once and restores the
session cookie in later tests. The `validate` function checks that the cached
session still works before each test reuses it.

`log: false` keeps the password out of the Command Log, and
`failOnStatusCode: false` keeps it out of the error message if the login fails.
The assertion then checks only the status code.

```javascript
beforeEach(() => {
  cy.session(
    'api-login',
    () => {
      cy.env(['username', 'password']).then(({ username, password }) => {
        cy.request({
          method: 'POST',
          url: '/api/login',
          body: { username, password },
          log: false,
          failOnStatusCode: false,
        }).then((response) => {
          expect(response.status, 'login status').to.eq(200)
        })
      })
    },
    {
      validate() {
        cy.request('/api/me').its('status').should('eq', 200)
      },
    }
  )
})

it('shows the dashboard to a logged-in user', () => {
  cy.visit('/dashboard')
  cy.contains('h1', 'Dashboard')
})
```

### Redirects, errors, and retries

#### Request a page without following redirects

To test where a page redirects, such as a dashboard that sends a logged-out
user away, set `followRedirect: false`. The response then has the redirect's
`status`, and `redirectedToUrl` holds the absolute URL the browser would go to
next.

```javascript
cy.request({
  url: '/dashboard',
  followRedirect: false, // turn off following redirects
}).then((response) => {
  // redirect status code is 302
  expect(response.status).to.eq(302)
  expect(response.redirectedToUrl).to.eq('http://localhost:8080/unauthorized')
})
```

#### Check every redirect `cy.request()` followed

When Cypress follows redirects, `response.redirects` lists each hop as the status
code and the absolute URL it redirected to. Use it to confirm that an old route
lands on the right page, and with the right status code.

```javascript
cy.request('/old-dashboard').then((response) => {
  expect(response.redirects).to.deep.eq([
    '301: http://localhost:8080/dashboard',
  ])
  expect(response.status).to.eq(200)
})
```

#### Test an error response with `failOnStatusCode: false`

By default, a status code other than `2xx` or `3xx` fails the test. Set
`failOnStatusCode: false` to get the response back instead, so you can assert on
the status code and the error your API returns.

```javascript
cy.request({
  url: '/api/users/999',
  failOnStatusCode: false,
}).then((response) => {
  expect(response.status).to.eq(404)
  expect(response.body).to.have.property('error', 'User not found')
})
```

The Command Log marks the `404` with a red indicator, and the test still passes
because the assertions match:

<DocsImage
  src="/img/api/request/command-log-request-404-failonstatuscode-false.png"
  alt="Command Log showing a request row reading GET 404 /api/users/999 with a red status indicator, followed by three passing assertions on the 404 status and the error property"
/>

#### Retry a request that fails with a server error

A service that's still starting up can answer with a `503` for a moment. With
`retryOnStatusCodeFailure: true`, Cypress retries a request that comes back with
a status code other than `2xx` or `3xx`, up to 4 times, before it fails the
test.

```javascript
cy.request({
  url: '/api/status',
  retryOnStatusCodeFailure: true,
})
  .its('status')
  .should('eq', 200)
```

#### Give a slow endpoint more time with `timeout`

`timeout` overrides [`responseTimeout`](/app/references/configuration#Timeouts)
for one request, so a slow endpoint doesn't need a longer timeout for every
request in your suite.

```javascript
cy.request({
  url: '/api/reports/monthly',
  timeout: 60000, // wait up to 60 seconds for this request only
})
```

### Files

#### Download a PDF file

With `encoding: 'binary'`, `response.body` holds the file's binary content, which
you can save with [`cy.writeFile()`](/api/commands/writefile). This works for
other file types too, such as `.zip` or `.doc` files.

```javascript
cy.request({
  url: 'http://localhost:8080/some-document.pdf',
  encoding: 'binary',
}).then((response) => {
  cy.writeFile('path/to/save/document.pdf', response.body, 'binary')
})
```

#### Get the data URL of an image

With `encoding: 'base64'`, `response.body` holds the image's base64-encoded
content, which you can use to build a
[Data URI](https://developer.mozilla.org/en-US/docs/Web/HTTP/Basics_of_HTTP/Data_URIs).

```javascript
cy.request({
  url: 'https://docs.cypress.io/img/logo/cypress-logo-circle-dark.png',
  encoding: 'base64',
}).then((response) => {
  const base64Content = response.body
  const mime = response.headers['content-type'] // or 'image/png'
  // see https://developer.mozilla.org/en-US/docs/Web/HTTP/Basics_of_HTTP/Data_URIs
  const imageDataUrl = `data:${mime};base64,${base64Content}`
})
```

#### Upload a file with `multipart/form-data`

To upload a file, build a
[`FormData`](https://developer.mozilla.org/en-US/docs/Web/API/FormData) object
and pass it as the `body`. Cypress encodes each field, sends the file's bytes
unchanged, and sets the `Content-Type: multipart/form-data` header with the
boundary the server needs to parse the parts. Leave `form` unset, since it
applies to URL-encoded forms only.

This is the `cy.request()` equivalent of `curl -F file=@image.png`:

```javascript
cy.env(['apiToken']).then(({ apiToken }) => {
  // image fixtures are read as base64 by default
  cy.fixture('image.png').then((image) => {
    const formData = new FormData()

    formData.append(
      'file',
      Cypress.Blob.base64StringToBlob(image, 'image/png'),
      'image.png'
    )

    cy.request({
      method: 'POST',
      url: '/api/action/upload_file',
      headers: {
        Authorization: `Bearer ${apiToken}`,
      },
      body: formData,
    })
      .its('status')
      .should('eq', 200)
  })
})
```

The third argument to `formData.append()` sets the filename the server
receives. Without it, the part is sent with the filename `blob`. Plain string
fields go in the same object, such as `formData.append('description', 'Avatar')`.

The response to a `FormData` request arrives as raw bytes, even when it is JSON.
See [Response body parsing](#Response-body-parsing) to read it.

### API testing workflows with `cy.request()`

#### Send query parameters with `qs`

The `qs` option builds the query string for you. Cypress merges it with any
query string already in the `url`, rather than replacing it.

```javascript
cy.request({
  url: '/api/users?active=true',
  qs: { page: 2, limit: 10 },
})
// requests /api/users?active=true&page=2&limit=10
```

#### Create a record, then use its ID in later requests

Seed the data a test needs, then use what the API returns. Here the `id` from
the `POST` response drives the `GET` and the `DELETE` that cleans up.

```javascript
cy.request('POST', '/api/users', { name: 'Jane' })
  .its('body.id')
  .then((id) => {
    cy.request(`/api/users/${id}`).its('body.name').should('eq', 'Jane')
    cy.request('DELETE', `/api/users/${id}`).its('status').should('eq', 204)
  })
```

#### Assert on the status, headers, and response time

Every response carries its `status`, its `headers`, and the `duration` of the
request in milliseconds, so one request can check all three.

```javascript
cy.request('/api/users').then((response) => {
  expect(response.status).to.eq(200)
  expect(response.headers['content-type']).to.include('application/json')
  expect(response.duration).to.be.lessThan(500)
})
```

#### Type the response body in TypeScript

`cy.request()` takes a type argument for the response body, so `response.body`
is typed in your editor instead of `any`.

```typescript copyTsToJs
interface User {
  id: number
  name: string
}

cy.request<User>('/api/users/1').then((response) => {
  expect(response.body.name).to.eq('Jane')
})
```

#### Poll an endpoint until a job finishes

To wait for work the server does in the background, call `cy.request()` from a
function that calls itself until the response shows the job is done. The
`attempts` count stops the loop, so a job that never finishes fails the test
rather than polling forever.

```javascript
function waitForJob(id, attempts = 10) {
  if (attempts === 0) {
    throw new Error(`Job ${id} did not finish`)
  }

  cy.request(`/api/jobs/${id}`).then(({ body }) => {
    if (body.status !== 'done') {
      cy.wait(500)
      waitForJob(id, attempts - 1)
    }
  })
}

cy.request('POST', '/api/jobs', { type: 'export' })
  .its('body.id')
  .then((id) => {
    waitForJob(id)
  })
```

For a version that yields the finished job so you can assert on it, see
[Poll an asynchronous job](/app/guides/api-testing#Poll-an-asynchronous-job).

## Notes

### How `cy.request()` sends a request

`cy.request()` doesn't send the request from the browser. Your test hands it to
the Cypress server, which runs in Node.js and sends it to your server directly.
Along the way, the Cypress server reads the browser's cookies for the URL and
saves any `Set-Cookie` headers it gets back into the browser.

<DocsImage
  src="/img/api/request/request-runs-in-node.svg"
  alt="Diagram: your test in the browser sends cy.request() to the Cypress server in Node.js, which reads cookies from the browser, sends the request to your server, saves Set-Cookie headers back into the browser, and yields the response. The DevTools Network tab, CORS checks, and cy.intercept() routes are not involved."
  noBorder
/>

Because the request doesn't go through the browser:

- It doesn't appear in the browser's DevTools Network tab.
- CORS doesn't apply, so you can request any server, whatever its CORS headers.
- [`cy.intercept()`](/api/commands/intercept) routes don't match it. It always
  reaches your real server, which is what you want when you test an endpoint
  without starting your front end.
- Cypress doesn't verify the server's TLS certificate, so a self-signed or
  expired certificate doesn't fail the request. It also means `cy.request()`
  doesn't catch a certificate problem.
- It sends the browser's `User-Agent` unless you set one in `headers`. To change
  the browser's own user agent, see
  [how to override the browser's default user agent](/app/faq#Can-I-override-or-change-the-default-user-agent-the-browser-uses).

For example, docs.cypress.io sends no CORS headers, and the request still
succeeds:

```javascript
// docs.cypress.io sends no CORS headers, and cy.request() still succeeds
cy.request('https://docs.cypress.io').its('status').should('eq', 200)
```

### How `cy.request()` sends and stores cookies

Before it sends a request, Cypress attaches the cookies the browser would have
sent to that URL. When the response has `Set-Cookie` headers, Cypress sets those
cookies in the browser, so later requests and page visits use them.

Cookies are pulled from the cookie jar by domain match. A cookie set without
`hostOnly: true` is a domain cookie, so it can be attached to a `cy.request()`
aimed at a _different_ host that domain-matches it (for example a sibling
subdomain on the same registrable domain). If a cookie shows up on a request
unexpectedly, see
[Cookie scope (host-only vs. domain cookies)](/api/commands/setcookie#Cookie-scope-host-only-vs-domain-cookies)
for how to scope it to a single exact host with `hostOnly: true`.

### How `cy.request()` follows redirects

With `followRedirect: true`, the default, Cypress follows each redirect and sends
your `headers` again. Keep these behaviors in mind:

- Cookies carry across. Cypress saves any `Set-Cookie` headers into the browser,
  then attaches the cookies that match the next URL.
- `Authorization` is dropped when the redirect changes the hostname.
- A redirected `POST`, `PUT`, or `DELETE` is followed as a `GET`, without its
  body or `Content-Type`. Only a `307` keeps the method and body.

### How `cy.request()` handles request and response bodies

#### Request body serialization

What Cypress sends, and what you get back in `response.body`, depends on the
type of `body`:

| `body`                   | `Content-Type` Cypress sets                                  | `response.body`                                                              |
| ------------------------ | ------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| Object or boolean        | `application/json`, unless you set one                       | Parsed whenever it is valid JSON, whatever the response's `Content-Type`     |
| Object with `form: true` | `application/x-www-form-urlencoded`                          | Parsed when the response's `Content-Type` ends in `json`, otherwise a string |
| String                   | None                                                         | Parsed when the response's `Content-Type` ends in `json`, otherwise a string |
| `FormData`               | `multipart/form-data` with a boundary, replacing one you set | An `ArrayBuffer` of the raw bytes, whatever the response's `Content-Type`    |
| `Blob`                   | None                                                         | An `ArrayBuffer` of the raw bytes, whatever the response's `Content-Type`    |
| None                     | None                                                         | Parsed when the response's `Content-Type` ends in `json`, otherwise a string |

For a string or `Blob` body, set a `Content-Type` in `headers` if your server
expects one.

A `FormData` body needs no `Content-Type` of its own. Cypress encodes each field
as a part of a `multipart/form-data` body, and a `File` or `Blob` field keeps
its filename and type, defaulting to `application/octet-stream` when it has no
type. The boundary that separates the parts goes in the `Content-Type` header
Cypress sets, replacing any you pass in `headers`.

Don't combine a `FormData` body with `form: true` or an
`application/x-www-form-urlencoded` header. Either one sends the body down the
URL-encoded form path, and the request fails with a network-level error.

#### Response body parsing

`response.body` is parsed into an object when either:

- The response's `Content-Type` ends in `json`, such as `application/json`.
- The request `body` is an object or boolean (without `form: true`), and the
  response is valid JSON.

After a `FormData` or `Blob` request, `response.body` is an `ArrayBuffer` of raw
bytes, even for JSON, so decode it before you assert on it. In every other case,
it is a string.

```javascript
const formData = new FormData()
formData.append('name', 'Jane')

cy.request({ method: 'POST', url: '/api/users', body: formData }).then(
  (response) => {
    const user = JSON.parse(new TextDecoder().decode(response.body))
    expect(user).to.have.property('name', 'Jane')
  }
)
```

## Rules

<HeaderRequirements />

- `cy.request()` requires being chained off of `cy`.
- `cy.request()` requires that the server sends a response.
- `cy.request()` requires that the response status code be `2xx` or `3xx` when
  `failOnStatusCode` is `true`.

<HeaderAssertions />

- `cy.request()` will only run assertions you have chained once, and will not
  [retry](/app/core-concepts/retry-ability).

<HeaderTimeouts />

- `cy.request()` can time out waiting for the server to respond.

## Command Log

This example requests the comments endpoint and tests the response:

```javascript
cy.request('https://jsonplaceholder.cypress.io/comments').then((response) => {
  expect(response.status).to.eq(200)
  expect(response.body).to.have.length(500)
  expect(response).to.have.property('headers')
  expect(response).to.have.property('duration')
})
```
