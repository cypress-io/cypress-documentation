# task

Execute code in [Node](https://nodejs.org) via the `task` plugin event.

:::caution

<strong>Anti-Pattern</strong>

We do not recommend starting a web server using `cy.task()`. Read about
[best practices](/app/core-concepts/best-practices#Web-Servers) here.

:::

## Syntax

```javascript
cy.task(event)
cy.task(event, arg)
cy.task(event, arg, options)
```

### Usage

<Icon name="check-circle" color="green" /> **Correct Usage**

```javascript
// in test
cy.task('log', 'This will be output to the terminal')
```

:::cypress-config-plugin-example

```javascript
on('task', {
  log(message) {
    console.log(message)

    return null
  },
})
```

:::

The `task` plugin event handler can return a value or a promise. The command
will fail if `undefined` is returned or if the promise is resolved with
`undefined`. This helps catch typos or cases where the task event is not
handled.

If you do not need to return a value, explicitly return `null` to signal that
the given event has been handled.

### Arguments

<Icon name="angle-right" /> **event _(String)_**

An event name to be handled via the `task` event in the
[setupNodeEvents](/app/plugins/plugins-guide#Using-a-plugin) function.

<Icon name="angle-right" /> **arg _(Object)_**

An argument to send along with the event. This can be any value that can be
serialized by
[JSON.stringify()](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/JSON/stringify),
and the handler receives it the way `JSON.stringify()` would serialize it:

- Functions, symbols, and `undefined` are dropped from object properties and
  become `null` inside arrays.
- Regular expressions, `Map`, and `Set` become empty objects (`{}`).
- `Date` objects become ISO date strings.

When you omit `arg`, the handler receives `undefined`, so a default parameter
value in the handler applies.

If you need to pass multiple arguments, use an object

```javascript
// in test
cy.task('hello', { greeting: 'Hello', name: 'World' })
```

:::cypress-config-plugin-example

```ts
on('task', {
  // deconstruct the individual properties
  hello({ greeting, name }) {
    console.log('%s, %s', greeting, name)

    return null
  },
})
```

:::

<Icon name="angle-right" /> **options _(Object)_**

Pass in an options object to change the default behavior of `cy.task()`.

| Option    | Default                                                 | Description                                                                         |
| --------- | ------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `log`     | `true`                                                  | Displays the command in the [Command log](/app/core-concepts/open-mode#Command-Log) |
| `timeout` | [`taskTimeout`](/app/references/configuration#Timeouts) | Time to wait for `cy.task()` to resolve before [timing out](#Timeouts)              |

<HeaderYields />

`cy.task()` yields the value returned or resolved by the `task` event in
[setupNodeEvents](/app/plugins/plugins-guide#Using-a-plugin).

## Examples

`cy.task()` provides an escape hatch for running arbitrary Node code, so you can
take actions necessary for your tests outside of the scope of Cypress. This is
great for:

- Seeding your test database.
- Storing state in Node that you want persisted between spec files.
- Performing parallel tasks, like making multiple http requests outside of
  Cypress.
- Running an external process.

### Read a file that might not exist

Command [cy.readFile()](/api/commands/readfile) assumes the file exists. If you
need to read a file that might not exist, use `cy.task`.

```javascript
// in test
cy.task('readFileMaybe', 'my-file.txt').then((textOrNull) => { ... })
```

:::cypress-config-plugin-example

```ts
import fs from 'fs'
```

```ts
on('task', {
  readFileMaybe(filename) {
    if (fs.existsSync(filename)) {
      return fs.readFileSync(filename, 'utf8')
    }

    return null
  },
})
```

:::

### Return number of files in the folder

```javascript
// in test
cy.task('countFiles', 'cypress/downloads').then((count) => { ... })
```

:::cypress-config-plugin-example

```ts
import fs from 'fs'
```

```ts
on('task', {
  countFiles(folderName) {
    return new Promise((resolve, reject) => {
      fs.readdir(folderName, (err, files) => {
        if (err) {
          return reject(err)
        }

        resolve(files.length)
      })
    })
  },
})
```

:::

### Seed a database

```js
// in test
describe('e2e', () => {
  beforeEach(() => {
    cy.task('defaults:db')
    cy.visit('/')
  })

  it('displays article values', () => {
    cy.get('.article-list').should('have.length', 10)
  })
})
```

:::cypress-config-plugin-example

```ts
// we require some code in our app that
// is responsible for seeding our database
import db from '../../server/src/db'
```

```ts
on('task', {
  'defaults:db': () => {
    return db.seed('defaults')
  },
})
```

:::

### Clean up and verify downloaded files

Tasks are a good fit for file system work, such as emptying the downloads folder
between tests and then finding the file the test just downloaded.
`config.downloadsFolder` is the resolved absolute path, so the task keeps
working if the project overrides
[`downloadsFolder`](/app/references/configuration#Downloads).

```javascript title='downloads.cy.js'
cy.task('clearDownloads')

cy.task('latestDownload').then((filepath) => {
  expect(filepath).to.be.a('string')
  cy.readFile(filepath)
})
```

:::cypress-config-plugin-example

```ts
import fs from 'fs'
import path from 'path'
```

```ts
const downloads = config.downloadsFolder

on('task', {
  clearDownloads() {
    fs.rmSync(downloads, { recursive: true, force: true })
    fs.mkdirSync(downloads, { recursive: true })

    return null
  },

  latestDownload() {
    const files = fs
      .readdirSync(downloads)
      .map((name) => ({
        name,
        time: fs.statSync(path.join(downloads, name)).mtimeMs,
      }))
      .sort((a, b) => b.time - a.time)

    return files.length ? path.join(downloads, files[0].name) : null
  },
})
```

:::

Cypress already trashes the downloads folder before `cypress run` when
[`trashAssetsBeforeRuns`](/app/references/configuration#trashAssetsBeforeRuns)
is enabled, which it is by default. A `clearDownloads` task is for clearing the
folder between tests within a run.

### Run an external command or CLI

When setup depends on a tool that isn't a Node module, such as a Docker
container, a database CLI, or a cloud provider's command line tool, spawn it
from the task with
[`child_process.execFileSync()`](https://nodejs.org/api/child_process.html#child_processexecfilesynccommand-args-options).
Passing the arguments as an array avoids the shell entirely, so quoting and
`PATH` resolution behave the same way on every platform.

```javascript title='database.cy.js'
cy.task('resetDatabase')
```

:::cypress-config-plugin-example

```ts
import { execFileSync } from 'child_process'
```

```ts
on('task', {
  resetDatabase() {
    execFileSync('docker', ['exec', 'db', 'reset-script'], { stdio: 'pipe' })

    return null
  },
})
```

:::

A task can also return the command's output to the test:

```javascript title='bucket.cy.js'
cy.task('listBucket', 's3://my-test-bucket').should('have.length', 3)
```

:::cypress-config-plugin-example

```ts
import { execFileSync } from 'child_process'
```

```ts
on('task', {
  listBucket(bucket) {
    const output = execFileSync('aws', ['s3', 'ls', bucket], {
      encoding: 'utf8',
    })

    return output.split('\n').filter(Boolean)
  },
})
```

:::

### Run Node code before each test

There is no `setupNodeEvents` event for each test. To run Node code before every
test, call `cy.task()` from a global `beforeEach` in your
[support file](/app/core-concepts/writing-and-organizing-tests#Support-file).

```javascript
// cypress/support/e2e.js
beforeEach(function () {
  cy.task('logTestStart', this.currentTest.fullTitle())
})
```

:::cypress-config-plugin-example

```ts
on('task', {
  logTestStart(title) {
    console.log(`Starting: ${title}`)

    return null
  },
})
```

:::

### Return a Promise from an asynchronous task

```javascript
// in test
cy.task('pause', 1000)
```

:::cypress-config-plugin-example

```ts
on('task', {
  pause(ms) {
    return new Promise((resolve) => {
      // tasks should not resolve with undefined
      setTimeout(() => resolve(null), ms)
    })
  },
})
```

:::

### Type the value a task yields

In TypeScript, `cy.task()` yields `unknown` unless you pass a type parameter
describing what the task returns. Cypress doesn't check the type at runtime, so
keep it in step with the handler.

```ts title="users.cy.ts"
type User = { id: number; name: string }

cy.task<User[]>('getUsers').then((users) => {
  // users is typed as User[]
  expect(users[0].name).to.eq('Ada')
})
```

:::cypress-config-plugin-example

```ts
on('task', {
  getUsers() {
    return [
      { id: 1, name: 'Ada' },
      { id: 2, name: 'Grace' },
    ]
  },
})
```

:::

### Wait for an email or background job

`cy.task()` runs the handler once and doesn't retry it. To wait for something
that happens outside the browser, such as an email arriving or a background job
finishing, poll inside the handler and resolve once the result is ready.

```javascript title='signup.cy.js'
cy.task(
  'waitForEmail',
  { to: 'new-user@example.com', timeout: 30000 },
  { timeout: 40000 }
)
  .its('subject')
  .should('eq', 'Welcome to the app')
```

:::cypress-config-plugin-example

```ts
// findEmail comes from your email testing service's client
import { findEmail } from './mail-client'
```

```ts
on('task', {
  async waitForEmail({ to, timeout }) {
    const deadline = Date.now() + timeout

    while (Date.now() < deadline) {
      const email = await findEmail(to)

      if (email) {
        return email
      }

      await new Promise((resolve) => setTimeout(resolve, 1000))
    }

    throw new Error(`No email to ${to} arrived within ${timeout}ms`)
  },
})
```

:::

Give the `cy.task()` `timeout` option a few seconds more than the handler's own
deadline. The handler then gives up first, and the test fails with its message
instead of a generic timeout.

### Share state between spec files

The config process keeps running for the whole run, so a value stored in a
variable there is still available to later spec files.

```javascript title='create-org.cy.js'
cy.task('setValue', { key: 'orgId', value: 42 })
```

```javascript title='view-org.cy.js'
cy.task('getValue', 'orgId').should('eq', 42)
```

:::cypress-config-plugin-example

```ts
const store: Record<string, unknown> = {}
```

```ts
on('task', {
  setValue({ key, value }) {
    store[key] = value

    return null
  },
  getValue(key) {
    // return null rather than undefined when the key is missing
    return store[key] ?? null
  },
})
```

:::

Keep these behaviors in mind:

- The store starts empty each time the config process starts, such as at the
  beginning of every `cypress run`.
- Machines running specs in parallel each have their own config process, so
  they don't share values.
- A spec that reads a value another spec wrote only passes when the specs run
  in that order. Use a store for values you can recreate when they're missing,
  and [`cy.session()`](/api/commands/session) for caching logins.

### Save a variable across non same-origin URL visits

When visiting non same-origin URL, Cypress will
[change the hosted URL to the new URL](/app/guides/cross-origin-testing), wiping the
state of any local variables. We want to save a variable across visiting non
same-origin URLs.

We can save the variable and retrieve the saved variable outside of the test
using `cy.task()` as shown below.

```javascript
// in test
describe('Href visit', () => {
  it('captures href', () => {
    cy.visit('https://example.cypress.io')
    cy.get('a')
      .invoke('attr', 'href')
      .then((href) => {
        // href is not same-origin as current url
        // like https://www.cypress-dx.com
        cy.task('setHref', href)
      })
  })

  it('visit href', () => {
    cy.task('getHref').then((href) => {
      // visit non same-origin url https://www.cypress-dx.com
      cy.visit(href)
    })
  })
})
```

:::cypress-config-plugin-example

```ts
let href: string
```

```ts
on('task', {
  setHref: (val) => {
    return (href = val)
  },
  getHref: () => {
    return href
  },
})
```

:::

### Command options

#### Change the timeout

You can increase the time allowed to execute the task, although _we do not
recommend executing tasks that take a long time to exit_.

Cypress will _not_ continue running any other commands until `cy.task()` has
finished, so a long-running command will drastically slow down your test runs.

```javascript
// will fail if seeding the database takes longer than 20 seconds to finish
cy.task('seedDatabase', null, { timeout: 20000 })
```

## Notes

### Tasks must end

#### Tasks that do not end are not supported

`cy.task()` does not support tasks that do not end, such as:

- Starting a server.
- A task that watches for file changes.
- Any process that needs to be manually interrupted to stop.

A task must end within the `taskTimeout` or Cypress will fail the current test.

### Errors thrown in a task fail the test

When a handler throws or returns a rejected promise, `cy.task()` fails the test
with the error's message. The stack trace from Node.js appears in the error's
stack under `From Node.js Internals`.

Return `null` when "not found" is an answer the test can act on, and throw when
the test can't continue:

:::cypress-config-plugin-example

```ts
const users = [{ email: 'ada@example.com', name: 'Ada' }]
```

```ts
on('task', {
  // a missing user is an expected answer, so return null
  findUser(email) {
    return users.find((user) => user.email === email) ?? null
  },
  // a test that deletes a missing user has bad setup, so throw
  deleteUser(email) {
    const index = users.findIndex((user) => user.email === email)

    if (index === -1) {
      throw new Error(`No user with email ${email}`)
    }

    users.splice(index, 1)

    return null
  },
})
```

:::

```javascript title='users.cy.js'
cy.task('deleteUser', 'grace@example.com')
```

```text
CypressError: `cy.task('deleteUser')` failed with the following error:

> No user with email grace@example.com

https://on.cypress.io/api/task
```

### Tasks are merged automatically

Sometimes you might be using plugins that export their tasks for registration.
Cypress automatically merges `on('task')` objects for you. For example if you
are using
[cypress-skip-and-only-ui](https://github.com/bahmutov/cypress-skip-and-only-ui)
plugin and want to install your own task to read a file that might not exist:

:::cypress-config-plugin-example

```ts
import skipAndOnlyTask from 'cypress-skip-and-only-ui/task'
import fs from 'fs'
const myTask = {
  readFileMaybe(filename) {
    if (fs.existsSync(filename)) {
      return fs.readFileSync(filename, 'utf8')
    }

    return null
  },
}
```

```ts
// register plugin's task
on('task', skipAndOnlyTask)
// and register my own task
on('task', myTask)
```

:::

See [#2284](https://github.com/cypress-io/cypress/issues/2284) for
implementation.

The same merging lets you split your own tasks into modules by area and
register each one:

```ts copyTsToJs
// cypress/tasks/state.ts
const store: Record<string, unknown> = {}

export const stateTasks = {
  setValue({ key, value }: { key: string; value: unknown }) {
    store[key] = value

    return null
  },
  getValue(key: string) {
    return store[key] ?? null
  },
}
```

:::cypress-config-plugin-example

```ts
import { stateTasks } from './cypress/tasks/state'
import { userTasks } from './cypress/tasks/users'
```

```ts
on('task', stateTasks)
on('task', userTasks)
```

:::

:::caution

<strong>Duplicate task keys</strong>

If multiple task objects use the same key, the later registration overwrites
that particular key, the same way merging multiple objects with duplicate keys
overwrites the first one. Cypress prints a warning in the terminal that names
each duplicated task.

:::

### Reset timeout via `Cypress.config()`

You can change the timeout of `cy.task()` for the remainder of the tests by
setting the new values for `taskTimeout` within
[Cypress.config()](/api/cypress-api/config).

```js
Cypress.config('taskTimeout', 30000)
Cypress.config('taskTimeout') // => 30000
```

### Set timeout in the test configuration

You can configure the `cy.task()` timeout within a suite or test by passing the
new configuration value within the
[test configuration](/app/references/configuration#Test-Configuration).

This will set the timeout throughout the duration of the tests, then return it
to the default `taskTimeout` when complete.

```js
describe('has data available from database', { taskTimeout: 90000 }, () => {
  before(() => {
    cy.task('seedDatabase')
  })

  // tests

  after(() => {
    cy.task('resetDatabase')
  })
})
```

### Allows a single argument only

The syntax `cy.task(name, arg, options)` only has place for a single argument to
be passed from the test code to the plugins code. In the situations where you
would like to pass multiple arguments, place them into an object to be
destructured inside the task code. For example, if you would like to execute a
database query and pass the database profile name you could do:

```javascript
// in test
const dbName = 'stagingA'
const query = 'SELECT * FROM users'

cy.task('queryDatabase', { dbName, query })
```

:::cypress-config-plugin-example

```ts
import mysql from 'mysql'
// the connection strings for different databases could
// come from system environment variables
const connections = {
  stagingA: {
    host: 'staging.my.co',
    user: 'test',
    password: '***',
    database: 'users',
  },
  stagingB: {
    host: 'staging-b.my.co',
    user: 'test',
    password: '***',
    database: 'users',
  },
}

// querying the database from Node
function queryDB(connectionInfo, query) {
  const connection = mysql.createConnection(connectionInfo)

  connection.connect()

  return new Promise((resolve, reject) => {
    connection.query(query, (error, results) => {
      if (error) {
        return reject(error)
      }

      connection.end()

      return resolve(results)
    })
  })
}
```

```ts
on('task', {
  // destructure the argument into the individual fields
  queryDatabase({ dbName, query }) {
    const connectionInfo = connections[dbName]

    if (!connectionInfo) {
      throw new Error(`Do not have DB connection under name ${dbName}`)
    }

    return queryDB(connectionInfo, query)
  },
})
```

:::

### Argument should be serializable

The argument `arg` sent via `cy.task(name, arg)` should be serializable; it
cannot have circular dependencies (issue
[#5539](https://github.com/cypress-io/cypress/issues/5539)). If there are any
special fields like `Date`, you are responsible for their conversion (issue
[#4980](https://github.com/cypress-io/cypress/issues/4980)):

```javascript
// in test
cy.task('date', new Date()).then((s) => {
  // the yielded result is a string
  // we need to convert it to Date object
  const result = new Date(s)
})
```

:::cypress-config-plugin-example

```javascript
on('task', {
  date(s) {
    // s is a string, so convert it to Date
    const d = new Date(s)

    // do something with the date
    // and return it back
    return d
  },
})
```

:::

### Accessing secrets securely

You can use `cy.task()` to securely access secrets at runtime when they aren't available during configuration. Using `cy.task()` may be useful when secrets are retrieved from external secret managers or APIs that aren't available at configuration time.

[cy.env()](/api/commands/env) is the preferred way to access secrets securely and use them in your tests, and is recommended for secrets that are available at configuration time.

```javascript
// in test - executes at runtime
cy.task('getSecret', 'API_KEY', { log: false }).then((apiKey) => {
  cy.request({
    method: 'POST',
    url: 'https://api.example.com/data',
    headers: {
      Authorization: `Bearer ${apiKey}`,
    },
    log: false,
  })
})
```

Pass `{ log: false }` to both commands. Otherwise the Command Log shows the
`cy.task()` call, its console output shows the secret it yields, and the
`cy.request()` console output shows the `Authorization` header. With
`log: false`, neither command appears in the Command Log. When
[Test Replay](/cloud/features/test-replay) is recording, Cypress still records
a hidden entry for each command.

:::cypress-config-plugin-example

```ts
// Task definition - executes when cy.task() is called in tests
on('task', {
  getSecret(secretName: string) {
    // This reads from process.env at runtime, not at configuration time
    // Useful when secrets are fetched dynamically or only needed conditionally
    const secret = process.env[secretName]

    if (!secret) {
      throw new Error(`Secret ${secretName} is not set`)
    }

    return secret
  },
})
```

:::

## Rules

<HeaderRequirements />

- `cy.task()` requires being chained off of `cy`.
- `cy.task()` requires a non-empty string as its first argument.
- `cy.task()` requires the `task` event to be registered in
  [setupNodeEvents](/app/plugins/plugins-guide#Using-a-plugin), with a handler
  for the given event name.
- `cy.task()` requires being invoked from the spec file or support file in
  end-to-end tests.
- `cy.task()` requires the task to eventually end.

<HeaderAssertions />

- `cy.task()` will only run assertions you have chained once, and will not
  [retry](/app/core-concepts/retry-ability).

<HeaderTimeouts />

- `cy.task()` can time out waiting for the task to end.
