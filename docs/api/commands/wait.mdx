# wait

Wait for a number of milliseconds or wait for an aliased resource to resolve
before moving on to the next command.

## Syntax

```javascript
cy.wait(time)
cy.wait(alias)
cy.wait(aliases)
cy.wait(time, options)
cy.wait(alias, options)
cy.wait(aliases, options)
```

```typescript
// Specifying request and response types for aliased intercepts
type UserReq = {}
type UserRes = {}
type ActivityReq = {}
type ActivityRes = {}

cy.intercept('/users/*').as('getUsers')
cy.intercept('/activities/*').as('getActivities')

// As templated types:
cy.wait<UserReq, UserRes>('@getUsers').then(({ request, response }) => {
  request.body // will be of type UserReq
  response.body // will be of type UserRes
})

// As inferred types, with type `Interception` available in `cypress/types/net-stubbing`
cy.wait('@getUsers').then(
  ({ request, response }: Interception<UserReq, UserRes>) => {
    request.body // will be of type UserReq
    response.body // will be of type UserRes
  }
)

// When passing an array of aliases, types must be inferred:
cy.wait(['@getUsers', 'getActivities']).then(
  (
    interceptions: Array<
      Interception<UserReq | ActivityReq, UserRes | ActivityRes>
    >
  ) => {
    interceptions.forEach(({ request, response }) => {
      request.body // will be of type UserReq | ActivityReq
      response.body // will be of type UserRes | ActivityRes
    })
  }
)
```

### Usage

<Icon name="check-circle" color="green" /> **Correct Usage**

```javascript
cy.wait(500)
cy.wait('@getProfile')
```

### Arguments

<Icon name="angle-right" /> **time _(Number)_**

The amount of time to wait in milliseconds.

<Icon name="angle-right" /> **alias _(String)_**

An aliased route as defined using the [`.as()`](/api/commands/as) command and
referenced with the `@` character and the name of the alias.

:::info

<strong>Core Concept</strong>

[You can read more about aliasing routes in our Core Concept Guide](/app/guides/network-requests#Waiting).

:::

<Icon name="angle-right" /> **aliases _(Array)_**

An array of aliased routes as defined using the [`.as()`](/api/commands/as)
command and referenced with the `@` character and the name of the alias.

<Icon name="angle-right" /> **options _(Object)_**

Pass in an options object to change the default behavior of `cy.wait()`.

| Option            | Default                                                                                                                 | Description                                                                         |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `log`             | `true`                                                                                                                  | Displays the command in the [Command log](/app/core-concepts/open-mode#Command-Log) |
| `timeout`         | [`requestTimeout`](/app/references/configuration#Timeouts), [`responseTimeout`](/app/references/configuration#Timeouts) | Time to wait for `cy.wait()` to resolve before [timing out](#Timeouts)              |
| `requestTimeout`  | [`requestTimeout`](/app/references/configuration#Timeouts)                                                              | Overrides the global `requestTimeout` for this request. Defaults to `timeout`.      |
| `responseTimeout` | [`responseTimeout`](/app/references/configuration#Timeouts)                                                             | Overrides the global `responseTimeout` for this request. Defaults to `timeout`.     |

<HeaderYields />

#### When given a `time` argument:

- `cy.wait()` yields the same subject it was given.
- It is [unsafe](/app/core-concepts/retry-ability#Only-queries-are-retried)
  to chain further commands that rely on the subject after `.wait()`.

#### When given an `alias` argument:

- `cy.wait()` 'yields an object containing the HTTP request and response
  properties of the request.

:::info

Cypress parses `response.body` into an `object` only when the response has a JSON
`Content-Type` header, such as `application/json`. JSON sent without one yields
`response.body` as a `string`. A `304 Not Modified` has no body, so on the legacy
network path `response.body` is an empty string, while Chrome, Chromium, and Edge
on the native browser network yield the complete `200` response. See
[the notes about `body` and `304 Not Modified`](/api/commands/intercept#Response-object-properties)
in the `cy.intercept()` documentation for details and examples.

:::

## Examples

### Time

#### Wait for an arbitrary period of milliseconds:

```js
cy.wait(2000) // wait for 2 seconds
```

:::caution

<strong>Anti-Pattern</strong>

You almost **never** need to wait for an arbitrary period of time. There are
always better ways to express this in Cypress.

Read about
[best practices](/app/core-concepts/best-practices#Unnecessary-Waiting) here.

:::

Additionally, it is often much easier to use [`cy.debug()`](/api/commands/debug)
or [`cy.pause()`](/api/commands/pause) when debugging your test code.

### Alias

For a detailed explanation of aliasing, see
[Waiting in the Network Requests guide](/app/guides/network-requests#Waiting).

#### Wait for a specific request to respond

:::visit-mount-example

```js
// Wait for the alias 'getAccount' to respond
// without changing or stubbing its response
cy.intercept('/accounts/*').as('getAccount')
-{cy.visit('/accounts/123')::cy.mount(<Account />)}-
cy.wait('@getAccount').then((interception) => {
  // we can now access the low level interception
  // that contains the request body,
  // response body, status, etc
})
```

:::

#### Wait automatically increments responses

Each time we use `cy.wait()` for an alias, Cypress waits for the next nth
matching request.

```javascript
// stub an empty response to requests for books
cy.intercept('GET', '/books', []).as('getBooks')
cy.get('#search').type('Peter Pan')

// wait for the first response to finish
cy.wait('@getBooks')

// the results should be empty because we
// responded with an empty array first
cy.get('#book-results').should('be.empty')

// now the request (aliased again as `getBooks`) will return one book
cy.intercept('GET', '/books', [{ name: 'Peter Pan' }]).as('getBooks')

cy.get('#search').type('Peter Pan')

// when we wait for 'getBooks' again, Cypress will
// automatically know to wait for the 2nd response
cy.wait('@getBooks')

// we responded with one book the second time
cy.get('#book-results').should('have.length', 1)
```

#### Wait for a request with a specific payload

`cy.wait()` yields the next matching request, whatever its body holds. An
assertion that fails on that request doesn't make `cy.wait()` move on to a
later one, because `cy.wait()` is not a query (see
[Retry-ability](#Retry-ability)). The difference matters when your app sends an
unknown number of similar requests, such as a debounced autosave, and the test
cares about one of them.

To wait for the request that carries a specific value, alias only that request.
Set `req.alias` in a route handler when the body matches, as in
[Aliasing individual requests](/api/commands/intercept#Aliasing-individual-requests),
and wait on that alias:

```js title="cypress/e2e/notes.cy.js"
cy.intercept('POST', '/graphql', (req) => {
  if (req.body.variables?.input?.notes === 'final') {
    req.alias = 'saveFinalNotes'
  }
})

cy.get('[data-cy=notes]').type('final')

// waits for the request whose body has notes: 'final'
cy.wait('@saveFinalNotes').its('response.statusCode').should('eq', 200)
```

The handler adds its alias alongside any alias another route gives the same
request, so a shared intercept that aliases every request by its GraphQL
operation name keeps working. The conditional route has to see the request
before any route that sends a response, so define it after a stubbing route, or
set `middleware: true` when it has to come first, such as in a `beforeEach()`
hook. See
[Add more than one alias to an intercepted request](/api/commands/intercept#Add-more-than-one-alias-to-an-intercepted-request).

To assert on the requests sent so far instead, use
[`cy.get()`](/api/commands/get#Get-all-aliased-intercepts) with the `.all`
suffix. `cy.get()` is a query, so the assertion retries until one of the
interceptions matches:

```js title="cypress/e2e/notes.cy.js"
cy.intercept('POST', '/graphql').as('graphql')

cy.get('[data-cy=notes]').type('final')

cy.get('@graphql.all').should((interceptions) => {
  const notes = interceptions.map(
    (interception) => interception.request.body.variables?.input?.notes
  )

  expect(notes).to.include('final')
})
```

`cy.get('@graphql.all')` includes each interception as soon as its request
goes out, so a matching request's `response` can still be `undefined`. When the
test needs the response, wait on a per-request alias.

### Aliases

#### You can pass an array of aliases that are waited on before resolving.

When passing an array of aliases to `cy.wait()`, Cypress waits for all
requests to complete within the given `requestTimeout` and `responseTimeout`.

:::visit-mount-example

```js
cy.intercept('/users/*').as('getUsers')
cy.intercept('/activities/*').as('getActivities')
cy.intercept('/comments/*').as('getComments')
-{cy.visit('/dashboard')::cy.mount(<Dashboard />)}-

cy.wait(['@getUsers', '@getActivities', '@getComments']).then(
  (interceptions) => {
    // interceptions will now be an array of matching requests
    // interceptions[0] <-- getUsers
    // interceptions[1] <-- getActivities
    // interceptions[2] <-- getComments
  }
)
```

:::

#### Using [`.spread()`](/api/commands/spread) to spread the array into multiple arguments.

```javascript
cy.intercept('/users/*').as('getUsers')
cy.intercept('/activities/*').as('getActivities')
cy.intercept('/comments/*').as('getComments')
cy.wait(['@getUsers', '@getActivities', '@getComments']).spread(
  (getUsers, getActivities, getComments) => {
    // each interception is now an individual argument
  }
)
```

## Notes

### Nesting

Cypress automatically waits for the network call to complete before proceeding
to the next command.

```js
// Anti-pattern: placing Cypress commands inside .then callbacks
cy.wait('@alias')
  .then(() => {
    cy.get(...)
  })

// Recommended practice: write Cypress commands serially
cy.wait('@alias')
cy.get(...)

// Example: assert status from cy.intercept() before proceeding
cy.wait('@alias').its('response.statusCode').should('eq', 200)
cy.get(...)
```

Read
[Guide: Introduction to Cypress](/app/core-concepts/introduction-to-cypress#Commands-Run-Serially)

### Retry-ability

How you write the chain after `cy.wait()` decides whether your assertions
[retry](/app/core-concepts/retry-ability), and how long a failing assertion
takes to fail. Both styles below work, so pick the one that matches what you
want.

Retry-ability belongs to the chain, not to a single command. `cy.wait()` is not
a query, so an assertion chained straight onto it gets a single attempt against
the interception object it yielded:

```js
// one attempt: fails as soon as the status code is wrong
cy.wait('@getAccount').should(
  'have.nested.property',
  'response.statusCode',
  200
)
```

Add a query such as [`.its()`](/api/commands/its) or
[`.invoke()`](/api/commands/invoke) and you start a new retryable chain. The
query re-reads the property, and everything after it retries for up to
[`defaultCommandTimeout`](/app/references/configuration#Timeouts) (`4000` ms by
default):

```js
// retries for up to 4 seconds before passing or failing
cy.wait('@getAccount').its('response.statusCode').should('eq', 200)
```

If you want the retrying version to fail fast instead, set the query's timeout
to `0`:

```js
// checks the value once, at that moment
cy.wait('@getAccount')
  .its('response.statusCode', { timeout: 0 })
  .should('eq', 200)
```

### Timeouts {#Notes-Timeouts}

#### `requestTimeout` and `responseTimeout`

When used with an alias, `cy.wait()` goes through two separate "waiting"
periods.

The first period waits for a matching request to leave the browser. The
[`requestTimeout`](/app/references/configuration#Timeouts) option configures
this duration and has a default of `5000` ms.

This default means that when you begin waiting for an aliased request, Cypress waits
up to 5 seconds for your application to make a matching request. If Cypress finds
no matching request, you get an error message that looks like this:

<DocsImage
  src="/img/api/wait/error-for-no-matching-route-when-waiting-in-test.png"
  alt="Error for no matching request"
/>

Once Cypress detects that a matching request has begun its request, it then
switches over to the 2nd waiting period. The
[`responseTimeout`](/app/references/configuration#Timeouts) option configures
this duration and has a default of `30000` ms.

This default means Cypress now waits up to 30 seconds for the external server to
respond to this request. If Cypress detects no response, you get an error
message that looks like this:

<DocsImage
  src="/img/api/wait/timeout-error-when-waiting-for-route-response.png"
  alt="Timeout error for request wait"
/>

The two timeouts give you the best of both worlds - a fast error feedback loop when
requests never go out and a much longer duration for the actual external
response.

#### Using an Array of Aliases

When passing an array of aliases to `cy.wait()`, Cypress waits for all
requests to complete within the given `requestTimeout` and `responseTimeout`.

## Rules

<HeaderRequirements />

- When passed a `time` argument `cy.wait()` can be chained off of `cy` or off
  another command.
- When passed an `alias` argument `cy.wait()` requires being chained off of
  `cy`.

<HeaderAssertions />

- Assertions chained _directly_ to `cy.wait()` run once and do not
  [retry](/app/core-concepts/retry-ability).
- Assertions chained after a query such as [`.its()`](/api/commands/its) or
  [`.invoke()`](/api/commands/invoke) _do_ retry, because
  [retry-ability follows the chain](#Retry-ability), not the command.

<HeaderTimeouts />

- `cy.wait()` can time out waiting for the request to go out.
- `cy.wait()` can time out waiting for the response to return.
