## Notification preferences {#Notification-preferences}

By default, Cypress Cloud posts a {props.platform} message to each configured
channel only for failing runs. You can select any combination of the following
preferences:

- **Failed runs**: notifies on runs with a _failed_ or _errored_ status.
- **Passed runs**: notifies on runs with a _passed_ status.
- **Canceled runs**: notifies on runs with a _canceled_ status.
- **Timed out runs**: notifies on runs with a _timed out_ status.
- **Flaky tests**: notifies on runs that contain an identified _flaky_ test.

To set notification preferences:

1. Navigate to the **{props.platform}** configuration page.
2. Select the notification preferences for each channel.

### Flaky test alerts {#Flaky-test-alerts}

The **Flaky tests** preference works independently from the run status preferences. Independent preferences mean you can configure a channel to receive notifications _only_ when Cypress Cloud detects flaky tests — even if you don't subscribe to passed or failed runs. See [Example configurations](#Example-configurations) for a concrete setup.

When flaky test alerts are enabled, the {props.platform} message includes flaky test counts in the test results section and lists flaky specs alongside failed specs in the specs for review section.

:::tip

<Icon name="star" /> **Premium Cypress Cloud Feature**

Flaky test detection requires the flaky test management feature to be enabled for your organization. See [Flaky Test Management](/cloud/features/flaky-test-management) for more details.

:::

### Filter notifications by tag, run group, or branch {#Filter-notifications-by-tag-run-group-or-branch}

When configuring at the project-level, you can filter notifications posted to {props.platform} based on a
[tag](/app/references/command-line#cypress-run-tag-lt-tag-gt),
[group](/app/references/command-line#cypress-run-group-lt-name-gt), or branch the run was
recorded with. Filtering by tag, group, or branch is helpful for posting notifications only for certain runs,
like those to a staging or release environment, or only for runs on your main branch.

1. Navigate to the **{props.platform}** configuration page.
2. Under **Tags**, select the **Tag** dropdown for the desired integration and
   select which tag(s) to filter. If you select more than one tag, Cypress Cloud sends the {props.platform} message
   if any of the tags were associated with the run.
3. Under **Run Groups**, select the **Run Group** dropdown for the desired integration and
   select which run group(s) to filter. If you select more than one run group, Cypress Cloud sends the {props.platform} message
   if any of the run groups were associated with the run.
4. Select the **Branch** dropdown for the desired integration and
   select which branch(es) to filter. The dropdown lists branches that runs in this project were
   recorded on. If you select more than one branch, Cypress Cloud sends the {props.platform} message if the run was
   recorded on any of the selected branches. Select **Unknown branch** to include runs recorded
   without branch information.

Branch names must match exactly. If you select no branch, Cypress Cloud sends notifications for runs on every branch.

If you select more than one type of filter, only a run that matches every selected filter
triggers a {props.platform} message. For example, if you select a tag and a branch, the run must
have one of the selected tags and be recorded on one of the selected branches.

## Message content {#Message-content}

Each {props.platform} notification includes run metadata and up to six configurable content sections. You can choose which sections appear in your messages and how they're displayed.

<!-- add image showing a complete run completion message for a failed run, with all content sections visible -->

### What's included in every message {#Whats-included-in-every-message}

Every run completion message includes the following run properties:

- **Run title**: The run number and commit message, linked to the run in Cypress Cloud.
- **Run status**: A color-coded status indicator (passed, failed, errored, timed out, or canceled).
- **Project**: The project name, linked to the project in Cypress Cloud.
- **Branch**: The branch name where the run was recorded.
- **Commit author**: The author of the commit that triggered the run.
- **CI build**: The CI provider and build number, linked to the CI build.

### Configurable content sections {#Configurable-content-sections}

You can enable or disable any of the following content sections for each {props.platform} channel:

- **Test results**: Shows pass, fail, skip, pending, and flaky counts. Each count links directly to the filtered view in Cypress Cloud.
- **UI Coverage results**: Shows the coverage percentage along with counts of tested and untested elements and links. Only appears when [UI Coverage](/ui-coverage/get-started/introduction) data is available.
- **Accessibility results**: Shows the accessibility pass percentage, failed rules broken down by severity (critical, serious, moderate, minor), and failed elements. Only appears when [Cypress Accessibility](/accessibility/get-started/introduction) data is available.
- **Specs for review**: Lists up to 10 failed and flaky spec files with clickable links, the count of failed or flaky tests in each, and the run group name. If there are more than 10, the message includes a link to see all specs.
- **Run tags**: Displays the tags associated with the run.
- **Run groups**: Displays the run groups associated with the run.

To configure message content:

1. Navigate to the **{props.platform}** configuration page.
2. Adjust the content sections for each channel.

<!-- add image showing the message content configuration UI with toggles for each content section -->

### Display modes {#Display-modes}

You can choose between two display modes for your {props.platform} messages:

- **Stacked** (default): Each test result status appears on its own line with an icon and count. Stacked mode is easier to scan when there are many statuses.
- **Compact**: All status counts appear on a single line, saving vertical space in your {props.platform} channel.

The display mode applies to the test results, UI Coverage, and accessibility sections.

### Customize messages further with webhooks {#Customize-messages-further-with-webhooks}

If you need more control over message content than these options provide, use a
[Cypress Cloud webhook](/cloud/integrations/webhooks) to trigger the message
instead. Cypress Cloud sends the run details to an endpoint you choose as a
[JSON payload](/cloud/integrations/webhooks#Payload), and your own system
decides what to post, where, and when.

For example, you could:

- Post failed runs on your main branch to an alerts channel and all other runs
  to a quieter channel, based on the payload's `status` and `commitBranch`.
- Alert only when failures pass a threshold, using `totalFailed` or
  `flakyTestCount`.
- Address the commit author by name with `commitAuthorName`, or link straight
  to the pull request with `ciPullRequestUrl`.
- Use your own wording and layout, including details from other internal systems.

## Example configurations {#Example-configurations}

You can combine the options above — notification preferences, tag and run group filters, content sections, display modes, and org-vs-project scoping — to build notification setups tailored to how your team works. Below are some common configurations.

### Route notifications by environment {#Route-notifications-by-environment}

Create separate project-level channels for each environment and use tag filters to route runs to the right place. For example, a `#staging-tests` channel filtered to the `staging` tag with **Failed runs** and **Passed runs** enabled gives your QA team full visibility into staging health, while a `#prod-alerts` channel filtered to the `production` tag with only **Failed runs** enabled keeps production notifications focused on breakages.

### Dedicated flaky test triage {#Dedicated-flaky-test-triage}

Add a channel like `#flaky-triage` with only the **Flaky tests** preference enabled and no run status preferences selected. This channel only receives a notification when a run contains flaky tests — regardless of whether the run passed or failed — so your team can triage new flake without the noise of every run result.

### Slim CI bridge for high-volume projects {#Slim-CI-bridge-for-high-volume-projects}

For projects with frequent CI runs, set up a channel with only the **Test results** content section enabled in **Compact** display mode. This setup gives your team a single-line pass/fail summary per run with a direct link to the CI build, keeping the channel scannable even at high volume.

### Cross-team visibility with focused project channels {#Cross-team-visibility-with-focused-project-channels}

Configure an organization-level `#cypress-results` channel with **Failed runs** enabled so leadership and stakeholders can monitor test health across all projects. Then add project-level channels like `#team-checkout-tests` with additional content sections (specs for review, run tags) and extra notification preferences (passed runs, flaky tests) so individual teams get the detail they need for the projects they own.

## Managing channels {#Managing-channels}

### Mute a channel {#Mute-a-channel}

If you want Cypress Cloud to temporarily stop posting {props.platform} messages to a
certain channel, you can **Mute** that channel. Muting pauses and resumes
notifications for a specific channel without losing the configuration you've put
in place.

1. Navigate to the **{props.platform}** configuration page.
2. Toggle the **Active** selector for each {props.platform} channel you want muted.

#### Per-project muting for organization channels {#Per-project-muting-for-organization-channels}

If you have an organization-level {props.platform} channel, you can mute it for specific projects without affecting other projects. Per-project muting is useful when you want most projects to post to a shared channel but need to silence notifications for a particular project temporarily.

1. Navigate to the **Project Settings** page for the project you want to mute.
2. Click the **Integrations** tab.
3. Toggle the mute setting for the organization-level {props.platform} channel.

:::caution

Toggling the mute on an organization-level install clears all project-level mute overrides for that channel. If you're using per-project muting, be aware that changing the global mute state resets those overrides.

:::
