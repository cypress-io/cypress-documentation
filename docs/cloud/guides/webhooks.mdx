# Automate on run completion with webhooks

When a Cypress Cloud run finishes, the
[`run.completed` webhook](/cloud/integrations/webhooks) delivers a JSON payload
describing the run. This guide shows how to turn that single event into real
outcomes, such as a message in a channel, a tracking ticket, a deployment, or a
page to an on-call engineers.

The reference documentation covers the full event, payload, headers, security,
and retry behavior. This guide is the use-case companion: worked examples first,
then a complete zero-to-one walkthrough of a **custom Slack message** with
pass and fail formatting.

:::info

**You do not need to run a server.** Every example here points the webhook's
**Payload URL** at a no-code or low-code tool that receives the delivery for you.
For the tradeoffs, including signature verification, see
[Send to a no-code destination](/cloud/integrations/webhooks#Send-to-a-no-code-destination).

:::

## What you can build

One event, `run.completed`, can drive many downstream actions. The pattern is
always the same: point the Payload URL at a tool that catches the webhook, map
the [payload fields](/cloud/integrations/webhooks#Payload) you care
about, and optionally act only on certain runs by filtering on a field such as
`status`.

| Outcome                             | How to build it                                                                                                   | Gate on                       |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| Post to a channel                   | [Zapier](https://zapier.com), [Make](https://www.make.com), or [n8n](https://n8n.io) catches the webhook and sends a Slack, Microsoft Teams, or Discord message. | Any run, or `status = failed` |
| Create a Jira ticket                | [Jira automation](https://support.atlassian.com/cloud-automation/docs/jira-automation-triggers/#Incoming-webhook) receives the delivery on its incoming-webhook trigger and creates an issue. | `status = failed`             |
| Trigger a deploy                    | The webhook calls a CD provider's build hook, or a GitHub [`repository_dispatch`](https://docs.github.com/en/actions/using-workflows/events-that-trigger-workflows#repository_dispatch) event, to start a deployment. | `status = passed`             |
| Page an on-call engineer            | [PagerDuty](https://support.pagerduty.com/main/docs/webhooks) receives the event on an integration URL and opens an incident. | `status = failed`             |
| Feed a dashboard or data warehouse  | A no-code platform maps the fields and appends a row to a sheet, database, or warehouse for reporting.            | Any run                       |

:::note

**Only `run.completed` exists today.** It fires for every terminal run state:
`passed`, `failed`, `errored`, `timedOut`, and `cancelled`. There are no
separate "run failed" or "run passed" events, so you decide what to act on by
reading the `status` field in your tool, as the examples above show. See
[Events](/cloud/integrations/webhooks#Events) for the current list.

:::

### How the examples fit together

Each outcome uses the same three moving parts:

1. **A destination URL.** The tool you are integrating with gives you a webhook
   URL. That URL becomes the **Payload URL** on your Cypress Cloud webhook.
2. **Field mapping.** The [`run.completed` payload](/cloud/integrations/webhooks#Payload)
   is a flat JSON object, so fields such as `status`, `projectName`, `runNumber`,
   `runUrl`, `totalFailed`, and `commitBranch` map directly to variables in your
   tool.
3. **A condition (optional).** Most tools let you continue only when a field
   matches, for example `status` is `failed`, so a ticket or page is created only
   when it should be.

The rest of this guide walks through those three parts in detail for Slack.

## Zero to one: a custom Slack message

Cypress Cloud already has a built-in [Slack integration](/cloud/integrations/slack)
that posts run results. Reach for a webhook when you want a message Cypress Cloud
does not offer out of the box: your own wording, your own fields, a specific
channel, or different formatting for passing and failing runs. This walkthrough
builds one from scratch.

### What you'll build

A message posted to a Slack channel every time a run completes, that:

- Names the project, run number, and branch, and links to the run in Cypress
  Cloud.
- Shows the test totals, including how many failed.
- Formats **passing** runs differently from **failing** ones, so a red build is
  obvious at a glance.

You'll use [Slack Workflow Builder](https://slack.com/help/articles/360053571454),
which can receive a webhook directly and map its JSON into a message, so no
separate automation account is required.

### Prerequisites

- **Permission to manage webhooks** for the Cypress Cloud project. You must be an
  **Owner**, **Admin**, or **Team Admin**. See
  [Getting started](/cloud/integrations/webhooks#Getting-started).
- **A Slack plan that includes Workflow Builder**, and permission to create and
  publish a workflow in your workspace. Conditional (if/else) steps require a
  paid Slack plan; a fallback that works on any plan is described below.
- **The channel** you want the message posted to.

### Step 1: Create a webhook-triggered Slack workflow

1. In Slack, open **Workflow Builder** and create a new workflow.
2. For the way the workflow starts, choose **From a webhook**.
3. Under **Set up variables**, add a key for each payload field you want in the
   message. Slack reads these from the top-level keys of the JSON body. Add, at a
   minimum:

   - `status`
   - `projectName`
   - `runNumber`
   - `runUrl`
   - `commitBranch`
   - `totalTests`
   - `totalFailed`

4. Save the trigger. Slack generates a **webhook URL**. Copy it; it becomes your
   Cypress Cloud **Payload URL** in [Step 4](#Step-4-Point-the-Cypress-Cloud-webhook-at-Slack).

:::note

**Match the field names exactly.** The variable keys must match the payload keys
character for character, including capitalization, for example `runNumber`, not
`runnumber`. Stick to the flat scalar fields for a Slack message. Array fields
such as `tags` and `groups` don't map cleanly to a Workflow Builder variable; if
you need them, transform the payload in a platform like
[Make](https://www.make.com) or [n8n](https://n8n.io) first.

:::

### Step 2: Compose the message

Add a **Send a message to a channel** step, choose your channel, and write the
message, inserting the variables where you want the run's values to appear. For
example:

```text
Cypress run #{runNumber} for {projectName} ({commitBranch}) finished: {status}
{totalFailed} of {totalTests} tests failed.
View the run: {runUrl}
```

When a run completes, Slack replaces each variable with the value from the
payload.

### Step 3: Format passing and failing runs differently

The `status` field tells you how the run ended. Use it to make a failing run
stand out.

- **On a paid Slack plan**, add an **If/else** branch before the message step.
  Set the condition to check whether the `status` variable equals `passed`. In
  the "passing" path, send a success-styled message; in the other path, send a
  failure-styled one, for example leading with a clear label and the failure
  count:

  ```text
  FAILED — Cypress run #{runNumber} for {projectName} on {commitBranch}
  {totalFailed} of {totalTests} tests failed. Investigate: {runUrl}
  ```

- **On any plan**, skip the branch and put the status directly in the text so the
  outcome is always spelled out in words, never by color alone:

  ```text
  [{status}] Cypress run #{runNumber} — {projectName} ({commitBranch})
  {totalFailed}/{totalTests} failed · {runUrl}
  ```

:::tip

Because `status` can be `passed`, `failed`, `errored`, `timedOut`, or
`cancelled`, treat "not passed" as the attention case rather than checking only
for `failed`. That way an `errored` or `timedOut` run still gets your failure
formatting.

:::

Publish the workflow when the message looks right.

### Step 4: Point the Cypress Cloud webhook at Slack

1. In Cypress Cloud, open your project's **Settings**, find the **Webhooks**
   panel, and click **Add webhook**. See
   [Create a webhook](/cloud/integrations/webhooks#Create-a-webhook).
2. Paste the Slack workflow's webhook URL as the **Payload URL**.
3. Leave `run.completed` selected. Save the webhook.

:::caution

**Slack Workflow Builder cannot verify the signature.** It has no place to run
HMAC verification against the raw request body, so you cannot use a
[signing secret](/cloud/integrations/webhooks#Verify-webhook-signatures) to
authenticate the request here. Treat the Slack webhook URL as a secret: don't
share it or commit it, since anyone who has it can post to your channel. For the
full tradeoff, see
[Send to a no-code destination](/cloud/integrations/webhooks#Send-to-a-no-code-destination).

:::

### Step 5: Test the delivery

Use **Send test** on the webhook to confirm Cypress Cloud can reach Slack. See
[Send a test event](/cloud/integrations/webhooks#Send-a-test-event).

:::note

**The test event is a `webhook.ping`, not a `run.completed`.** Its body is
`{ "message": "Webhook ping" }`, so it does **not** contain `status`,
`runNumber`, or the other run fields your message maps. Send test confirms the
connection and that the workflow fires; it will not render your mapped values.

To confirm the field mapping end to end, use a real `run.completed` payload
either way:

- **Redeliver a past run.** In the webhook's **Recent deliveries**, expand a
  previous `run.completed` delivery and choose **Redeliver**. This replays a real
  payload immediately, which is the fastest way to see your message fully
  populated. See [Delivery history and retries](/cloud/integrations/webhooks#Delivery-history-and-retries).
- **Record a run.** Trigger a Cypress run so a fresh `run.completed` fires.

:::

### Step 6: Go live

Once a real delivery renders the message the way you want, you're done. The
workflow runs on every completed run. If you need to change the wording or fields
later, edit the Slack workflow and republish; the Payload URL stays the same, so
the Cypress Cloud webhook needs no change.

## Where to go next

- **Send to Microsoft Teams instead of Slack.** Microsoft Teams offers
  [Workflows](https://support.microsoft.com/office/browse-and-add-workflows-in-microsoft-teams-4998095c-8b72-4b0e-984c-f2ad39e6ba9a)
  with an incoming-webhook trigger that works the same way: create the flow, map
  the payload fields, and use its URL as the Payload URL. Cypress Cloud also has a
  built-in [Microsoft Teams integration](/cloud/integrations/microsoft-teams) for
  standard notifications.
- **Route by branch, tag, or CI provider.** Add a condition on fields such as
  `commitBranch`, `tags`, or `ciProvider` so, for example, only `main` failures
  page on-call while feature branches post to a quieter channel.
- **Filter what you act on.** Since `run.completed` fires for every terminal
  state, use your tool's filter step to continue only when `status` is not
  `passed`, or only when `totalFailed` is greater than zero, to cut noise.
- **Combine outcomes.** A single delivery can fan out: post to a channel, open a
  Jira ticket, and append a row to a reporting sheet from the same webhook, using
  a platform like [Make](https://www.make.com) or [n8n](https://n8n.io).
