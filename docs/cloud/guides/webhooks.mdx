# Build custom integrations with webhooks

When a Cypress Cloud run finishes, the
`run.completed` webhook delivers a JSON payload
describing the run. This guide shows how to use that event to drive a specific process for you or your team, such as a message in a channel, a tracking ticket, a deployment, or a page to an on-call engineers.

The [Cloud Webhook documentation](/cloud/integrations/webhooks) covers the full event, payload, headers, security, and retry behavior. This guide is the use-case companion: worked examples first, then a complete zero-to-one walkthrough of a **custom Slack message** with pass and fail formatting.

:::info

**You do not need to run a server.** Every example here points the webhook's
**Payload URL** at a no-code or low-code tool that receives the delivery for you.
For the tradeoffs, including signature verification, see
[Send to a no-code destination](/cloud/integrations/webhooks#Send-to-a-no-code-destination).

:::

## What you can build

One event, `run.completed`, can drive many downstream actions. Point the
**Payload URL** at a tool that accepts an inbound webhook, map the
[payload fields](/cloud/integrations/webhooks#Payload) you care about, and
filter in the destination if you only want certain runs. Slack Workflow Builder
(the walkthrough on this page) works this way. Some destinations go through a
no-code platform or a short script that receives the Cypress POST and performs
the next action.

### How the examples fit together

Each outcome uses the same three moving parts:

1. **A destination URL.** The tool you are integrating with gives you a webhook
   URL. That URL becomes the **Payload URL** on your Cypress Cloud webhook.
2. **Field mapping.** The [`run.completed` payload](/cloud/integrations/webhooks#Payload)
   is a flat JSON object, so fields such as `status`, `projectName`, `runNumber`,
   `runUrl`, `totalFailed`, and `commitBranch` map directly to variables in your
   tool.
3. **A condition (optional).** Most tools let you continue only when a field
   matches, for example `status` is `failed`, so a ticket or page is created only
   when it should be.

The rest of this guide walks through those three parts in detail for Slack.

## Zero to one: a custom Slack message

Cypress Cloud already has a built-in [Slack integration](/cloud/integrations/slack)
that posts run results. Reach for a webhook when you want a message Cypress Cloud
does not offer out of the box: your own wording, your own fields, a specific
channel, or different formatting for passing and failing runs. This walkthrough
builds one from scratch.

### What you'll build

A Slack message every time a run completes, posted to a channel or sent to a
person, that:

- Names the project and links to the run in Cypress Cloud.
- Shows the test totals, including how many failed.
- Can format **passing** runs differently from **failing** ones, so a failed
  run is obvious at a glance.

  title="Custom run completion message"

/>

You'll use [Slack Workflow Builder](https://slack.com/help/articles/360053571454),
which can receive a webhook directly and map its JSON into a message, so no
separate automation account is required. If the
[Cypress Slack app](/cloud/integrations/slack) is already installed in the
workspace, linking `runUrl` in the message can unfurl the usual run actions
(**Compare to last run**, **See failures**, **See errors**, **Create Issue**).

### Prerequisites

- **Permission to manage webhooks** for the Cypress Cloud project. You must be an
  **Owner**, **Admin**, or **Team Admin**, or you can request one to add the necessary setting for you.
- **A Slack plan that includes Workflow Builder**, and permission to create and
  publish a workflow in your workspace. Conditional (if/else) steps require a
  paid Slack plan; a fallback that works on any plan is described below.
- **The channel or person** you want the message sent to.

### Step 1: Create a webhook-triggered Slack workflow

1. In Slack, open **Workflow Builder** and create a new workflow.
2. For the way the workflow starts, choose **Starts with a webhook**.
3. Under **Data Variables**, add a key for each payload field you want in the
   message. Slack reads these from the top-level keys of the JSON body. You will likely want to start with fields like this:

   - `message` (only present in Cypress Cloud's generic `webhook.ping` test event)
   - `status`
   - `projectName`
   - `runNumber`
   - `runUrl`
   - `commitBranch`
   - `totalTests`
   - `totalFailed`

   You can add any other [payload field](/cloud/integrations/webhooks#Payload)
   you plan to use, such as `commitMessage` or `commitAuthorName`.

   <DocsImage
     src="/img/cloud/guides/webhooks/slack-workflow-variables.png"
     alt="Slack Data Variables list mapping totalTests, commitMessage, runUrl, and projectName"
     title="Data Variables"
     width={720}
   />

4. Save the trigger. Slack generates a **Web request URL**. Click **Copy Link**;
   that URL becomes your Cypress Cloud **Payload URL** later. Treat it as a
   secret: anyone who has the link can trigger the workflow.

:::note

**Note**: Array fields such as `tags` and `groups` don't map cleanly to a Workflow Builder variable. If you need these in Slack, you may want to transform the response in another service, or contact us about updating the payload.

:::

### Step 2: Compose the message

If needed, add a check using a **Branch workflow**
step that checks fields such as `commitAuthorName`, `commitBranch`, `tags`, or
`ciProvider` to only send the message on certain conditions.

<DocsImage
  src="/img/cloud/guides/webhooks/slack-branch-by-author.png"
  alt="Branch workflow condition: if commitAuthorName equals a specific user, send that person a message"
  title="Route by commit author"
  width={720}
/>

Inside that branch, add a **Send a message to a channel** or **Send a message to a person** step. Choose the destination, and write the message, using **Insert a variable** to drop
in the fields you mapped in Step 1. For example:

```text
Hey! A {projectName} test run that just finished:

- Status: {status}
- Failures: {totalFailed} test(s) failed out of {totalTests} tests
```

Link the words "test run" (or the run number) to `{runUrl}` so the message opens
the run in Cypress Cloud.

<DocsImage
  src="/img/cloud/guides/webhooks/slack-compose-message.png"
  alt="Slack message composer with projectName, status, totalFailed, and totalTests inserted as variables"
  title="Compose the message"
  width={640}
/>

When a run completes, Slack replaces each variable with the value from the
payload.

:::tip

**Tip**: Slack workflows give you a huge amount of flexibility in how to set your team up for success, without any custom code.

In the screenshot above, the "Compare to last run", "See failures", and "See errors" buttons are all deep links to Cypress Cloud pages for that specific run, built using the branch and project variables from the webhook payload. This use Slack's **Interactive Buttons** to drive next actions and assign a custom URL.

The Create Issue button uses Slack's **built-in Jira integration** to start a ticket based on that run, but you could use any other next step (for example, PagerDuty) as well.

:::

### Step 3: Format passing and failing runs differently

The `status` field tells you how the run ended. Use it to make a failing run
stand out.

- **On a paid Slack plan**, add a **Branch workflow** step (If/else) before the
  message step. Set the condition to check whether the `status` variable equals
  `passed`. In the passing path, send a success-styled message; in the other
  path, send a failure-styled one, for example leading with a clear label and the
  failure count:

  ```text
  FAILED — Cypress run #{runNumber} for {projectName} on {commitBranch}
  {totalFailed} of {totalTests} tests failed. Investigate: {runUrl}
  ```

- **On any plan**, skip the branch and put the status directly in the text so the
  outcome is always spelled out in words, never by color alone:

  ```text
  [{status}] Cypress run #{runNumber} — {projectName} ({commitBranch})
  {totalFailed}/{totalTests} failed · {runUrl}
  ```

Because `status` can be `passed`, `failed`, `errored`, `timedOut`, or
`cancelled`, treat "not passed" as the attention case rather than checking only
for `failed`. That way an `errored` or `timedOut` run still gets your failure
formatting.

**Publish the workflow** when the message looks right.

### Step 4: Point the Cypress Cloud webhook at Slack

1. In Cypress Cloud, open your project's **Settings**, find the **Webhooks**
   panel, and click **Add webhook**. See
   [Create a webhook](/cloud/integrations/webhooks#Create-a-webhook).
2. Paste the Slack workflow's webhook URL as the **Payload URL**.
3. Leave `run.completed` selected. Save the webhook.

:::caution

**Security note**: You cannot use a
[signing secret](/cloud/integrations/webhooks#Verify-webhook-signatures) to
authenticate the request here. Treat the Slack webhook URL itself as a secret: don't
share it or commit it, since anyone who has it can post to your channel. For the
full tradeoff, see
[Send to a no-code destination](/cloud/integrations/webhooks#Send-to-a-no-code-destination).

:::

### Step 5: Test the delivery

Use **Send test** on the webhook to confirm Cypress Cloud can reach Slack. See
[Send a test event](/cloud/integrations/webhooks#Send-a-test-event).

:::note

**The test event is a `webhook.ping`, not a `run.completed`.** Its body is
`{ "message": "Webhook ping" }`, so it does **not** contain `status`,
`runNumber`, or the other run fields your message maps. Send test confirms the
connection and that the workflow fires; it will not render your mapped values.

To confirm the field mapping end to end, **record a Cypress run** so a fresh `run.completed` fires, if your project is not recording runs often enough for you to quickly see activity. You can trigger this run locally with a single test to avoid waiting on your full pipeline.

:::

### Step 6: Go live

Once a real delivery renders the message the way you want, you're done. The
workflow runs on every completed run. If you need to change the wording or fields
later, edit the Slack workflow and republish; the Payload URL stays the same, so
the Cypress Cloud webhook needs no change.

## GitHub status checks

Use the [GitHub integration](/cloud/integrations/github#Status-checks) to report
Cypress results on the pull request. It posts commit status checks per run group
or spec.

For a custom check, such as your own `context` name or a pass/fail rule on
`totalFailed` and `commitBranch`, point the **Payload URL** at
[Zapier](https://zapier.com), [Make](https://www.make.com), or
[n8n](https://n8n.io). That tool acts as a forwarder: it receives the Cypress
POST, then calls GitHub with `commitSha`, `status`, and `runUrl` so a
[`repository_dispatch`](https://docs.github.com/en/actions/using-workflows/events-that-trigger-workflows#repository_dispatch)
workflow can post the commit status. Store a GitHub token in the tool.

When a check fails and you want the tests, screenshots, or Test Replay for that
run, use the [Cloud CLI](/cloud/integrations/cloud-cli) or
[Cloud MCP](/cloud/integrations/cloud-mcp).

## Other options

- **Send to Microsoft Teams instead of Slack.** Microsoft Teams offers
  [Workflows](https://support.microsoft.com/office/browse-and-add-workflows-in-microsoft-teams-4998095c-8b72-4b0e-984c-f2ad39e6ba9a)
  with an incoming-webhook trigger that works the same way: create the flow, map
  the payload fields, and use its URL as the Payload URL. Cypress Cloud also has a
  built-in [Microsoft Teams integration](/cloud/integrations/microsoft-teams) for
  standard notifications.
- **Post to Google Chat.** Deploy an
  [Apps Script web app](https://developers.google.com/apps-script/guides/web)
  whose `doPost` reads the Cypress JSON and POSTs a message to a Chat
  [incoming webhook](https://developers.google.com/workspace/chat/quickstart/webhooks).
- **Filter what you act on.** Since `run.completed` fires for every terminal
  state, use your tool's filter step to continue only when `status` is not
  `passed`, or only when `totalFailed` is greater than zero, to cut noise.
- **Combine outcomes.** A single delivery can fan out: post to a channel, open a
  Jira ticket, and append a row to a reporting sheet from the same webhook, using
  a platform like Zapier, Make or n8n.
