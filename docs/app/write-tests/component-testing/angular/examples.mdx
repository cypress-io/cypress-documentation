# Angular Examples

To mount a component with `cy.mount()`, import the component and pass it to the
method:

```ts
import { StepperComponent } from './stepper.component'

it('mounts', () => {
  cy.mount(StepperComponent)
})
```

## Passing Data to a Component

You can pass inputs and outputs to a component by setting
[componentProperties](/app/component-testing/angular/api#MountConfig)
in the options:

```ts
cy.mount(StepperComponent, {
  componentProperties: {
    count: 100,
  },
})
```

## Testing Event Handlers

Pass a Cypress [spy](/app/guides/stubs-spies-and-clocks#Spies) to an event
prop and validate that the component called it:

```ts
it('clicking + fires a change event with the incremented value', () => {
  cy.mount(StepperComponent, {
    componentProperties: {
      change: createOutputSpy('changeSpy'),
    },
  })
  cy.get('[data-cy=increment]').click()
  cy.get('@changeSpy').should('have.been.calledWith', 1)
})
```

## Imports/Declarations/Providers

If you need to set up any additional `imports`, `declarations`, or `providers`
for your component to mount successfully, you can set them in the options
(similar to setting them up in `ngModule` in a app):

:::info
Cypress adds a standalone component to the test module's `imports`, so
`providers` work with standalone components, including the providers of any
module passed in `imports`. A standalone component's template uses only what
its own `imports` array lists. Components, directives, and pipes from
`declarations`, or exported by a module in `imports`, aren't available to that
template, and Angular throws an error if the standalone component itself is in
`declarations`.
:::

```ts
cy.mount(ComponentThatFetchesData, {
  imports: [HttpClientModule],
  declarations: [ButtonComponent],
  providers: [DataService],
})
```

See
[Default Declarations, Providers, or Imports](/app/component-testing/angular/examples#Default-Declarations-Providers-or-Imports)
to set up common options in a custom `cy.mount()` command to avoid having to
repeat this boilerplate for each test.

## Using Standalone

Not only are [Standalone Components](https://angular.io/guide/standalone-components) supported, they are the simplest components to write tests for.
Standalone Components provide the Angular compiler with everything it needs to compile through its [`@Component()`](https://angular.io/api/core/Component) decorator.
This self-sufficiency means that in most cases you can mount a Standalone Component without ever providing any `imports`, `decorators`, or `providers`. Mounting then becomes as simple as:

```ts
cy.mount(MyStandaloneComponent)
```

## Using Angular Template Syntax

The `cy.mount()` method also supports the Angular template syntax when mounting
a component. Some developers might prefer this approach to the object based
mount style:

```ts
cy.mount(`<app-stepper [count]="100"></app-stepper>`, {
  declarations: [StepperComponent],
})
```

> When using template syntax, the component needs to added to the declarations
> in the options parameter.

Using with event emitter spy:

```ts
cy.mount('<app-button (click)="onClick.emit($event)">Click me</app-button>', {
  declarations: [ButtonComponent]
  componentProperties: {
    onClick: createOutputSpy('onClickSpy'),
  },
})
cy.get('button').click();
cy.get('@onClickSpy').should('have.been.called');
```

## Accessing the Component Instance

To work with the component instance directly in a test, chain `.then()` off
`cy.mount()`. The `.then()` callback receives the subject that `cy.mount()`
yields: an object that holds the rendered `component` and its `fixture`.

The example below uses the component to spy on its `change` event emitter:

```ts
it('clicking + fires a change event with the incremented value', () => {
  cy.mount(
    '<app-stepper count="100" (change)="change.emit($event)"></app-stepper>',
    {
      componentProperties: { change: new EventEmitter() },
      declarations: [StepperComponent],
    }
  ).then((wrapper) => {
    console.log({ wrapper })
    cy.spy(wrapper.component.change, 'emit').as('changeSpy')
    return cy.wrap(wrapper).as('angular')
  })
  cy.get(incrementSelector).click()
  cy.get('@changeSpy').should('have.been.calledWith', 101)
})
```

## Get Angular services from dependency injection

Some of what a component does lands in a service rather than in its template. A
component test reaches that service through Angular's dependency injection to
confirm what a stateful fake recorded after a click, answer requests through
`HttpTestingController`, or dispatch actions to a state store.

`cy.mount()` yields the `fixture` and the `component`, and Cypress has no
built-in command for injection. A test calls `TestBed.inject()` instead:
`cypress/angular` mounts components with Angular's own `TestBed` from
`@angular/core/testing`, so the `TestBed` a spec imports is the one that
configured the mounted component, and `TestBed.inject()` returns providers from
that test module.

Call `TestBed.inject()` inside `.then()` after `cy.mount()`. The `CartService`
below keeps the cart in a signal, and `ProductComponent` adds to the cart
without displaying it:

```ts title="src/app/cart.service.ts"
import { Injectable, signal } from '@angular/core'

@Injectable({ providedIn: 'root' })
export class CartService {
  private readonly items = signal<string[]>([])

  add(product: string) {
    this.items.update((items) => [...items, product])
  }

  getItems() {
    return this.items()
  }
}
```

```ts title="src/app/product.component.ts"
import { Component, inject } from '@angular/core'
import { CartService } from './cart.service'

@Component({
  selector: 'app-product',
  template: `<button data-cy="buy" (click)="buy()">Buy</button>`,
})
export class ProductComponent {
  private readonly cart = inject(CartService)

  buy() {
    this.cart.add('Cypress T-shirt')
  }
}
```

The test clicks the `"Buy"` button, then checks the cart:

```ts title="src/app/product.component.cy.ts"
import { TestBed } from '@angular/core/testing'
import { CartService } from './cart.service'
import { ProductComponent } from './product.component'

it('adds the product to the cart', () => {
  cy.mount(ProductComponent)
  cy.get('[data-cy=buy]').click()

  cy.then(() => TestBed.inject(CartService))
    .invoke('getItems')
    .should('deep.equal', ['Cypress T-shirt'])
})
```

[`.invoke()`](/api/commands/invoke) calls `getItems()` again each time
`.should()` retries, so the assertion waits for the cart to update.

`TestBed.inject()` returns whatever the test module provides for a token. When
the test passes a fake in `providers`, such as
`{ provide: CartService, useValue: cartFake }`, `TestBed.inject(CartService)`
returns `cartFake`.

### Call `TestBed.inject()` inside the command chain

`cy.mount()` queues a command, and Cypress configures `TestBed` for the
component when that command runs, not when the test function calls
`cy.mount()`. A `TestBed.inject()` call at the top level of the test runs
before `cy.mount()` configures the test module, so Angular creates an empty test
module to answer the call, and the mount fails:

```ts title="src/app/product.component.cy.ts"
// ❌ Runs before cy.mount() configures TestBed
const cart = TestBed.inject(CartService)

cy.mount(ProductComponent)
```

```text
Error: Cannot configure the test module when the test module has already been instantiated. Make sure you are not using `inject` before `TestBed.configureTestingModule`.
```

Keep `TestBed.inject()` in a `.then()` callback, or in another command, that
comes after `cy.mount()`. Cypress also resets `TestBed` after each test and when
a test calls `cy.mount()` again, so inject the service again after each mount
rather than keeping a reference to the old instance.

### Get services from an Angular component's own injector

`TestBed.inject()` reads from the test module's injector. When a component lists
a service in its own `providers` array, Angular creates a separate instance for
that component, and `TestBed.inject()` returns the module's instance instead.
Get the component's instance from the injector on the `fixture` that
`cy.mount()` yields. This version of `ProductComponent` provides its own
`CartService`:

```ts title="src/app/product.component.ts"
import { Component, inject } from '@angular/core'
import { CartService } from './cart.service'

@Component({
  selector: 'app-product',
  template: `<button data-cy="buy" (click)="buy()">Buy</button>`,
  providers: [CartService],
})
export class ProductComponent {
  private readonly cart = inject(CartService)

  buy() {
    this.cart.add('Cypress T-shirt')
  }
}
```

The test aliases the component's cart, then checks it after the click:

```ts title="src/app/product.component.cy.ts"
import { CartService } from './cart.service'
import { ProductComponent } from './product.component'

it('adds the product to the component cart', () => {
  cy.mount(ProductComponent)
    .then(({ fixture }) => fixture.debugElement.injector.get(CartService))
    .as('cart')

  cy.get('[data-cy=buy]').click()

  cy.get<CartService>('@cart')
    .invoke('getItems')
    .should('deep.equal', ['Cypress T-shirt'])
})
```

### Answer HTTP requests with `HttpTestingController`

The same pattern drives Angular's testing controllers. The `UserListComponent`
below loads users with `HttpClient`:

```ts title="src/app/user-list.component.ts"
import { HttpClient } from '@angular/common/http'
import { Component, inject } from '@angular/core'
import { toSignal } from '@angular/core/rxjs-interop'

type User = { id: number; name: string }

@Component({
  selector: 'app-user-list',
  template: `
    <ul>
      @for (user of users(); track user.id) {
        <li>{{ user.name }}</li>
      }
    </ul>
  `,
})
export class UserListComponent {
  readonly users = toSignal(inject(HttpClient).get<User[]>('/api/users'), {
    initialValue: [],
  })
}
```

Provide `provideHttpClient()` and `provideHttpClientTesting()`, then answer the
request through `HttpTestingController`:

```ts title="src/app/user-list.component.cy.ts"
import { provideHttpClient } from '@angular/common/http'
import {
  HttpTestingController,
  provideHttpClientTesting,
} from '@angular/common/http/testing'
import { TestBed } from '@angular/core/testing'
import { UserListComponent } from './user-list.component'

it('lists the users the API returns', () => {
  cy.mount(UserListComponent, {
    providers: [provideHttpClient(), provideHttpClientTesting()],
  })

  cy.then(() => {
    TestBed.inject(HttpTestingController)
      .expectOne('/api/users')
      .flush([{ id: 1, name: 'Jane' }])
  })

  cy.get('li').should('have.text', 'Jane')
})
```

To stub the request at the network layer instead, leave out
`provideHttpClientTesting()` and stub `/api/users` with
[`cy.intercept()`](/api/commands/intercept).

### Add a custom `cy.inject()` command for Angular

To skip the `.then()` in each test, add an `inject` command to the component
support file, next to `mount`:

<Tabs groupId="cypress-lang">
<TabItem value="js" label="JavaScript">

```js title="cypress/support/component.js"
import { TestBed } from '@angular/core/testing'
import { mount } from 'cypress/angular'

Cypress.Commands.add('mount', mount)
Cypress.Commands.add('inject', (token) =>
  cy.wrap(TestBed.inject(token), { log: false })
)
```

</TabItem>
<TabItem value="ts" label="TypeScript">

```ts title="cypress/support/component.ts"
import { ProviderToken } from '@angular/core'
import { TestBed } from '@angular/core/testing'
import { mount } from 'cypress/angular'

declare global {
  namespace Cypress {
    interface Chainable {
      mount: typeof mount
      /**
       * Gets a provider from the Angular TestBed injector
       * @param token The class or InjectionToken to look up
       */
      inject<T>(token: ProviderToken<T>): Chainable<T>
    }
  }
}

Cypress.Commands.add('mount', mount)
Cypress.Commands.add('inject', (token) =>
  cy.wrap(TestBed.inject(token), { log: false })
)
```

</TabItem>
</Tabs>

The command yields the service through [`cy.wrap()`](/api/commands/wrap).
`{ log: false }` hides that inner `wrap`, so `cy.inject()` adds no entry of its
own to the Command Log, while the `.invoke()` and assertion after it still
appear. To show an `inject` entry, call
[`Cypress.log()`](/api/cypress-api/cypress-log) inside the command. Because
`cy.inject()` is a Cypress command, Cypress runs `TestBed.inject()` in order
after the commands before it, including `cy.mount()`. So `cy.inject()` works at
the top level of the test:

```ts title="src/app/product.component.cy.ts"
import { CartService } from './cart.service'
import { ProductComponent } from './product.component'

it('adds the product to the cart', () => {
  cy.mount(ProductComponent)
  cy.get('[data-cy=buy]').click()

  cy.inject(CartService)
    .invoke('getItems')
    .should('deep.equal', ['Cypress T-shirt'])
})
```

`cy.inject()` reads from `TestBed`, the same as `TestBed.inject()`. For a
service in a component's own `providers`, use the fixture's injector as shown in
[Get services from an Angular component's own injector](#Get-services-from-an-Angular-components-own-injector).

## Working with Legacy @Input() Decorators

With the release of Angular 18, [signals](https://angular.dev/guide/signals) became the preferred way to handle data binding.
However, legacy components that use `@Input()` and `@Output()` decorators are still supported.

Interacting with legacy `@Input()` decorators is a bit different than working with signals.
To update the `@Input()` value, you need to use the `componentRef.setInput` method so Angular change detection runs properly.
Otherwise, you may see errors.

```ts
cy.mount(StepperComponent, { componentProperties: { count: 100 } })
  .then(({ fixture }) => {
    return cy.contains('span', '100').wrap(fixture)
  })
  .then((fixture) => {
    fixture.componentRef.setInput('count', 110)
    return cy.contains('span', '110')
  })
```

## Using createOutputSpy()

To make spying on event emitters easier, there is a utility function called
`createOutputSpy()` which automatically creates an `EventEmitter`
and sets up the spy on its `.emit()` method. You can use `createOutputSpy()` like the following:

```ts
import { createOutputSpy } from 'cypress/angular'

it('clicking + fires a change event with the incremented value', () => {
  // Arrange
  cy.mount('<app-stepper (change)="change.emit($event)"></app-stepper>', {
    declarations: [StepperComponent],
    componentProperties: {
      change: createOutputSpy<boolean>('changeSpy'),
    },
  })
  cy.get(incrementSelector).click()
  cy.get('@changeSpy').should('have.been.called')
})
```

## Signals

:::info

With Cypress 14, signal support is directly included in the `cypress/angular` testing harness.

:::

The below examples work with a very simple component called `TestComponent`, which looks something like shown below:

```typescript
// app/components/test-component.component.ts
import { Component, input, model } from '@angular/core'

@Component({
  selector: 'test-component',
  templateUrl: './test-component.component.html',
  standalone: true,
})
export class TestComponent {
  title = input.required<string>()
  count = model<number>(1)
}
```

```html
<!-- app/components/test-component.component.html -->
<p data-cy="test-component-title-display">{{ title() }}</p>
<p data-cy="test-component-count-display">{{ count() }}</p>
<button data-cy="test-component-count-incr" (click)="count.set(count() + 1)">
  Increase
</button>
<button data-cy="test-component-count-decr" (click)="count.set(count() - 1)">
  Decrease
</button>
```

### Testing Signals

There are two ways to test signals within Cypress Component Testing:

1. [Inferred Generic Type](#Inferred-Generic-Type)
2. [Writable Signal](#Writable-Signal)

#### Inferred Generic Type

In the example below, the `title` prop being passed into our `TestComponent` is a `string`. A `string` is the generic type of our `input()` signal we defined in our `TestComponent`.

```typescript
let titleProp = 'Test Component'
cy.mount(TestComponent, {
  componentProperties: {
    title: titleProp,
  },
})

cy.get('[data-cy="test-component-title-display"]').should(
  'have.text',
  'Test Component'
)
```

:::info
Under the hood, Cypress wraps the generic value in a writable `signal()` and merges it into the prop. In other words, this example is really:

```typescript
cy.mount(TestComponent, {
  componentProperties: {
    title: signal('Test Component'),
  },
})
```

:::

Wrapping a generic value works for any signal. Shown below is an example of testing a `model()` signal with a generic type `number` as seen in our `TestComponent`:

```ts
cy.mount(TestComponent, {
  componentProperties: {
    title: 'Test Component',
    count: 3,
  },
})

cy.get('[data-cy="test-component-count-display"]').should('have.text', '3')
```

#### Writable Signal

Inferred generic types work very well for most test cases. However, they don't allow us to update the prop in the component after the prop is passed in. For this use case, we need to use a writable `signal()`.

A writable `signal()` allows us to test our one-way data binding for our `input()` signals.

```typescript
const myTitlePropAsSignal = signal('Test Component')
cy.mount(TestComponent, {
  componentProperties: {
    title: myTitlePropAsSignal,
  },
})

cy.get('[data-cy="test-component-title-display"]').should(
  'have.text',
  'Test Component'
)
cy.then(() => {
  // now set the input() through a signal to update the one-way binding
  myTitlePropAsSignal.set('FooBar')
})

cy.get('[data-cy="test-component-title-display"]').should('have.text', 'FooBar')
```

And our two-way data binding for our `model()` signals.

```typescript
let count = signal(5)
cy.mount(TestComponent, {
  componentProperties: {
    title: 'Test Component',
    count,
  },
})

cy.then(() => {
  // now set the model() through a signal to update the binding in the component
  count.set(8)
})

cy.get('[data-cy="test-component-count-display"]').should('have.text', '8')

// some action occurs that changes the count to 9 inside the component, which updates the binding in our test
cy.get('[data-cy="test-component-count-incr"]').click()
cy.get('[data-cy="test-component-count-display"]').should('have.text', '9')
cy.then(() => {
  expect(count()).to.equal(9)
})
```

#### Change Spies

Cypress doesn't propagate changes via spy from `input()` signals.

For writable signals, such as `model()`s or `signal()`s, Cypress **does** propagate changes if you create an output spy with the prop's name suffixed with `Change`. In the example below,
`countChange` spies on changes to the `count` signal.

```typescript
cy.mount(TestComponent, {
  componentProperties: {
    title: 'Test Component',
    count: 4,
    // @ts-expect-error
    countChange: createOutputSpy('countChange'),
  },
})

// some action occurs that changes the count
cy.get('[data-cy="test-component-count-incr"]').click()

cy.get('@countChange').should('have.been.called')
```

## Testing Error States

<ComponentTestingErrorStates />

```ts
import { UserProfileComponent } from './user-profile.component'

it('surfaces a render error', () => {
  cy.on('uncaught:exception', (err) => {
    // Assert on the error thrown during render...
    expect(err.message).to.include('user is required')

    // ...and return false so Cypress does not fail the test.
    return false
  })

  cy.mount(UserProfileComponent)
})
```

### Testing with a custom `ErrorHandler`

The recommended way to observe render errors in Angular is a custom
[`ErrorHandler`](https://angular.dev/api/core/ErrorHandler) provider. Angular
routes errors thrown during change detection to the `ErrorHandler`, so you can
provide one backed by a [`cy.stub()`](/api/commands/stub) and assert it was
called:

```ts
import { ErrorHandler } from '@angular/core'
import { ChildWithErrorComponent } from './child-with-error.component'

it('routes render errors to the ErrorHandler', () => {
  const handleError = cy.stub().as('handleError')

  // A custom ErrorHandler observes the error, but it does NOT stop the error
  // from propagating to Cypress as an uncaught exception. Cypress fails on
  // uncaught exceptions by default, so we must still suppress that behavior.
  cy.on('uncaught:exception', (err) => {
    // Only suppress the specific error we expect.
    expect(err.message).to.include('I crashed!')

    return false
  })

  cy.mount(ChildWithErrorComponent, {
    providers: [{ provide: ErrorHandler, useValue: { handleError } }],
  })

  cy.get('@handleError').should('have.been.called')
})
```

## Custom Mount Commands

### Customizing `cy.mount()`

By default, `cy.mount()` is a simple passthrough to `mount()`, however, you can
customize `cy.mount()` to fit your needs. For instance, you may find yourself
doing repetitive work during mounting. To reduce boilerplate you may
find it useful to create a custom mount command.

### Default Declarations, Providers, or Imports

If you find yourself registering a bunch of declarations, providers, or imports
in your individual tests, we recommend doing them all within a custom
`cy.mount()` command. The overhead is usually minimal for all your tests and it
helps keep your spec code clean.

Below is a sample that registers several default component declarations while
still letting you pass in additional ones via the config param. You can also
apply the same pattern to providers and module imports.

<Tabs>
<TabItem value="cypress/support/component.js">

```js
import { mount } from 'cypress/angular'
import { ButtonComponent } from 'src/app/button/button.component'
import { CardComponent } from 'src/app/card/card.component'

const declarations = [ButtonComponent, CardComponent]

function customMount(component, config) {
  if (!config) {
    config = { declarations }
  } else {
    config.declarations = [...(config?.declarations || []), ...declarations]
  }
  return mount(component, config)
}

Cypress.Commands.add('mount', customMount)
```

</TabItem>
<TabItem value="cypress/support/component.ts">

```ts
import { Type } from '@angular/core'
import { mount, MountConfig, MountResponse } from 'cypress/angular'
import { ButtonComponent } from 'src/app/button/button.component'
import { CardComponent } from 'src/app/card/card.component'

const declarations = [ButtonComponent, CardComponent]

function customMount<T>(component: string | Type<T>, config?: MountConfig<T>) {
  if (!config) {
    config = { declarations }
  } else {
    config.declarations = [...(config?.declarations || []), ...declarations]
  }
  return mount<T>(component, config)
}

declare global {
  namespace Cypress {
    interface Chainable {
      /**
       * Helper mount function for Angular Components
       * @param component Angular Component or template string to mount
       * @param config Options passed to Angular TestBed
       */
      mount<T>(
        component: string | Type<T>,
        config?: MountConfig<T>
      ): Cypress.Chainable<MountResponse<T>>
    }
  }
}

Cypress.Commands.add('mount', customMount)
```

</TabItem>
</Tabs>

This custom mount command skips manually passing in the
`ButtonComponent` and `CardComponent` as declarations into each `cy.mount()`
call.

### Mount components that use the Angular Router

If a component injects `ActivatedRoute` or `Router`, or its template uses a
directive such as `routerLink`, add the
[Angular Router](https://angular.dev/guide/routing) to the test with
[`provideRouter()`](https://angular.dev/api/router/provideRouter). Inside
`cy.mount()`, the Router reads its URL from the in-memory location that
Angular's testing module provides, not from the browser's address bar. Calling
`window.history.pushState()` changes what `cy.url()` reports but not the route
the component sees. The Router also skips the initial navigation an app runs at
startup, so the test tells the Router which URL to load.

Below is a sample mount command that provides the Router and navigates to an
`initialUrl` from the options, much like `initialEntries` for React Router's
`MemoryRouter`:

<Tabs groupId="cypress-lang">
<TabItem value="js" label="JavaScript">

```js title="cypress/support/component.js"
import { provideRouter, Router } from '@angular/router'
import { mount } from 'cypress/angular'

function customMount(component, config = {}) {
  const {
    routes = [],
    initialUrl = '/',
    providers = [],
    ...mountConfig
  } = config

  return mount(component, {
    ...mountConfig,
    // Providers from the test come last so they take precedence,
    // such as a stub for ActivatedRoute
    providers: [provideRouter(routes), ...providers],
  }).then((response) => {
    const router = response.fixture.debugElement.injector.get(Router)

    return cy
      .wrap(router.navigateByUrl(initialUrl), { log: false })
      .then(() => response)
  })
}

Cypress.Commands.add('mount', customMount)
```

</TabItem>
<TabItem value="ts" label="TypeScript">

```ts title="cypress/support/component.ts"
import { Type } from '@angular/core'
import { provideRouter, Router, Routes } from '@angular/router'
import { mount, MountConfig, MountResponse } from 'cypress/angular'

type RouterMountConfig<T> = MountConfig<T> & {
  routes?: Routes
  initialUrl?: string
}

function customMount<T>(
  component: string | Type<T>,
  config: RouterMountConfig<T> = {}
) {
  const {
    routes = [],
    initialUrl = '/',
    providers = [],
    ...mountConfig
  } = config

  return mount<T>(component, {
    ...mountConfig,
    // Providers from the test come last so they take precedence,
    // such as a stub for ActivatedRoute
    providers: [provideRouter(routes), ...providers],
  }).then((response) => {
    const router = response.fixture.debugElement.injector.get(Router)

    return cy
      .wrap(router.navigateByUrl(initialUrl), { log: false })
      .then(() => response)
  })
}

declare global {
  namespace Cypress {
    interface Chainable {
      /**
       * Helper mount function for Angular components that use the router
       * @param component Angular component or template string to mount
       * @param config Options passed to Angular TestBed, plus `routes` and `initialUrl`
       */
      mount<T>(
        component: string | Type<T>,
        config?: RouterMountConfig<T>
      ): Cypress.Chainable<MountResponse<T>>
    }
  }
}

Cypress.Commands.add('mount', customMount)
```

`router.navigateByUrl()` returns a promise, so the command wraps it with
[`cy.wrap()`](/api/commands/wrap) to have Cypress wait for the navigation to
finish before the test continues. Pass the app's `routes` when `initialUrl`
points to a path other than `/`, since the Router rejects a URL that matches no
route.

The component below reads a `name` query parameter from `ActivatedRoute`:

```ts title="src/app/greeting/greeting.ts"
import { Component, inject } from '@angular/core'
import { toSignal } from '@angular/core/rxjs-interop'
import { ActivatedRoute } from '@angular/router'
import { map } from 'rxjs'

@Component({
  selector: 'app-greeting',
  template: `<p data-cy="greeting">Hello, {{ name() ?? 'guest' }}</p>`,
})
export class Greeting {
  private readonly route = inject(ActivatedRoute)

  readonly name = toSignal(
    this.route.queryParamMap.pipe(map((params) => params.get('name')))
  )
}
```

To set up a scenario, pass the URL to load as `initialUrl`. The tests below
check the greeting with and without a query string:

```ts title="src/app/greeting/greeting.cy.ts"
import { Greeting } from './greeting'

it('greets a guest when the URL has no name', () => {
  // No need to pass an initialUrl, since the default URL is '/'
  cy.mount(Greeting)

  cy.get('[data-cy=greeting]').should('have.text', 'Hello, guest')
})

it('greets the name from the query string', () => {
  cy.mount(Greeting, { initialUrl: '/?name=Jane' })

  cy.get('[data-cy=greeting]').should('have.text', 'Hello, Jane')
})
```

The Router updates `queryParamMap` after the component renders, and `cy.mount()`
runs Angular without zone.js. Read route values into a signal, as `toSignal()`
does here, so the template updates when the navigation finishes. A plain class
property assigned inside `subscribe()` doesn't schedule change detection, so the
template keeps showing the value from before the navigation.

#### Stub ActivatedRoute instead of the Angular Router

When a component only reads from `ActivatedRoute`, provide a stub in place of
the real Router. The test then controls exactly what the route emits, and the
stub works with standalone components:

```ts title="src/app/greeting/greeting.cy.ts"
import { ActivatedRoute, convertToParamMap } from '@angular/router'
import { of } from 'rxjs'
import { Greeting } from './greeting'

it('greets the name from a stubbed route', () => {
  cy.mount(Greeting, {
    providers: [
      {
        provide: ActivatedRoute,
        useValue: { queryParamMap: of(convertToParamMap({ name: 'Jane' })) },
      },
    ],
  })

  cy.get('[data-cy=greeting]').should('have.text', 'Hello, Jane')
})
```

With the custom mount command above, the stub replaces the `ActivatedRoute`
that `provideRouter()` supplies, because providers from the test come last.
