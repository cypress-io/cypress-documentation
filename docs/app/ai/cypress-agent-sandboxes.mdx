# Run Cypress in an AI agent sandbox

Run Cypress in your AI agent's sandbox, so the agent tests its own changes
before it hands them back. The agent runs your specs with `cypress tap`, reads the
failures, and fixes them, instead of leaving that work to you.

Agents such as Claude Code on the web and Cursor Cloud run in a
sandbox: an isolated container or virtual machine with no screen and no person to click
through the Cypress App. [`cypress tap`](/app/tooling/cypress-tap) reads from a
running Cypress App in open mode, so the sandbox has to run that app too. This
page covers what the sandbox needs and how an agent starts a session on its own.

## How Cypress and an AI agent share a sandbox

Three things run in the same sandbox:

1. The agent, which runs shell commands
2. The Cypress App in open mode (`cypress open`), with a browser it launches
   for the selected testing type
3. `cypress tap` commands, which the agent runs to start specs and read results

`cypress tap` finds the Cypress session through files on the same machine and
talks to it over local connections. It cannot reach a Cypress App running on
another machine, so the agent and Cypress have to share one sandbox.

## Requirements for running Cypress in an agent sandbox

- Cypress 16.3.0 or later
- A Node.js version that Cypress supports (see
  [System requirements](/app/get-started/install-cypress#System-requirements))
- On Linux, the `xvfb` package
- Network access to the hosts in the table below
- A Chromium-based browser (see
  [Choose a browser](#Choose-a-browser-for-cypress-tap-in-a-sandbox))

A sandbox has no screen, so on Linux Cypress starts a virtual one for the app
and the browser using [Xvfb](https://www.x.org/releases/X11R7.6/doc/man/man1/Xvfb.1.xhtml).
To use a display you already have, set the `DISPLAY` environment variable. If
`DISPLAY` points to a display that isn't running, Cypress starts its own.

### Network hosts to allow in an agent sandbox

Many agent sandboxes block network traffic by default. Allow these hosts so the
Cypress binary downloads and the app can reach its services:

| Host                  | Used for                                        |
| --------------------- | ----------------------------------------------- |
| `registry.npmjs.org`  | Installing the `cypress` npm package            |
| `download.cypress.io` | Finding and downloading the Cypress binary      |
| `cdn.cypress.io`      | Downloading the Cypress binary                  |
| `api.cypress.io`      | Requests the Cypress App makes to Cypress Cloud |

Also allow the hosts your tests use, such as your app, APIs, and auth services,
and any package registries your project installs from other than npm.

:::note

If your app is only reachable from a corporate VPN, work with your network
security team to give the sandbox a route to it, such as through a proxy.

:::

## How Cypress detects an AI agent

Cypress recognizes common coding agents from the environment variables they
set. When it detects an agent, Cypress automates the parts of the Cypress App
that would otherwise wait for a click, such as the welcome screens, so the agent
can start a session with no one at the keyboard.

If Cypress doesn't recognize your agent, set `CYPRESS_AGENT_MODE=1` on the same
command line that starts Cypress. Some agents start a new shell for each
command, so a variable exported in one command isn't set in the next. See
[Environment variables](#Environment-variables).

## Keep the file changes an agent makes in a sandbox

An agent can create, edit, and delete files as part of its task, and those
changes stay inside the sandbox. Copy them back to your machine or commit them
to a branch before the sandbox goes away. How you find and keep those changes
depends on your agent and how you configured the sandbox, so check your agent's
documentation.

## Run Cypress tests non-interactively in a sandbox

[`cypress run`](/app/references/command-line#cypress-run) runs your specs and
reports whether they passed or failed, the same as in CI.

## Run Cypress tests interactively with cypress tap

With `cypress tap`, an agent runs specs one at a time, watches each run, and
queries the app under test along the way. In a sandbox, this needs a Cypress App
running in the background.

### Prepare the project

In a sandbox, Cypress uses your project's existing `cypress.config.*` file.

If the project has no configuration yet, Cypress creates one when an agent
starts it with `--e2e`. For component testing (`--component`), create the
configuration before you launch Cypress in a sandbox, so Cypress doesn't have to
guess your framework and bundler.

### Start Cypress in the background

Run `cypress open` with a browser and a testing type, and leave it running. Use
`nohup` so Cypress keeps running after the command that starts it returns:

```shell title="Command"
nohup npx cypress open --e2e --browser chromium --project . > cypress-open.log 2>&1 &
```

This command writes Cypress's output to `cypress-open.log`, including errors,
configuration problems, and the location of any files Cypress creates for you.
Tell your agent to read this file when something goes wrong.

When Cypress detects an agent, it skips the welcome screens as long as you pass
`--project`, `--browser` (or set `defaultBrowser` in the config), and a testing
type.

`cypress open --detached` waits until Cypress is ready before it returns, but
stops writing output after that point. Use the `nohup` form when you want the
ongoing log in `cypress-open.log`, which the troubleshooting steps on this page
rely on. Use `--detached` when you want the command to block until Cypress is
ready.

```shell title="Command"
npx cypress open --e2e --browser chromium --project . --detached
```

### Wait for the browser

The browser can take a while to start the first time. Poll `cypress tap status`
until it reports `browserAttached: true`. If the loop exits with an error or
times out, read `cypress-open.log` for the reason.

```shell title="Command"
deadline=$((SECONDS + 90))

until out=$(npx cypress tap status --json) && echo "$out" | grep -Eq '"browserAttached": *true'; do
  echo "$out" | grep -Eq '"status": *"error"' && { echo "$out"; exit 1; }
  [ "$SECONDS" -ge "$deadline" ] && { echo "no browser after 90 s; see cypress-open.log"; exit 1; }
  sleep 1
done
```

### Run specs and read the results

From here the agent uses the same commands as on a local machine:

```shell title="Command"
npx cypress tap run cypress/e2e/checkout.cy.ts
npx cypress tap status --json
npx cypress tap reporter --json
```

See
[Get started with the `cypress tap` commands](/app/tooling/cypress-tap#Get-started-with-the-cypress-tap-commands)
for the full loop and
[Poll `cypress tap status` for a verdict](/app/tooling/cypress-tap#Poll-cypress-tap-status-for-a-verdict)
for how to tell that a run finished. The
[`cypress-tap` skill](/app/tooling/ai-skills#cypress-tap) teaches an agent this
loop.

If `status` stays at `spec not selected` after you run a spec, run the spec again.

## Choose a browser for cypress tap in a sandbox

`cypress tap` works with Chromium-based browsers: Chrome, Chromium, Edge, and
Electron.

Pass Chrome or Chromium by name if it's on the `PATH`, or pass the path to its
executable:

```shell title="Command"
npx cypress open --e2e --browser /usr/bin/chromium --project .
```

Cypress checks the browser's `--version` output against the versions it knows,
such as `Chromium 123.0.6312.4`. A name is checked only against that browser's
pattern, while a path is checked against every pattern Cypress knows, so if a
name isn't recognized, try the full path. If neither works, Cypress doesn't
recognize that build. It writes the reason and the raw `--version` output to
`cypress-open.log`, and `cypress tap status` stays at `browser not selected`.

Many sandboxes come with a Chromium build that a browser-automation tool
installed. Run it with `--version` to check that it reports itself as Chromium,
then pass its path to `--browser`, or link it onto your `PATH` as `chromium` and
pass that name.

Electron ships with Cypress, so it works without installing a browser. Cypress
prints a deprecation warning when you use it, because Electron as a test browser
is [deprecated](/app/references/migration-guide#Migrating-away-from-the-Electron-browser).

Once a `cypress.config.*` file exists, setting
[`defaultBrowser`](/app/references/configuration#Browser) in it works the same
way as passing `--browser`, so you set the browser once instead of on every
command that starts Cypress. On the first launch of a project with no
configuration file, pass `--browser`.

## Configure Claude Code, Cursor, and other sandboxes

Expand your sandbox below for the setup it needs.

<AccordionBlock title="Claude Code on the web" icon={<Icon name="claude" />}>

1. In the environment's network settings, allow the hosts in
   [Network hosts to allow](#Network-hosts-to-allow-in-an-agent-sandbox).
2. In the environment's setup script, install your dependencies, which also
   downloads the Cypress binary:

   ```shell title="Setup script"
   npm ci
   ```

   As an alternative that lives in your repository, add a `SessionStart` hook
   that installs when the session runs on the web:

   ```json title=".claude/settings.json"
   {
     "hooks": {
       "SessionStart": [
         {
           "hooks": [
             {
               "type": "command",
               "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/session-start.sh"
             }
           ]
         }
       ]
     }
   }
   ```

   ```shell title=".claude/hooks/session-start.sh"
   #!/bin/bash
   set -euo pipefail
   [ "${CLAUDE_CODE_REMOTE:-}" = "true" ] || exit 0
   cd "$CLAUDE_PROJECT_DIR"
   npm install --no-audit --no-fund >&2
   npx cypress verify >&2 || { npx cypress install >&2; npx cypress verify >&2; }
   ```

3. Claude Code on the web already has `xvfb` and a Chromium build installed,
   but that Chromium isn't on the `PATH`. `DISPLAY` is unset, so Cypress
   starts its own Xvfb display (see
   [Requirements](#Requirements-for-running-Cypress-in-an-agent-sandbox)).
   Link the Chromium build onto your `PATH` as
   `chromium` so you can pass it by name, then start Cypress with it. Tell the
   agent to run these commands, or
   [add the recipe to your agent's instructions](#Add-the-recipe-to-your-agents-instructions).

   ```shell title="Command"
   mkdir -p ~/bin
   ln -sf "$(ls /opt/pw-browsers/chromium-*/chrome-linux/chrome | head -1)" ~/bin/chromium
   PATH="$HOME/bin:$PATH" nohup npx cypress open --e2e --browser chromium --project . > cypress-open.log 2>&1 &
   ```

</AccordionBlock>

<AccordionBlock title="Cursor Cloud" icon={<Icon name="hexagon-nodes" />}>

Cursor Cloud builds the environment from a Dockerfile and runs commands from
`.cursor/environment.json`.

```dockerfile title=".cursor/Dockerfile"
FROM cypress/browsers:<tag>
```

```json title=".cursor/environment.json"
{
  "build": { "dockerfile": "Dockerfile" },
  "install": "npm ci"
}
```

Use a
[`cypress/browsers` image](/app/continuous-integration/overview#Cypress-Docker-Images)
that matches your Node.js version in place of `<tag>`. This image comes with
Chrome, Firefox, and Edge, but not Chromium, so pass `--browser chrome` when
you [start Cypress](#Start-Cypress-in-the-background). Allow the hosts in
[Network hosts to allow](#Network-hosts-to-allow-in-an-agent-sandbox) in the
environment's network settings.

</AccordionBlock>

<AccordionBlock title="Other sandboxes" icon={<Icon name="laptop-code" />}>

Any other sandbox that meets the
[requirements](#Requirements-for-running-Cypress-in-an-agent-sandbox) can work,
including a local Docker container or an agent sandbox on your own machine.
Expect to install its dependencies and configure it yourself.

If the sandbox restricts where processes can write or which ports they can
open, allow writes to the Cypress binary cache folder (`CYPRESS_CACHE_FOLDER` in
[Environment variables](#Environment-variables)) and connections on
`127.0.0.1`.

</AccordionBlock>

## Environment variables

| Name                     | Description                                                                                                                                                                                                                                            |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `CYPRESS_AGENT_MODE`     | Set to `1` or `true` to make Cypress recognize this run as an AI agent, or to `0` or `false` to turn that off. It only controls recognition: skipping the welcome screen still needs `--project`, a browser (or `defaultBrowser`), and a testing type. |
| `CYPRESS_CACHE_FOLDER`   | [Changes the location of the Cypress binary cache](/app/references/advanced-installation#Binary-cache)                                                                                                                                                 |
| `CYPRESS_INSTALL_BINARY` | [Sets which Cypress binary to install: a version, URL, or local file](/app/references/advanced-installation#Install-binary)                                                                                                                            |

## Troubleshoot Cypress in an agent sandbox

- **The binary download fails.** The sandbox blocks `download.cypress.io` or
  `cdn.cypress.io`. Allow them, or use a mirror. See
  [Network hosts to allow](#Network-hosts-to-allow-in-an-agent-sandbox).

- **Cypress reports a missing system library.** The error names the library and
  an install command for Debian and Ubuntu. For a library it does not
  recognize, it gives an `apt-file search` command instead. `apt-file` is not
  installed by default, so install it first:

  ```shell title="Command"
  apt-get install apt-file && apt-file update
  ```

  Then install the library and run the command again.

- **Cypress reports that Xvfb is missing.** Install the `xvfb` package, or set
  `DISPLAY` to a display that is running.

- **`status` stays at `not connected`.** Cypress is not running yet, or it has
  not started loading the project. Read `cypress-open.log`.
  A project with a configuration file but no support file may also stay at
  `not connected` instead of reporting an error; check that
  `cypress/support/e2e.js` or `cypress/support/e2e.ts` exists.

- **`status` reports `error`.** The project failed to load: an invalid
  configuration file, or (for component testing) a dev server that failed to
  start. Cypress prints the same error to `cypress-open.log`, and
  `npx cypress tap status --json` includes it under `error`. After a
  configuration file fails to load, or `setupNodeEvents` throws, Cypress stops
  watching the configuration, so restart Cypress to pick up your fix.

- **`status` stays at `browser not selected`.** This can happen for two
  reasons. First, check that you passed `--project`, `--browser` (or set
  `defaultBrowser`), and a testing type to `cypress open`; if you already
  did, set `CYPRESS_AGENT_MODE=1`, since Cypress didn't recognize the agent.
  Second, if you pointed `--browser` at a path, Cypress may not have
  recognized the binary at that path; read the reason in `cypress-open.log`
  and see [Choose a browser](#Choose-a-browser-for-cypress-tap-in-a-sandbox).

- **Cypress ignores `ELECTRON_RUN_AS_NODE`.** Some agent environments set this
  variable, which makes Electron run as plain Node.js with no window.
  `cypress open` ignores it and prints a warning.

- **Component testing shows no session and no error.** Check that the
  configuration, support file, `component-index.html`, and bundler config (such
  as `vite.config.*`) exist, and that `setupNodeEvents` does not throw. Cypress
  does not scaffold component testing for an agent because it needs a
  framework and bundler to be chosen and their dependencies installed, so
  create these files first. To check the setup, run
  `npx cypress run --component --spec <spec>`.

- **`status` reports `not connected` for a session that was running.**
  `cypress tap` running in a different PID namespace than Cypress, such as a
  separate container sharing the filesystem, can decide the session is gone.
  Run `tap` in the same container as Cypress.

- **`cypress open` exits right away.** Run `npx cypress verify` to see why the
  Cypress binary cannot start.

## Limitations of Cypress in agent sandboxes

- The agent and Cypress have to run in the same sandbox.
- An open Cypress session with a browser uses about 2 GB of memory in a small
  project, and more in a larger one. Size the sandbox accordingly.
- Most agents don't persist the sandbox filesystem, so each new session
  downloads, extracts, and verifies the Cypress binary and your dependencies
  again. We recommend persisting the binary cache directory (see
  `CYPRESS_CACHE_FOLDER` in [Environment variables](#Environment-variables))
  if your agent supports it.
- `--detached` leaves the Xvfb that Cypress started running after Cypress
  exits. If more than one session shares the host, `pgrep Xvfb` can't tell
  their displays apart, and `pkill Xvfb` stops all of them. Give each session
  its own sandbox, torn down when the session ends.
- `cypress tap` has its own
  [limitations](/app/tooling/cypress-tap#Limitations-of-the-cypress-tap-CLI).
