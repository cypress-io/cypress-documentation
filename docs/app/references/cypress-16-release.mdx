# Cypress 16

Cypress 16 adds HTTP/2 support and makes four performance improvements the default. Every change on this page applies when you upgrade, without editing a spec.

Cypress 16 is also a major release with breaking changes. See [Before you upgrade](#Before-you-upgrade).

:::info

<WhatYoullLearn />

- What changed in Cypress 16 and whether it affects your project
- How to restore the previous behavior when you need it
- What to check before you upgrade

:::

## What changed

| Change                                                       | Previous behavior                                  | Affects                                      |
| ------------------------------------------------------------ | -------------------------------------------------- | -------------------------------------------- |
| Requests use HTTP/2 when the server supports it              | All requests used HTTP/1.1                         | Chromium-based browsers                      |
| `keystrokeDelay` defaults to `0`                             | Defaulted to `10` milliseconds                     | Every [`cy.type()`](/api/commands/type) call |
| Faster visibility algorithm is the default                   | Opt-in as `experimentalFastVisibility`             | Every visibility check                       |
| Cookie and storage commands are queries, so assertions retry | Read state once and failed if it was not ready yet | The five commands listed below               |
| `manageBrowserMemory` is on by default                       | Opt-in as `experimentalMemoryManagement`           | Chromium-based browsers                      |

Keeping Cypress up to date is the first item on the [priority checklist](/app/guides/test-performance#Priority-checklist) in our test performance guide, ahead of any configuration change you can make.

## HTTP/2 support

Cypress proxies every request between the browser and your servers so that commands like [`cy.intercept()`](/api/commands/intercept) can observe and modify network traffic. That proxy spoke HTTP/1.1, which meant your application ran over an older protocol under test than it does in production.

In Cypress 16, requests use HTTP/2 whenever the server supports it. Your tests do not change.

**Request-heavy pages load faster.** HTTP/2 multiplexes many requests over one connection instead of queuing them behind a small number of parallel slots. In our benchmark loading 1,000 images, the HTTP/2 page finished in 1,362ms compared to 3,896ms over HTTP/1.1. Pages that fire many small requests, such as those served by a Vite dev server, benefit most.

**Server-Sent Events are no longer capped at 6 connections.** Browsers limit Server-Sent Events to 6 connections per domain over HTTP/1.1, which put upload progress indicators, live notifications, and activity feeds out of reach. Over HTTP/2, the number of concurrent streams is negotiated with the server and defaults to 100.

HTTP/2 applies to Chromium-based browsers, including Chrome, Chromium, and Edge. Firefox and WebKit continue to use HTTP/1.1.

## Zero keystroke delay

[`cy.type()`](/api/commands/type) waited 10 milliseconds between keystrokes. In Cypress 16, [`keystrokeDelay`](/api/cypress-api/keyboard-api) defaults to `0`, and forms fill as fast as your application accepts the input.

If your application depends on the timing between keystrokes, such as an input with aggressive debouncing, restore the previous delay globally in a support file:

```js title="cypress/support/e2e.js"
Cypress.Keyboard.defaults({
  keystrokeDelay: 10,
})
```

Or set it for a single command:

```js title="spec.cy.js"
cy.get('#search').type('cypress', { delay: 10 })
```

## Faster visibility checks

Cypress runs a visibility algorithm every time it asserts or checks that an element is visible. The legacy algorithm walked up the ancestor tree and read CSS properties at each level, which repeatedly triggered layout recalculation in the browser.

Cypress 16 makes the faster algorithm the default. It calls the browser's built-in `checkVisibility()` method first, then confirms coverage with an adaptive point-sampling algorithm, which avoids most of that layout recalculation. We shipped it as [`experimentalFastVisibility`](/app/references/experiments#Experimental-Fast-Visibility) and are promoting it now that it has proven itself.

Suites with many visibility assertions see the largest improvement, as do suites that run against applications with large, deeply nested component trees.

## Retryable cookie and storage queries

Reading a cookie that was set asynchronously, after a redirect or a server round trip, could miss it by a few milliseconds and fail. These commands are now queries:

- [`cy.getCookie()`](/api/commands/getcookie)
- [`cy.getCookies()`](/api/commands/getcookies)
- [`cy.getAllCookies()`](/api/commands/getallcookies)
- [`cy.getAllLocalStorage()`](/api/commands/getalllocalstorage)
- [`cy.getAllSessionStorage()`](/api/commands/getallsessionstorage)

Assertions chained to a query re-read the underlying state and retry until they pass or time out:

```js title="spec.cy.js"
cy.getCookie('session_id').should('exist')
```

That assertion waits for the cookie the same way [`cy.get()`](/api/commands/get) waits for an element, which removes a common cause of flake.

## Browser memory management on by default

In a long run, the browser accumulates memory across tests. As memory pressure builds, the browser slows down and can crash before the suite finishes. [`experimentalMemoryManagement`](/app/references/experiments#Configuration) has addressed this since Cypress 12.4.0 by clearing memory between tests. In Cypress 16 it is stable, renamed to `manageBrowserMemory`, and enabled by default.

This is not a blanket speed improvement. Clearing memory takes time, paid on every test transition. It helps suites that get progressively slower as they run or that crash before finishing. On a suite that was never near a memory limit, it adds overhead instead. Measure your suite before and after, and turn it off if it does not help:

:::cypress-config-example

```ts
{
  manageBrowserMemory: false,
}
```

:::

`manageBrowserMemory` applies to Chromium-based browsers, including Chrome, Edge, and Electron. It has no effect in Firefox or WebKit. See [Manage memory accumulation](/app/guides/test-performance#Manage-memory-accumulation) for how to measure the impact on your suite.

## Updated runtime and browser versions

Cypress 16 ships on Node.js 24 and Chromium 146, and supports current major versions of the component testing toolchain, including Vite 8 and Angular 21 and 22. Each brings performance work that your tests inherit.

We also removed `experimentalSourceRewriting`, which could make a single [`cy.visit()`](/api/commands/visit) 5 to 10 times slower in projects that enabled it, along with several long-deprecated APIs.

## Before you upgrade

Cypress 16 is a major release. It removes several long-deprecated APIs, changes the defaults described above, and raises the minimum versions of Node.js, Vite, and Angular. The Electron browser is deprecated as a test browser and warns when selected, though it still runs tests in this release.

Read the [migration guide](/app/references/migration-guide) for the steps behind each change, and the [changelog](/app/references/changelog) for the full list.

To upgrade, install the latest version on a branch:

<PackageManagerTabs install="cypress@latest" dev />

Then run your suite in the [browsers your users use](/app/references/launching-browsers), and record the run to [Cypress Cloud](/cloud/get-started/introduction) to compare durations against your last run on Cypress 15.

If something behaves differently and the migration guide does not explain why, [open an issue](https://github.com/cypress-io/cypress/issues/new/choose).

## Common questions

### <Icon name="angle-right" /> Does Cypress support HTTP/2?

Yes, as of Cypress 16. HTTP/2 is enabled by default in Chromium-based browsers, including Chrome, Chromium, and Edge. Firefox and WebKit continue to use HTTP/1.1.

### <Icon name="angle-right" /> Do I need to change my tests to use HTTP/2?

No. Requests use HTTP/2 automatically when the server supports it.

### <Icon name="angle-right" /> Will Cypress 16 make my tests faster?

It depends on where your suite spends its time. The improvements are largest for suites with request-heavy pages, frequent typing, many visibility assertions, or long runs that hit memory pressure. Suites that are slow because of fixed waits, repeated logins through the UI, or slow real network calls are unaffected by these changes. Start with the [test performance guide](/app/guides/test-performance) to find your bottleneck.

### <Icon name="angle-right" /> Is the Electron browser removed in Cypress 16?

No. Electron is deprecated and warns when selected, but it still runs tests. We have not scheduled the major version that will remove it.

### <Icon name="angle-right" /> Is Cypress 16 a breaking release?

Yes. It removes several long-deprecated APIs, changes some defaults, and raises the minimum versions of Node.js, Vite, and Angular. The [migration guide](/app/references/migration-guide) covers the steps for each change.
