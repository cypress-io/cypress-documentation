# Environment Variables & Secrets

Cypress tests often need values that change across environments like API URLs, credentials, feature flags, or configuration toggles.

Not all values should be treated the same. Some are **secrets that must be protected**, while others are **safe to expose** and convenient to access synchronously.

This guide helps you choose the right API for your use case.

## Secrets and sensitive values

**Use [`cy.env()`](/api/commands/env)** for sensitive values like API keys, passwords, tokens, or credentials.

`cy.env()` retrieves only the values you explicitly request, when you need them, and avoids exposing all environment variables in browser state. This approach provides privileged access that doesn't automatically serialize values into browser context.

**Examples of secrets:**

- API keys
- Authentication tokens
- Passwords
- Database credentials
- Private service endpoints

```javascript
cy.env(['apiKey']).then(({ apiKey }) => {
  cy.request({
    url: 'https://api.example.com/data',
    headers: { Authorization: `Bearer ${apiKey}` },
  })
})
```

See the [`cy.env()`](/api/commands/env) command documentation for complete details.

### Handling the yielded value safely

Keep the value inside a `.then()` callback and pass it straight to the command
that needs it. [`.then()`](/api/commands/then) adds no entry to the Command Log.

## Public configuration values

**Use [`Cypress.expose()`](/api/cypress-api/expose)** for public, non-sensitive configuration values.

`Cypress.expose()` provides synchronous access to configuration that is safe to expose in the browser context. Values are accessible to application code, third-party scripts, and browser extensions.

**Examples of public configuration:**

- Feature flags
- API versions
- Plugin configuration
- Environment labels (staging, prod)
- Public service URLs

```javascript
const apiVersion = Cypress.expose('apiVersion') // Synchronous access
const featureFlag = Cypress.expose('featureFlag')

if (featureFlag) {
  cy.get(`[data-testid="feature-${apiVersion}"]`).should('be.visible')
}
```

See the [`Cypress.expose()`](/api/cypress-api/expose) API documentation for complete details.

## Set environment variables

You can set environment variables for `cy.env()` using several methods:

1. **Cypress configuration file** - Set in the `env` key of your Cypress configuration
1. **`cypress.env.json` file** - Create a `cypress.env.json` file in your project root
1. **`CYPRESS_*` environment variables** - Set OS-level environment variables with `CYPRESS_` prefix
1. **`--env` CLI flag** - Pass environment variables via command line
1. **`setupNodeEvents`** - Set dynamically in the `setupNodeEvents` function

### 1. Configuration File

Set environment variables in your Cypress configuration file under the `env` key:

:::cypress-config-example

```ts
{
  env: {
    apiUrl: 'https://api.example.com',
    apiKey: process.env.API_KEY, // From OS environment
  }
}
```

:::

### 2. `cypress.env.json`

Create a `cypress.env.json` file in your project root. Values here override conflicting environment variables in your Cypress configuration.

`cypress.env.json` sets only `cy.env()` values. A `baseUrl` key in the file
doesn't change the `baseUrl` configuration option. See
[Configuration overrides vs. cy.env() values](#Configuration-overrides-vs-cyenv-values).

```json
{
  "host": "veronica.dev.local",
  "api_server": "http://localhost:8888/api/v1/"
}
```

:::caution

**Important**: Add `cypress.env.json` to `.gitignore` if it contains sensitive data.

:::

### 3. `CYPRESS_*` environment variables

Set OS-level environment variables with the `CYPRESS_` or `cypress_` prefix:

```shell
export CYPRESS_HOST=laura.dev.local
export cypress_api_server=http://localhost:8888/api/v1/
```

Cypress removes the leading `CYPRESS_` or `cypress_` prefix and keeps the rest
of the name exactly as written, so the variables above are read as
`cy.env(['HOST'])` and `cy.env(['api_server'])`.

A `CYPRESS_*` variable named after a configuration option, such as
`CYPRESS_BASE_URL`, sets that option instead and isn't readable with
`cy.env()`. See
[CYPRESS\_\* variables named after configuration options](#CYPRESS_-variables-named-after-configuration-options).

:::danger

The environment variable `CYPRESS_INTERNAL_ENV` is reserved, so don't set it.

:::

:::note

The Cypress CLI and Cypress Cloud consume some `CYPRESS_`-prefixed variables
rather than treating them as test environment variables. Most notably, Cypress
reads [`CYPRESS_RECORD_KEY`](/app/references/command-line#cypress-run-record-key-lt-record-key-gt)
and [`CYPRESS_PROJECT_ID`](/cloud/account-management/projects#Project-ID)
directly from your operating system environment when recording to Cypress
Cloud. You must set both variables as OS-level environment variables (as shown above) and
**cannot** supply them through `cypress.env.json` or the `env` block of your
Cypress configuration.

:::

### 4. `--env` CLI flag

Pass environment variables via the command line. Separate multiple values with a comma, not a space. In some shells, like Windows PowerShell, you may need to surround the key/value pair with quotes.

```shell
cypress run --env host=kevin.dev.local,api_server=http://localhost:8888/api/v1
```

To pass a complex value, such as an object with nested fields, provide it as a
JSON string. A JSON string is also the way to include values that contain commas, spaces,
or quotes, since those characters would otherwise be interpreted by the shell or
as delimiters.

```shell
cypress run --env credentials='{"apiKey":"secret-key-12345","auth":{"user":"jane","token":"abc123"}}'
```

See the [`--env`](/app/references/command-line#cypress-run-env-lt-env-gt) command
line reference for more details.

Like `cypress.env.json`, `--env` sets only `cy.env()` values. To change a
configuration option such as `baseUrl` from the command line, use
[`--config`](/app/references/command-line#cypress-run-config-lt-config-gt)
instead.

### 5. setupNodeEvents

Set environment variables dynamically in the `setupNodeEvents` function:

:::cypress-config-plugin-example

```ts
export default defineConfig({
  e2e: {
    setupNodeEvents(on, config) {
      config.env.apiKey = process.env.API_KEY
      return config
    },
  },
})
```

:::

## Configuration overrides vs. cy.env() values

Setting `baseUrl` in `cypress.env.json` or with `--env baseUrl=...` doesn't
change where [`cy.visit()`](/api/commands/visit) goes. Those two methods only
set values for `cy.env()`. Configuration options such as `baseUrl`,
`viewportWidth`, or `defaultCommandTimeout` change only through the methods
that reach the Cypress configuration:

| Method                                                                           | Changes configuration options | Sets `cy.env()` values |
| -------------------------------------------------------------------------------- | ----------------------------- | ---------------------- |
| `--config` CLI flag                                                              | Yes                           | No                     |
| `--env` CLI flag                                                                 | No                            | Yes                    |
| Cypress configuration file                                                       | Yes                           | Yes, in the `env` key  |
| `cypress.env.json`                                                               | No                            | Yes                    |
| `CYPRESS_*` variable named after a configuration option, like `CYPRESS_BASE_URL` | Yes                           | No                     |
| Any other `CYPRESS_*` variable, like `CYPRESS_HOST`                              | No                            | Yes                    |
| `setupNodeEvents`                                                                | Yes                           | Yes, in `config.env`   |

Whatever `setupNodeEvents` returns takes precedence over the other methods in
this table.

### CYPRESS\_\* variables named after configuration options

Cypress checks every `CYPRESS_*` variable against the names of its
configuration options. A variable matches when the name after the prefix is
the option name as written (`CYPRESS_baseUrl`) or the option name in upper
snake case (`CYPRESS_BASE_URL`). A matching variable sets that configuration
option, and Cypress removes the variable from the values `cy.env()` reads:

```shell
export CYPRESS_BASE_URL=http://localhost:8080
```

```javascript title="cypress/e2e/spec.cy.js"
it('reads baseUrl from configuration, not from cy.env()', () => {
  expect(Cypress.config('baseUrl')).to.eq('http://localhost:8080')

  cy.env(['BASE_URL', 'baseUrl']).then(({ BASE_URL, baseUrl }) => {
    expect(BASE_URL).to.be.undefined
    expect(baseUrl).to.be.undefined
  })
})
```

To use the same value as a configuration option and in `cy.env()`, set it
under a name that isn't a configuration option, such as `CYPRESS_APP_URL`, and
read that name with `cy.env()`.

### Override baseUrl locally without committing it

To point your own runs at a different server while the committed configuration
keeps its default, read a variable of your own in the configuration file:

:::cypress-config-example

```ts
{
  e2e: {
    baseUrl: process.env.BASE_URL || 'http://localhost:3000',
  },
}
```

:::

```shell
BASE_URL=http://localhost:8080 npx cypress open
```

The configuration file reads `BASE_URL` each time Cypress loads it, so a value
from a git-ignored `.env` file that you load with a package such as `dotenv`
works the same way. Cypress reads `CYPRESS_*` variables from the environment
it starts in, before it loads the configuration file, so setting
`process.env.CYPRESS_BASE_URL` from inside the configuration file has no
effect. Read a variable of your own instead, as shown above.

## Set exposed configuration

You can set exposed configuration for `Cypress.expose()` via:

1. **Cypress configuration file** - Set in the `expose` key of your Cypress configuration
1. **`--expose` CLI flag** - Pass exposed configuration via command line

### 1. Configuration file

Set exposed configuration in your Cypress configuration file under the `expose` key:

:::cypress-config-example

```ts
{
  expose: {
    apiVersion: 'v2',
    featureFlag: true,
    environment: 'staging',
  }
}
```

:::

### 2. `--expose` CLI flag

Pass exposed configuration via the command line:

```shell
cypress run --expose apiVersion=v2,featureFlag=true
```

See the [`Cypress.expose()`](/api/cypress-api/expose) API documentation for complete details on setting exposed configuration.

## Migrate from Cypress.env()

`Cypress.env()` was removed in Cypress 16.0. If your tests still call it, migrate each value to the appropriate modern API:

- **Sensitive values** → [`cy.env()`](/api/commands/env)
- **Public configuration** → [`Cypress.expose()`](/api/cypress-api/expose)

See the [Migration Guide](/app/references/migration-guide#Migrating-away-from-Cypressenv) for detailed migration instructions.
