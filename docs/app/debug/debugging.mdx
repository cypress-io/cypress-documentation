# Debugging

Your Cypress test code runs in the same run loop as your application, so
you have access to the code running on the page, as well as the things the
browser makes available to you, like `document`, `window`, and `debugger`.

Based on those statements, you might be tempted to throw a `debugger` into your
test, like so:

:::visit-mount-example

```js
it('let me debug like a fiend', () => {
  -{cy.visit('/my/page/path')::cy.mount(<MyComponent />)}-

  cy.get('[data-testid="selector-in-question"]')

  debugger // Doesn't work
})
```

:::

The `debugger` statement may not work exactly as you are expecting. As you may remember from the
[Introduction to Cypress](/app/core-concepts/introduction-to-cypress), `cy`
commands enqueue an action to be taken later. Can you see what the test above
does given that perspective?

Both [`cy.visit()`](/api/commands/visit) and [`cy.get()`](/api/commands/get)
return immediately, having enqueued their work to be done later, and
`debugger` executes before any of the commands have actually run. You can
expect the same behavior in Component Tests when using
[`cy.mount()`](/api/commands/mount).

Let's use [`.then()`](/api/commands/then) to tap into the Cypress command during
execution and add a `debugger` at the appropriate time:

:::visit-mount-example

```js
it('let me debug when the after the command executes', () => {
  -{cy.visit('/my/page/path')::cy.mount(<MyComponent />)}-

  cy.get('[data-testid="selector-in-question"]').then(($selectedElement) => {
    // Debugger is hit after the cy.visit
    // and cy.get commands have completed
    debugger
  })
})
```

:::

Now we're in business! When you're visiting a page or mounting a component for
the first time, (shown above with the [`cy.get()`](/api/commands/get)chain and
its [`.then()`](/api/commands/then) attached) Cypress enqueues the commands
to execute. The `it` block exits, and Cypress starts its work:

1. In an end-to-end test, Cypress visits the page and waits for it to load.
   Alternatively, Cypress mounts and renders the component in a Component Test.
2. Cypress queries the element, and automatically waits and retries for a few
   moments if it doesn't find the element immediately.
3. Cypress executes the function passed to [`.then()`](/api/commands/then),
   yielding the found element to it.
4. Within the context of the [`.then()`](/api/commands/then) function, the
   `debugger` statement runs, halting the browser and calling focus to the Developer
   Tools.
5. You're in! Inspect the state of your application like you normally would if
   you'd dropped the `debugger` into your application code.

## Using [`.debug()`](/api/commands/debug)

Cypress also exposes a shortcut for debugging commands,
[`.debug()`](/api/commands/debug). Let's rewrite the test above using this
helper method:

:::visit-mount-example

```js
it('let me debug like a fiend', () => {
  -{cy.visit('/my/page/path')::cy.mount(<MyComponent />)}-

  cy.get('[data-testid="selector-in-question"]').debug()
})
```

:::

Cypress exposes the current subject that [`cy.get()`](/api/commands/get)
yields as the variable `subject` within your Developer Tools so that you can
interact with it in the console.

<DocsImage
  src="/img/app/debugging/debugging-subject.png"
  alt="Debugging Subject"
/>

Use [`.debug()`](/api/commands/debug) to quickly inspect any (or many!) part(s)
of your application during the test. You can attach it to any Cypress chain of
commands to have a look at the system's state at that moment.

## Step through test commands

You can run the test command by command using the
[`.pause()`](/api/commands/pause) command.

```javascript
it('adds items', () => {
  cy.pause()
  cy.get('[data-testid="new-todo"]')
  // more commands
})
```

Stepping with `cy.pause()` stops after each command, so you can inspect the web application, the DOM,
the network, and any storage to make sure everything happens as expected.

## Debug with an AI agent

Everything above puts you in front of the Cypress app. If you are working with
an AI coding agent, it can read the same information from the terminal with the
[`cypress tap`](/app/tooling/cypress-tap) CLI: run the spec you just changed,
poll the run's status, read the failing test's Command Log and error, and
inspect the DOM of the app under test at the moment a command ran.

Reading that information from the terminal closes the loop without you relaying failures back and forth. Start
Cypress with `cypress open`, then let your agent drive it from another
terminal.

```shell
npx cypress tap run cypress/e2e/checkout.cy.ts
npx cypress tap status --json
npx cypress tap reporter --test-id <id>
```

The [`cypress-tap` skill](/app/tooling/ai-skills#cypress-tap) is the easiest way
to hand this loop to your agent: it packages these commands so your agent drives
them correctly, without you writing the steps by hand. For the full workflow, or
a snippet you can drop into your agent's instructions file yourself, see
[driving Cypress from the terminal with an AI agent](/app/tooling/cypress-tap).

When the failure happened in CI rather than locally, and you recorded the run to
Cypress Cloud, your agent can triage it from the terminal too. The
[`cypress-cloud-cli` skill](/app/tooling/ai-skills#cypress-cloud-cli) drives the
[Cloud CLI](/cloud/integrations/cloud-cli) to read the failing run, its tests,
and their [Test Replay](/cloud/features/test-replay) data, so the agent can find
the likely cause from the recorded run before reproducing it locally with
`cypress tap`.

## Errors

Sometimes tests fail. Sometimes we want them to fail, just so we know they're
testing the right thing when they pass. But other times, tests fail
unintentionally and we need to figure out why. Cypress provides some tools to
help make that process as easy as possible.

## Debugging flake

While Cypress is
[flake-resistant](/app/get-started/why-cypress#Flake-resistant), some users
do experience flake, particularly when running in CI versus locally.

:::tip
To debug flake in your recorded tests in CI, try out [Test Replay](/cloud/features/test-replay) in Cypress Cloud.
Test Replay replays the test exactly as it ran in CI.
:::

Most often
in cases of flaky tests, we see that there are not enough assertions surrounding
test actions or network requests before moving on to the next assertion.

If there is any variation in the speed of the network requests or responses when
run locally versus in CI, then there can be failures in one over the other.

Because of this, we recommend asserting on as many required steps as possible
before moving forward with the test. Asserting on each step also helps later to isolate where the
exact failure is when debugging.

Flake can also occur when there are differences between your local and CI
environments. You can use the following methods troubleshoot tests that pass
locally but fail in CI.

- Review your CI build process to ensure nothing is changing with your
  application that would result in failing tests.
- Remove time-sensitive variability in your tests. For example, ensure a network
  request has finished before looking for the DOM element that relies on the
  data from that network request. You can use
  [aliasing](/app/core-concepts/variables-and-aliases#Aliases) for this.

Cypress Cloud also offers [Analytics](/cloud/features/analytics/overview) that illustrate
trends in your tests and can help identify the tests that flake or fail most often. Analytics
could help narrow down what is causing the flake -- for example, seeing
increased failures after a change to the test environment could indicate issues
with the new environment.

For more advice on dealing with flake read a
[series of our blog posts](https://cypress.io/blog/tag/flake/) and
[Identifying Code Smells in Cypress](https://codingitwrong.com/2020/10/09/identifying-code-smells-in-cypress.html).

## Debug setupNodeEvents and tasks with a Node debugger

The tools above debug code that runs in the browser. Your
[`setupNodeEvents`](/app/references/configuration#setupNodeEvents) function, its
[`cy.task()`](/api/commands/task) handlers, preprocessors, and component testing
dev servers run in Node.js instead, in a
[separate config process](/api/node-events/overview#Execution-context) that
Cypress starts on your system's Node.js. Attach a Node debugger to that process
to set breakpoints and step through your Node code the way you would in any
other Node program.

Cypress passes the `NODE_OPTIONS` environment variable you start it with on to
the config process, so that's where the debugger setup goes. The `--dev`,
`--inspect`, and `--inspect-brk` command line flags are for developing Cypress
itself, and an installed Cypress exits with an error when you pass them.

### Debug the Cypress config process in VS Code

VS Code's JavaScript Debug Terminal attaches to every Node process it starts,
including the Cypress config process, with no extra configuration:

1. Open the Command Palette and run **Debug: JavaScript Debug Terminal**.
2. Start Cypress from that terminal:

   <CypressCommandTabs command="open" />

3. Set a breakpoint in your Cypress configuration file or a file it imports,
   or add a `debugger` statement, as in this `cy.task()` handler.

:::cypress-config-plugin-example

```ts
const users = [{ email: 'jane@cypress.io', name: 'Jane Lane' }]
```

```ts
on('task', {
  findUser(email) {
    debugger // pauses here each time a test calls cy.task('findUser')
    return users.find((user) => user.email === email) ?? null
  },
})
```

:::

VS Code pauses at the breakpoint the next time Cypress runs that code. In
`cypress open`, Cypress restarts the config process each time you save your
configuration file or a file it imports. VS Code attaches to the new process
too, so your breakpoints keep working without restarting Cypress.

If you use VS Code's auto attach in a regular terminal instead, set it to
**Always**. In the default **Smart** mode, VS Code skips the config process,
because Cypress runs it from the Cypress cache, outside your workspace.

### Attach another Node debugger to the Cypress config process

WebStorm, Chrome DevTools, and other debuggers that speak the Node inspector
protocol attach to a process that has its inspector open. Set `NODE_OPTIONS` to
`--inspect=0` when you start Cypress:

```shell
NODE_OPTIONS=--inspect=0 npx cypress open
```

On Windows, set the variable with your shell's syntax, such as
`$env:NODE_OPTIONS="--inspect=0"` in PowerShell, then run `npx cypress open`.

Every Node process that inherits the variable prints the address its inspector
listens on. Your package manager and the Cypress CLI print theirs first, and the
config process prints the last one before Cypress loads your configuration:

```text
Debugger listening on ws://127.0.0.1:43857/3c346074-6f70-45b9-8ff8-c399a826dd21
```

Attach your debugger to that address. Keep these behaviors in mind:

- `--inspect=0` gives each process a free port. A fixed port such as
  `--inspect=9229` never reaches the config process: your package manager or
  the Cypress CLI takes the port first, and the config process starts without
  an inspector after printing
  `Starting inspector on 127.0.0.1:9229 failed: address already in use`.
- `--inspect-brk` in `NODE_OPTIONS` pauses the first Node process, your package
  manager or the Cypress CLI, and Cypress doesn't start until you attach a
  debugger to it and resume.
- Cypress loads your configuration before you have time to attach by hand, so a
  debugger you attach yourself stops in `cy.task()` handlers and other events
  that run later, not in the first run of `setupNodeEvents`. To stop there too,
  use the VS Code JavaScript Debug Terminal, which attaches as each process
  starts.
- Each restart of the config process in `cypress open` opens a new inspector on
  a new port, so attach to the new address after you change your configuration.
